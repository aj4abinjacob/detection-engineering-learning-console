Release v1 so a stranger can reproduce and recover it.

A release is evidence: clean checkout, meaningful tests, local Docker instructions, README, dependency/secret review, rollback plan, and an article explaining URL to handler.

Why it matters

Release readiness is not “works on my machine.” It is a bounded, repeatable proof that documented code can be tested, built, run locally, reviewed, and rolled back.

Declare v1 scope

List supported routes, auth/authz behavior, known limitations, local-only deployment assumptions, data handling, and out-of-scope production claims. A small explicit v1 is stronger than an undocumented broad claim.

At least 40 meaningful tests

Plan tests across normal, boundary, failure, authz, CSRF/cookies, parsing, persistence, and proxy/security behaviors. Count meaningful independent behavior, not generated duplicates. Save full-suite command/version/result.

Clean-checkout reproduction

Use a fresh local worktree/directory and only README steps. Record OS, language/runtime, dependency lock state, exact commands, expected outputs, and failures. Do not modify shared repository state for the exercise.

# From the root of your own AbuseGuard repository; choose a new explicit path.
git worktree add ../abuseguard-v1-proof HEAD
cd ../abuseguard-v1-proof
# Now follow README commands exactly and capture exit codes/sanitized output.

git worktree requires repository context; alternatively use git -C /explicit/repo/path worktree add /explicit/new/path HEAD. A worktree changes repository metadata and must use an explicit new path in your own repository. After preserving evidence and leaving the added worktree, remove that exact registered path from the original repository with git worktree remove /explicit/new/path. Never use broad recursive cleanup.

Clean local Docker evidence

Build/run only local approved Compose setup with synthetic configuration. Document ports, env variables by name not value, health check, shutdown, and cleanup targets. Do not publish images or expose services without separate authority.

docker compose config --quiet
docker compose build
docker compose up --detach
docker compose ps
curl --fail --show-error http://127.0.0.1:8080/health
# Preserve sanitized logs, then stop this explicitly scoped local project:
docker compose down

README is the deployment contract

Include prerequisites, setup, test, migration, local run, security configuration, troubleshooting, data/secret policy, and rollback. A stranger should not need hidden terminal history or private credentials.

Dependencies, SBOM, secrets

If approved tools are available, save SBOM/dependency/secret-check outputs with tool/version/time and review findings. If unavailable, record the gap and manual dependency inventory; do not install tools or claim a scan occurred. Never archive secrets in reports.

Rollback is a release requirement

Define previous version/artifact, schema migration reversibility, backup/restore point, feature/config switch, verification, owner, and communication. A database migration may require forward fix rather than downgrade; say so before release.

Write the URL-to-handler article

Explain URL parsing, DNS, TCP, TLS, HTTP, reverse proxy, application routing/authz, DB, and response. Name one threat/control at each layer and distinguish facts from deployment assumptions.

Release scenarios

README misses a variable

Clean checkout fails; update docs and rerun rather than relying on local shell state.

Test count is high but authz absent

Add meaningful cross-tenant/security tests; count is not quality alone.

Dependency tool unavailable

Record tool gap/manual inventory, do not fabricate SBOM results.

Migration rollback impossible

Document forward remediation, backup, and release gate before deploy.
