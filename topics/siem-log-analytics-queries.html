Purpose

Why this matters in detection engineering

A log query has two stages: select the relevant event population, then aggregate or correlate it over an explicit time and entity boundary. KQL filters documents; use ESQL or another aggregation facility for counts and windows.

A detection engineer must be able to trace how an observation becomes a feature, how that feature supports an inference, and how policy turns the inference into an action. The useful unit for this topic is five saved, versioned queries over sanitized AbuseGuard JSON with field mappings, time range, expected result, and negative case. Preserve enough lineage to reproduce it without collecting content that the decision does not require.

Boundaries

What can go wrong

Closest legitimate lookalike: normal release traffic, monitoring, retries, and route migrations can match a syntactically correct query.

Pipeline or interpretation failure: text-versus-keyword mappings, timezone defaults, missing fields, high-cardinality grouping, and unbounded searches change meaning or cost.

Safety boundary: work only with supplied sanitized fixtures or systems and accounts you own and are authorized to test. Minimize identifiers, exclude secrets and content, bound retention and access, and provide an accessible path when an automated action could affect a person.

Do not overclaimThis guide establishes a method for controlled defensive evidence. It does not prove identity, intent, causality, universal tool behavior, or how a third-party system will classify traffic.

Method

A repeatable defensive workflow

  1. Declare the question and scope. Name the owned route, entity, time range, authorization, expected population, and prohibited data before collection.
  2. Version the evidence. Save five saved, versioned queries over sanitized AbuseGuard JSON with field mappings, time range, expected result, and negative case, its schema or tool version, observation point, event and availability times, and missing-value behavior.
  3. Build a negative control. Include normal release traffic, monitoring, retries, and route migrations can match a syntactically correct query and state the response it should receive.
  4. Replay and decide. Recompute from immutable input, compare expected output, inspect false positives and false negatives, then apply test each query against a fixed fixture and annotate whether it filters, aggregates, or powers an alert.

Practice

Detection-engineering scenarios

BASELINE

1. The observed distribution changes

Trigger: a monitor for Log query languages detection engineers use daily: Elastic KQL / ES|QL and Splunk SPL — not just SQL shifts outside its recorded baseline. Artifact: five saved, versioned queries over sanitized AbuseGuard JSON with field mappings, time range, expected result, and negative case. Reasoning: compare time, producer, release, population, and data quality before attributing the shift to abuse. Boundary: a changed distribution is an observed fact, not a malicious label.

LOOKALIKE

2. A legitimate journey matches the candidate

Trigger: the candidate logic fires on normal release traffic, monitoring, retries, and route migrations can match a syntactically correct query. Artifact: a labeled negative-control replay. Reasoning: preserve the case, inspect which feature dominated, and choose a proportionate fallback. Boundary: do not tune the case away without measuring what new false negatives the change creates.

QUALITY

3. The pipeline changes while the rule stays green

Trigger: text-versus-keyword mappings, timezone defaults, missing fields, high-cardinality grouping, and unbounded searches change meaning or cost. Artifact: contract-test result, schema versions, and quality counters. Reasoning: quarantine or mark degraded evidence and restore the producer contract before judging detection quality. Boundary: absence, default values, and parser failures are not benign observations.

POLICY

4. Evidence is strong enough to review, not to punish

Trigger: several versioned signals agree on an unusual owned-lab journey. Artifact: feature lineage, reason codes, policy version, and expected guardrails. Reasoning: test each query against a fixed fixture and annotate whether it filters, aggregates, or powers an alert. Boundary: preserve rollback and never infer that an offline score proves the causal benefit of an intervention.
