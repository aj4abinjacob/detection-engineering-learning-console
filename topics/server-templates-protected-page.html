01 · Purpose

Presentation is not access control

A hidden link, client-side redirect, or template condition changes what a user sees. The protected route/service must still verify session and authorization before it loads or renders account data.

HTML

Server representation

Templates make document responses from safe context.

API

Program contract

Structured responses serve clients/integrations.

AUTHN

Who is it?

Resolve/validate session or credential.

AUTHZ

May it act?

02 · Protected route model

Request/cookiesession extraction/validation.
→
Principal + policyauthenticate then authorize account/page.
→
Template/APIrender minimal authorized context.

On failure choose response semantics deliberately: browser navigation may redirect to login; API callers usually need 401/403 structured error. Both paths enforce server-side policy first.

03 · Server-rendered HTML versus API

A template response includes HTML/layout and often navigation/session UX. An API response returns data for a client to render. They may reuse service/domain functions but should not assume identical error formats, caching, CSRF, or content-security requirements. Do not use HTML hiding as protection for an API endpoint.

04 · Template boundary

# FastAPI/Starlette template API is version-sensitive: follow installed docs.
# Pass a minimal, authorized context; do not pass DB/session objects or secrets.
return templates.TemplateResponse(request, "account.html",
    {"account": {"email": account.email, "display_name": account.display_name}})

Use: render a reviewed template with explicit safe context. Risk: template engine/API signature varies by FastAPI/Starlette version; pin/test your dependency. Template autoescaping helps for HTML contexts but is not universal security for JavaScript/URL/CSS contexts—avoid constructing executable markup from user input.

05 · Authentication dependency

from fastapi import Depends, HTTPException
def current_principal(request):
    # resolve opaque session server-side; do not trust a bare client account ID
    principal = session_service.get(request.cookies.get("session"))
    if principal is None: raise HTTPException(status_code=401, detail="authentication required")
    return principal

Use: one tested dependency/service for server-side session validation. Risk: cookie absence, expiry, revocation, and malformed value are normal cases; do not log the raw value or convert them to a 500.

06 · Authorization gate

@app.get("/account/{account_id}")
def account_page(account_id: str, principal=Depends(current_principal)):
    if principal.account_id != account_id:
        raise HTTPException(status_code=403, detail="not permitted")
    return render_account(account_id)

Use: enforce identity/object/action policy before loading/rendering sensitive data. Risk: real policies may include tenant, role, delegation, and resource ownership; centralize them rather than scattering equality checks. Decide 403 versus 404 disclosure policy consistently.

07 · Redirect is navigation UX

For a browser page, missing authentication may return a 303/302-style redirect to login with a validated local return path. Do not redirect an API client that expects JSON, and never accept an arbitrary external return URL (open redirect). A redirect after failure does not itself authorize the original request; the next protected request must recheck server policy.

08 · Safe errors and CSRF context

Use controlled error pages/messages that reveal no session internals, account existence beyond policy, stack traces, or template paths. For state-changing browser forms, apply appropriate CSRF defenses; SameSite cookies and hidden UI are not complete protection. Escape context and set deployment-appropriate security headers/content policy after testing.

09 · Protected-page event

{"request_id":"lab-r22","route":"/account/{account_id}","principal":"acct-pseudo",
 "authorization":"denied","status":403,"reason":"ownership"}

Log route template, safe pseudonymous subject/resource classes, authn/authz outcome, and request ID. Do not log session cookies, full account data, raw return URLs, or error stack traces to broad logs.

10 · Safety

Client-side controls are not gatesNever rely on hidden navigation, JavaScript checks, template branches, or a redirect to protect account data. Test direct requests to the protected route with missing, invalid, and other-user sessions in your local app only.

11 · Detection scenarios

IDOR

Account URL changes to another ID

Route parameter parsing succeeds; server object authorization must deny/handle concealment before querying/rendering data.

SESSION

Expired session loads template

Authentication dependency must fail before context construction; redirect/401 choice is representation-specific UX.

XSS

Display name is attacker-controlled

Use template escaping/context-safe output and validate display policy; do not mark untrusted values safe.

OPS

403 surge on account page

Aggregate safe policy reason, tenant/principal pseudonym, route, and release changes; distinguish user confusion from broken authorization deployment.
