SQL depth I · safe boundaries

Send values as data, never as executable SQL text.

SQL injection happens when untrusted text changes a query’s grammar. Parameter binding separates the statement from values. Identifiers cannot usually be bound, so select them from a closed allowlist—not string interpolation.

01 · Purpose

Query construction is a security boundary

Analysts often filter by user-entered IP, route, time, account, or dashboard option. Those are values. If concatenated into SQL, punctuation can become syntax. Parameterization makes the database parse the statement first and bind the value separately.

BOUNDARY

Code versus data

Statement grammar is authored code; external values are bound data with type/escaping handled by the driver.

CORRECTNESS

Quotes stop being fragile

A valid value containing an apostrophe stays one value rather than breaking a query string.

LIMIT

Parameters are not identifiers

Table, column, ORDER BY direction, and operators need a closed application-controlled choice.

CONTAINMENT

Privileges still matter

Binding lowers injection risk; a narrow read-only account limits damage from other defects.

Do not “escape then concatenate” as a substitute. Escaping rules, encodings, and drivers differ; a correct parameter API is designed for this separation.

03 · What goes wrong

Interpolation changes the statement before the database sees it

# DO NOT RUN OR COPY INTO AN APPLICATION: unsafe teaching anti-pattern.
sql = "SELECT request_id FROM access_requests WHERE source_ip = '" + supplied_ip + "'"

# Same problem: f-strings, %, .format(), and manual quote escaping.
# The supplied text is now part of SQL grammar, not a separately bound value.

This is unsafe even if a sample input looks like an IP: client input can be malformed, logs can contain attacker-controlled values, and “internal” dashboard filters can become externally influenced. Do not test injection strings against a real service. Use code review and synthetic local tests that assert the API receives a statement and separate parameters.

04 · Values

Bind every external value

import sqlite3

def requests_for_ip(conn: sqlite3.Connection, source_ip: str):
    return conn.execute(
        "SELECT request_id, status FROM access_requests WHERE source_ip = ?",
        (source_ip,),  # one-element tuple: comma matters
    ).fetchall()

def insert_reject(
    conn: sqlite3.Connection, observed_at: str, reason: str, excerpt: str
) -> None:
    conn.execute(
        """INSERT INTO rejected_requests(observed_at, reason, raw_excerpt)
           VALUES (?, ?, ?)""",
        (observed_at, reason, excerpt),
    )
cursor.execute(sql, parameters)

Execute one parameterized statement.Use the driver’s binding API for all runtime values. It assumes the SQL template is trusted code and the connection has appropriate privileges.

executemany(sql, sequence)

Bind a controlled sequence of parameter rows.Use for local/batched ingest with transaction boundaries. It is not a license to send unbounded input or omit validation/error reporting.

? / %s

Use the placeholder style required by the driver.SQLite DB-API uses ? (or named forms); common PostgreSQL Python drivers use %s. Never use Python’s percent operator to substitute a PostgreSQL placeholder.

05 · PostgreSQL versus SQLite

Parameter syntax belongs to the driver, not SQL folklore

# SQLite stdlib (qmark style)
conn.execute("SELECT * FROM accounts WHERE handle = ?", (handle,))

# PostgreSQL psycopg-style example (driver API; %s is a placeholder)
cur.execute("SELECT * FROM accounts WHERE handle = %s", (handle,))

# Named SQLite style is also supported:
conn.execute("SELECT * FROM accounts WHERE handle = :handle", {"handle": handle})

Read the exact driver documentation for parameter style, array/list adaptation, transaction defaults, and server-side preparation. PostgreSQL’s SQL positional syntax ($1) is different from Python DB-API placeholder conventions. A parameter may represent a literal value, not a keyword, identifier, or arbitrary clause.

06 · Dynamic identifiers

Allowlist finite choices; never bind or concatenate names

ORDER_COLUMNS = {"time": "observed_at", "status": "status"}
ORDER_DIRECTIONS = {"asc": "ASC", "desc": "DESC"}

def safe_order(choice: str, direction: str) -> str:
    try:
        return f"{ORDER_COLUMNS[choice]} {ORDER_DIRECTIONS[direction]}"
    except KeyError as exc:
        raise ValueError("unsupported sort option") from exc

# Only allowlisted fragments enter template construction; values remain bound.
sql = f"SELECT request_id, status FROM access_requests ORDER BY {safe_order(sort, direction)} LIMIT ?"
rows = conn.execute(sql, (limit,)).fetchall()

The f-string is safe here only because both fragments come from closed maps owned in source code, not a “sanitized” user string. Some PostgreSQL drivers provide identifier-composition helpers; use them exactly as documented when identifiers are dynamic. Validate limit as a bounded integer too—binding prevents syntax injection, not resource exhaustion.

07 · Build optional filters safely

Accumulate trusted fragments and parallel values

clauses = ["observed_at >= ?", "observed_at < ?"]
params: list[object] = [start, end]
if status is not None:
    clauses.append("status = ?")
    params.append(status)
sql = "SELECT request_id FROM access_requests WHERE " + " AND ".join(clauses)
rows = conn.execute(sql, params).fetchall()

Each clause is a fixed source-code fragment; each external value is appended only to params. Validate semantic constraints before querying: interval order, maximum span, status range, allowed sort, tenant scope, and pagination limit. Prefer an explicit query object/repository boundary over letting presentation code assemble SQL throughout the project.

08 · Defense in depth

Binding is necessary, not sufficient

Use least-privilege accounts: read-only analysis connections should not own schemas or write alerts. Apply authorization/tenant predicates server-side, set query timeouts/row limits where supported, and audit access. Stored procedures are safe only when their internal SQL also handles dynamic values/identifiers safely. An ORM can parameterize values, but raw SQL, unsafe query APIs, and authorization mistakes remain possible.

09 · Safety & validation

Do not create a live injection lab

Use an in-memory or explicitly disposable SQLite database with synthetic rows. No production writes, remote testing, or destructive payloads are needed to prove the design: compare the unsafe code review shape with a bound-value implementation, then test a quote-containing benign synthetic value as data. DDL/DML mutate even in local experiments; wrap controlled setup in a transaction or discard the named temporary database afterward. Log query templates and safe metadata, never raw credentials or sensitive parameter values.

10 · On the job

Detection-engineering scenarios

DASHBOARD

Analyst filters by source IP

Bind the filter value and enforce a bounded time range/tenant predicate. Validate IP syntax for product correctness, but do not mistake validation alone for SQL injection protection.

EXPORT

User selects sort order and limit

Allowlist column/direction and bind the numeric limit after range validation. A parameter placeholder cannot safely stand for ORDER BY column.

INGEST

Rejected raw field contains punctuation

Store it using bound INSERT parameters, with retention/length/redaction controls. Treat logging and CSV export as separate escaping boundaries too.

REVIEW

ORM query uses a raw fragment

Review its value/identifier boundary rather than assuming the ORM makes it safe. Replace raw interpolation with ORM filters, driver parameters, or a closed identifier map.
