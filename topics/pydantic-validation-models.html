Practical field guide · AbuseGuard

Validate the boundary; never confuse it with authorization.

Pydantic v2 models turn untrusted input into typed, constrained application values and structured validation errors. They do not prove user permission or business validity.

01 · Purpose

Schema is an input contract

An API accepts arbitrary client bytes. A model defines expected fields, coercion/strictness, bounds, serialization, and a safe error surface.

INPUT

Reject malformed

Fail before business/persistence work.

OUTPUT

Limit disclosure

Response schema avoids accidental fields.

TELEMETRY

Count categories

Validation failure is an observable outcome.

AUTHZ

Separate question

Valid ID is not authorized ID.

02 · Boundary

Untrusted JSONbytes/fields from client.
→
Model validationtyped constrained value or error.
→
Service policyauthz/business/persistence decision.

Validation is necessary but does not enforce ownership, rate limits, password hashing, or cross-record constraints.

03 · Pydantic v2 idioms

from pydantic import BaseModel, ConfigDict, Field
class RegisterIn(BaseModel):
    model_config = ConfigDict(extra="forbid")
    email: str = Field(min_length=3, max_length=254)
    password: str = Field(min_length=12, max_length=256, repr=False)

payload = RegisterIn.model_validate({"email":"a@b.test","password":"long-enough-pass"})
safe = payload.model_dump(exclude={"password"})

Use: v2 model_validate/model_dump and ConfigDict. Risk: FastAPI/Pydantic versions must be compatible; v1 examples (parse_obj, nested Config) are not the preferred v2 idiom. Do not use a model dump as a safe log by default.

04 · Field policy

Choose types and constraints from real requirements: bounded strings, explicit enums, URL/IP parsers where appropriate, and validators for local format rules. Avoid silently coercing security-sensitive types when strict behavior is needed; validate normalization semantics and retain original evidence only under policy. Field validators should be deterministic, quick, and free of remote I/O.

05 · Extra fields

extra="forbid" rejects unknown input, useful for small security-sensitive contracts; ignore may support forward-compatible clients but can hide typos; allow retains extras and needs deliberate handling. Select per boundary and version the API—do not let extras flow into persistence/authorization accidentally.

06 · Response models

class AccountOut(BaseModel):
    id: str
    email: str
@app.post("/register", response_model=AccountOut, status_code=201)
def register(data: RegisterIn) -> AccountOut: ...

Use: separate input/output models. Risk: never reuse an input model containing password/session/internal flags as output; response filtering is a guard, not replacement for designing minimal domain data.

07 · Structured errors

FastAPI normally returns a structured 422 validation response for request validation. Treat its exact format as version/framework contract and avoid exposing stack traces, internal validator details, raw secret values, or schemas that reveal sensitive policy. Return stable user-facing codes/messages and record safe error categories/counts internally.

08 · Test invalid inputs

def test_extra_register_field_is_rejected(client):
    response = client.post("/register", json={"email":"a@b.test","password":"x"*12,"admin":True})
    assert response.status_code == 422

Test missing, wrong type, boundary length, forbidden extra, and a valid case. Use synthetic credentials only. Also test that a valid request is rejected by authorization/business policy where appropriate.

09 · Safety

Validation errors are input from an attackerBound body size at server/proxy, avoid echoing invalid values, and do not log passwords or full JSON. Schema validation does not prevent resource exhaustion from huge requests before parsing.

10 · Detection scenarios

API

Extra admin flag appears

Forbid/ignore it per contract; never let client extras become persisted privilege state.

ABUSE

Malformed registration burst

Aggregate safe error categories/route/client provenance and rate-limit at edge; error text is not attribution.

LEAK

Password appears in response/log

Separate response models and audit serialization/logging paths; repr=False alone is not a complete secret-control strategy.

AUTHZ

Valid product ID is cross-tenant

Model validation passes; service authorization must deny it.
