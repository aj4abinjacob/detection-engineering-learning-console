Detection stack · decisions

Evaluate vendor defenses by documented behavior and outcomes.

Cloudflare, Akamai, DataDome, PerimeterX/HUMAN, and Kasada offerings are not interchangeable black boxes. Public documentation can establish selected integration and response facts; a tenant’s score, rules, thresholds, signals, and enforcement order remain configuration-, plan-, and contract-dependent unless the owner documents them.

Why this matters

At work, a vendor decision appears as a response, event, cookie/token, dashboard entry, or origin-side outcome. Detection engineering needs to connect that evidence to an approved policy and business impact—not infer the vendor’s secret model from a page response. This supports incident triage, rollout safety, support, and interviews about defense in depth.

Publicly documented vendor map

The following is a starting map, not a fingerprinting recipe. Recheck documentation and the customer’s entitlement before a production statement.

CLOUDFLARE · PUBLIC DOCS

Bot Management exposes a bot score to configured rules; Cloudflare documents custom rules, challenge actions, and JavaScript Detections as separate features. Availability and enforcement are plan/feature/configuration dependent.

AKAMAI · PRODUCT/CONTRACT

Akamai markets Bot Manager as bot management. Treat the enabled signals, actions, paths, and exceptions as tenant facts available only through authorized configuration, event, and support documentation.

DATADOME · PUBLIC DOCS

DataDome documents Device Check as a client-side verification that may be used before a block or CAPTCHA in specified contexts. That does not establish how any site configures it.

PERIMETERX / HUMAN / KASADA

HUMAN documents Sensor, Detector, and Enforcer roles and policy-driven allow/block behavior. “PerimeterX” may be a legacy product reference; map names through your authorized inventory. For Kasada, use only vendor/tenant documentation you are authorized to see; do not infer internals from public-facing behavior.

Risk, challenge, and response behavior

A risk score is a vendor- and policy-specific input, not a portable probability or universal scale. A challenge is a response designed to gather evidence or gate a request; it can be invisible/non-interactive, managed, interactive, embedded, or application-specific depending on the provider and configuration. A block, retry, redirect, cookie, header, or page is observable behavior—not proof of the exact product, rule, or signal that led to it.

Legitimate traffic mattersBrowser extensions, disabled JavaScript, mobile SDKs, APIs, accessibility tools, privacy software, shared NATs, and partner integrations can legitimately take a different path. Protect API and mobile routes with explicit design rather than applying a browser challenge assumption to them.

Plan and configuration determine the system you have

Before changing a control, record product/feature entitlement; deployment location; protected host/routes; browser/API/mobile split; rule order; exceptions for verified partners and internal monitors; observe versus enforce mode; response type; owner; rollback; and measurements. Cloudflare’s own documentation distinguishes Bot Fight Mode, Super Bot Fight Mode, and Enterprise Bot Management, while some actions and fields depend on product phase and plan. Similar names at other vendors do not imply equivalent behavior.

Scope and safety

Never profile, challenge, scrape, probe, or compare another organization’s protected site. Do not collect challenge tokens, cookies, fingerprints, or response sequences from third parties. Use learner-owned AbuseGuard, a vendor-provided sandbox, or supplied sanitized artifacts only. Do not bypass, replay, tamper with, or advise on evading a control. Keep screenshots, HAR files, and logs redacted: they can contain session identifiers, account data, and policy clues.

Outcome-based defensive workflow

  1. State scope and ownership. Identify the owned test host or supplied artifact and the approval/change record.
  2. Capture allowed evidence. Save timestamp, route class, response class, authorized vendor event category, and application outcome—without tokens or personal data.
  3. Compare a baseline. Use normal, accessibility/privacy, mobile/API, and approved synthetic-monitoring paths where relevant.
  4. Tune safely. Start in observe mode, corroborate with server evidence, provide an accessible fallback, measure impact, and retain a rollback.

Detection-engineering scenarios

1. New vendor integration affects checkout conversion

Trigger: a rollout coincides with more checkout failures. Artifact: authorized aggregate vendor action category, HTTP response class, route, and conversion dashboard. Observation point: owned edge/application telemetry. Reasoning: compare observe-mode and enforced cohorts, then isolate route and client class before changing policy. False-positive boundary: a failure page is not proof that the vendor caused the drop; application releases, payment changes, and network events are alternatives.

2. Partner API receives a browser-oriented challenge

Trigger: a documented partner integration begins failing. Artifact: contract route identity, request class, authorized edge event, and API error rate. Observation point: owned API gateway and vendor console. Reasoning: confirm route classification and configured exception with the policy owner; use API-appropriate authentication/rate controls. False-positive boundary: do not broadly allow an ASN or user agent just because an API failed.

3. Fraud team asks for the “vendor score” as a block rule

Trigger: an analyst proposes a single threshold. Artifact: approved score semantics, historical outcomes, route, and policy version. Observation point: authorized tenant analytics. Reasoning: test score bands with corroborating behavior and a managed/step-up response before enforcement. False-positive boundary: score scales and thresholds are not comparable across vendors, plans, or routes.

4. Response looks like a well-known provider

Trigger: an incident ticket contains a screenshot and names a vendor. Artifact: redacted response class plus the deployment inventory. Observation point: owned environment or supplied artifact. Reasoning: verify through configuration/change records and authorized events; report only what those sources establish. False-positive boundary: a script path, status code, or challenge visual is not reliable vendor attribution or evidence of a specific detection method.

Artifact-producing drills

1. Fact / inference ledger

Save artifacts/vendors/fact-ledger.md. For Cloudflare, Akamai, DataDome, PerimeterX/HUMAN, and Kasada, record one public fact with its URL, one authorized local fact if available, and at least two unknowns.

  • Do not infer private signals, rules, or thresholds.
  • Mark vendor/product naming uncertainty rather than guessing.

2. Owned AbuseGuard response matrix

Using only a learner-owned local/staging AbuseGuard control or supplied fixture, save artifacts/vendors/response-matrix.csv with route class, approved test persona, response class, server outcome, and policy version.

  • Redact tokens, cookies, hostnames, and account identifiers.
  • Include API/mobile/accessibility-compatible paths where your app supports them.

3. Safe rollout plan

Save artifacts/vendors/rollout-plan.md for a hypothetical signup control: observe stage, metrics, accessible fallback, partner/API exception design, escalation owner, and rollback trigger.

  • Explain why a challenge is not the same as a block.
  • Require no AI-assisted explanation when presenting the plan.
