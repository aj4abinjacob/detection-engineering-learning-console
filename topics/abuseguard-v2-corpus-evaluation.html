Purpose

Why this matters in detection engineering

A corpus is a versioned set of events, feature definitions, labels, provenance, and split assignments—not merely a CSV. Honest evaluation must reproduce the data from documented owned inputs and preserve representative failures and label maturity.

A detection engineer must be able to trace how an observation becomes a feature, how that feature supports an inference, and how policy turns the inference into an action. The useful unit for this topic is a sanitized corpus release with manifest, schema, generator versions, label provenance, split hashes, data card, and held-out report. Preserve enough lineage to reproduce it without collecting content that the decision does not require.

Boundaries

What can go wrong

Closest legitimate lookalike: a tiny controlled corpus can be useful for correctness while remaining unrepresentative of real user diversity and production base rates.

Pipeline or interpretation failure: manual edits, hidden exclusions, request-time label leakage, duplicate sessions, and test-set iteration create an impressive but invalid score.

Safety boundary: work only with supplied sanitized fixtures or systems and accounts you own and are authorized to test. Minimize identifiers, exclude secrets and content, bound retention and access, and provide an accessible path when an automated action could affect a person.

Do not overclaimThis guide establishes a method for controlled defensive evidence. It does not prove identity, intent, causality, universal tool behavior, or how a third-party system will classify traffic.

Method

A repeatable defensive workflow

  1. Declare the question and scope. Name the owned route, entity, time range, authorization, expected population, and prohibited data before collection.
  2. Version the evidence. Save a sanitized corpus release with manifest, schema, generator versions, label provenance, split hashes, data card, and held-out report, its schema or tool version, observation point, event and availability times, and missing-value behavior.
  3. Build a negative control. Include a tiny controlled corpus can be useful for correctness while remaining unrepresentative of real user diversity and production base rates and state the response it should receive.
  4. Replay and decide. Recompute from immutable input, compare expected output, inspect false positives and false negatives, then apply rebuild from a clean checkout, publish exact limitations, freeze held-out data, and keep failure cases visible.

Detection-engineering scenarios

BASELINE

1. The observed distribution changes

Trigger: a monitor for Sanitized labeled corpus (your app only) shifts outside its recorded baseline. Artifact: a sanitized corpus release with manifest, schema, generator versions, label provenance, split hashes, data card, and held-out report. Reasoning: compare time, producer, release, population, and data quality before attributing the shift to abuse. Boundary: a changed distribution is an observed fact, not a malicious label.

LOOKALIKE

2. A legitimate journey matches the candidate

Trigger: the candidate logic fires on a tiny controlled corpus can be useful for correctness while remaining unrepresentative of real user diversity and production base rates. Artifact: a labeled negative-control replay. Reasoning: preserve the case, inspect which feature dominated, and choose a proportionate fallback. Boundary: do not tune the case away without measuring what new false negatives the change creates.

QUALITY

3. The pipeline changes while the rule stays green

Trigger: manual edits, hidden exclusions, request-time label leakage, duplicate sessions, and test-set iteration create an impressive but invalid score. Artifact: contract-test result, schema versions, and quality counters. Reasoning: quarantine or mark degraded evidence and restore the producer contract before judging detection quality. Boundary: absence, default values, and parser failures are not benign observations.

POLICY

4. Evidence is strong enough to review, not to punish

Trigger: several versioned signals agree on an unusual owned-lab journey. Artifact: feature lineage, reason codes, policy version, and expected guardrails. Reasoning: rebuild from a clean checkout, publish exact limitations, freeze held-out data, and keep failure cases visible. Boundary: preserve rollback and never infer that an offline score proves the causal benefit of an intervention.
