Purpose

Why this matters in detection engineering

A portfolio index is a traceability matrix from a real target-role requirement to a verifiable artifact, exact evidence location, personal contribution, result, limitations, and reproducibility status. It prevents vague claims and exposes gaps before an interview does.

A detection engineer must be able to trace how an observation becomes a feature, how that feature supports an inference, and how policy turns the inference into an action. The useful unit for this topic is a role-by-role requirement matrix with source/date, artifact URL or path, commit/release, claim, contribution, evidence, limitation, and next gap. Preserve enough lineage to reproduce it without collecting content that the decision does not require.

Boundaries

What can go wrong

Closest legitimate lookalike: a role may value judgment, communication, or operations more than another technically complex artifact.

Pipeline or interpretation failure: copying generic job requirements, linking only a homepage, hiding team contribution, stale private links, and unsupported metrics make claims unverifiable.

Safety boundary: work only with supplied sanitized fixtures or systems and accounts you own and are authorized to test. Minimize identifiers, exclude secrets and content, bound retention and access, and provide an accessible path when an automated action could affect a person.

Do not overclaimThis guide establishes a method for controlled defensive evidence. It does not prove identity, intent, causality, universal tool behavior, or how a third-party system will classify traffic.

Method

A repeatable defensive workflow

  1. Declare the question and scope. Name the owned route, entity, time range, authorization, expected population, and prohibited data before collection.
  2. Version the evidence. Save a role-by-role requirement matrix with source/date, artifact URL or path, commit/release, claim, contribution, evidence, limitation, and next gap, its schema or tool version, observation point, event and availability times, and missing-value behavior.
  3. Build a negative control. Include a role may value judgment, communication, or operations more than another technically complex artifact and state the response it should receive.
  4. Replay and decide. Recompute from immutable input, compare expected output, inspect false positives and false negatives, then apply use current role evidence, map only truthful work, prioritize the smallest artifact that proves each requirement, and keep a private-safe version for sensitive experience.

Practice

Detection-engineering scenarios

BASELINE

1. The observed distribution changes

Trigger: a monitor for Requirement → artifact mapping for each target role shifts outside its recorded baseline. Artifact: a role-by-role requirement matrix with source/date, artifact URL or path, commit/release, claim, contribution, evidence, limitation, and next gap. Reasoning: compare time, producer, release, population, and data quality before attributing the shift to abuse. Boundary: a changed distribution is an observed fact, not a malicious label.

LOOKALIKE

2. A legitimate journey matches the candidate

Trigger: the candidate logic fires on a role may value judgment, communication, or operations more than another technically complex artifact. Artifact: a labeled negative-control replay. Reasoning: preserve the case, inspect which feature dominated, and choose a proportionate fallback. Boundary: do not tune the case away without measuring what new false negatives the change creates.

QUALITY

3. The pipeline changes while the rule stays green

Trigger: copying generic job requirements, linking only a homepage, hiding team contribution, stale private links, and unsupported metrics make claims unverifiable. Artifact: contract-test result, schema versions, and quality counters. Reasoning: quarantine or mark degraded evidence and restore the producer contract before judging detection quality. Boundary: absence, default values, and parser failures are not benign observations.

POLICY

4. Evidence is strong enough to review, not to punish

Trigger: several versioned signals agree on an unusual owned-lab journey. Artifact: feature lineage, reason codes, policy version, and expected guardrails. Reasoning: use current role evidence, map only truthful work, prioritize the smallest artifact that proves each requirement, and keep a private-safe version for sensitive experience. Boundary: preserve rollback and never infer that an offline score proves the causal benefit of an intervention.
