Make proxy and database boundaries explicitly trustworthy.

Docker, Nginx, TLS termination, forwarded headers, and database migration change what an app sees. Trust only explicit proxy hops or every IP-based detection can become false.

Why it matters

Production is a trust boundary: browser, DNS, TCP, TLS, proxy, app, and DB each transform evidence. A header is untrusted until a known proxy strips/sets it.

Request path

client -> DNS -> TCP/TLS -> Nginx -> Docker bridge -> app -> PostgreSQL

Draw the actual deployment path, including termination and observability points. Local Compose topology is not Internet topology.

Docker/Compose boundary

Use a minimal pinned base image, non-root process where practical, explicit ports/networks/volumes, and environment-injected secrets. Build from clean checkout and avoid mounting broad host paths or baking secrets into image layers.

Nginx reverse proxy

Nginx can terminate TLS, route upstream, set security headers, and mediate request limits. Proxy configuration must define timeouts, upstreams, headers, and logs deliberately; it is not an authorization substitute.

TLS termination

After termination, proxy-to-app traffic has its own network/trust boundary. Use protected internal network or re-encryption as deployment policy requires. App should know whether proxy headers are trustworthy before constructing redirects/logging scheme/client details.

Forwarded headers

X-Forwarded-For is a chain; X-Real-IP is commonly a single header. Client-supplied values are spoofable unless the immediately trusted proxy strips incoming copies and sets authoritative values. Docker bridge source is often proxy/container address, not original client.

Explicit trusted hops

# Use these only when another owned proxy/LB actually precedes Nginx.
# Substitute the exact private ingress subnet you operate.
set_real_ip_from 172.20.0.0/24;
real_ip_header X-Forwarded-For;
real_ip_recursive on;

location / {
    # Discard the incoming chain after real-IP normalization. The app receives
    # one authoritative address from this owned hop, not client-supplied XFF.
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Real-IP       $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_pass http://app:8000;
}

If Nginx is the first owned public edge, omit the real-IP directives and overwrite forwarding headers from its socket peer; never preserve an arbitrary client XFF with $proxy_add_x_forwarded_for. If an owned load balancer precedes Nginx, trust only its enumerated subnet and verify its strip/append behavior; real_ip_recursive walks the chain relative to those trusted hops. The app should accept forwarded metadata only from Nginx, and direct app access must be blocked. Test a direct spoofed XFF, a request through every owned hop, multiple values, and an untrusted peer before using client IP as a signal.

SQLite to PostgreSQL intentionally

SQLite is suitable for local development; PostgreSQL changes types, concurrency, migrations, credentials, backups, and operational ownership. Version schema migrations, test data migration, use least privilege, and plan rollback/backup rather than copying a file into production.

Safety

Use local Compose and synthetic data only. Do not expose ports publicly, deploy external services, or put certificates/keys/secrets in artifacts. Docker/Nginx syntax/version differs; validate config in disposable local environment and inspect logs for redaction.

Defensive scenarios

All users share one IP

App trusts Docker/Nginx peer address instead of explicit forwarded chain.

Spoofed forwarded header

Client header reached app because proxy did not strip/set trusted values.

HTTPS redirect loop

App/proxy disagree about scheme due to untrusted/missing proxy metadata.

SQLite migration surprise

Postgres type/constraint/concurrency behavior requires tested migration plan.
