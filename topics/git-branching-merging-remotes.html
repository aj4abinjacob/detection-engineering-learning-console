Practical field guide · Git collaboration

Make parallel work converge safely.

Branches are movable names for commits; remotes are other repositories. Read the graph and the references before integrating a rule change, and a merge, rebase, or push becomes an explicit engineering choice rather than a ritual.

01 · Purpose

Why collaboration mechanics matter in detection engineering

A change to a parser, enrichment source, or detection threshold is production behavior. Git’s graph records how independently tested changes meet, while remote references let a team exchange work without guessing whose copy is current.

REVIEW

Keep intent visible

A focused branch and small commits make a threshold change reviewable alongside its positive and negative fixtures.

REPRODUCIBILITY

Pin an exact graph point

An incident note can name the commit that shipped a rule bundle, even after later work lands.

CONCURRENCY

Expose collisions early

Git detects incompatible edits instead of silently picking a value for a critical correlation window.

SAFETY

Protect shared history

Remote tracking and leases reveal divergence before a push overwrites another engineer’s reachable commits.

ScopeThis guide assumes you already understand working tree → index → commit → branch → HEAD from Topic 1.6. A branch is not a copy of files; it is a local ref that names one commit. A remote-tracking ref such as origin/main is your local record of a remote branch after the last fetch.

02 · Mental model

Integrate commit graphs, not folders

Every commit names parent commit(s). To integrate a branch, Git compares the current tip, the incoming tip, and—when they diverged—their best common ancestor (merge base).

Fast-forward: Three-way merge: A──B──C main A──B──C──M main ╲ ╲ ╱ D──E feature D──E feature main can move C → E. merge base B + both tips C/E → M
Local branchmain is a movable ref at a local commit.refs/heads/main
↔
Remote-tracking reforigin/main is updated by fetch; it is not the remote itself.refs/remotes/origin/main
↔
Remote branchThe server’s branch changes only when a permitted push succeeds.origin

Fetch moves your remote-tracking knowledge. Merge or rebase changes local history or files. Push asks the remote to advance one of its refs. They are separate operations.

# Orient before any integration or publication.
git status
git log --oneline --graph --decorate --all -12
git branch -vv
git remote -v
git merge-base main feature/login-rule

git merge-base prints the common ancestor Git would use for a three-way merge. It assumes both revisions name commits available locally. It changes nothing and is useful when the graph is surprising.

03 · Integration

Fast-forward versus a true three-way merge

Graph conditionWhat git merge feature doesConsequence
Current tip is an ancestor of featureFast-forward: move the current branch pointer to feature’s tip.No merge commit; graph remains linear. It does not combine competing changes because none exist on the current line.
Both branches have commits after their merge baseThree-way merge: compute a result from base + current tip + incoming tip, then create a commit with two parents.The merge commit records that the histories joined and may need a human conflict decision.
Current tip already contains featureUsually “Already up to date.”No new commit or file change.
 
# From the branch that should receive the work.
git switch main                 # Git 2.23+; legacy: git checkout main
git merge --ff-only feature/login-rule

# If a merge commit is intentional even when a fast-forward is possible:
git merge --no-ff feature/login-rule

# Normal merge permits a fast-forward or a three-way merge as the graph requires.
git merge feature/login-rule
git merge --ff-only <branch>

Integrate only without a merge commit.Use when a linear policy is required. It assumes the receiving branch has no unique commits; it fails safely if histories diverged and never manufactures a merge.

git merge --no-ff <branch>

Record an integration event.Use when a team wants the feature branch visible as a merge commit. It changes local history and working files; resolve/test any conflict before completion.

git merge --abort

Stop an in-progress conflicted merge.Use only while git status says a merge is in progress. It tries to restore the pre-merge state, but pre-existing uncommitted edits can prevent a perfect restoration—inspect first.

Do not confuse the two--no-ff forces a merge commit even when Git could simply move a pointer. A true three-way merge is required only when both lines have diverged. Whether a merge commit is “better” is a team history policy, not a correctness rule.

04 · Human decision point

Resolve conflicts by deciding the final artifact

Git can combine non-overlapping changes. When two changes affect the same hunk, it cannot know whether a login rule needs a 5-minute or 15-minute window. It stops and records both candidates in the working tree.

<<<<<<< HEAD
window_minutes: 5       # current branch (“ours” during merge)
=======
window_minutes: 15      # incoming branch (“theirs” during merge)
>>>>>>> feature/geo-tuning

In this merge context, the first label (HEAD) is the branch you had checked out; the second is the branch supplied to git merge. During a rebase, “ours” and “theirs” are easy to misread because Git is replaying your commit onto a new base. Read the labels and actual content, not the nickname.

  1. Read the operation and every path. Run git status; do not edit only the first file it prints.
  2. Find the intent behind both sides. Inspect the commits with git log --oneline --left-right HEAD...feature and the surrounding tests or rule fixtures.
  3. Write one valid final file. Remove all <<<<<<<, =======, and >>>>>>> lines. Never leave markers in a parser, configuration, or rule.
  4. Validate the semantic decision. Run the project’s lint/test/replay commands, then use git diff --check to catch whitespace errors.
  5. Stage and finish the stated operation. git add <path> declares resolution. Finish a merge with git commit; finish a rebase with git rebase --continue.
git status
git diff --name-only --diff-filter=U     # unmerged paths only
# edit and test the final content
git add rules/impossible_travel.yml
git diff --staged
git commit                              # completes a merge
# Or, if status says rebase in progress: git rebase --continue
Conflict-marker safetyConflict markers are valid text, so a YAML, JSON, or source parser may report a later, misleading error—or an unvalidated artifact may be deployed. Treat marker removal as necessary but not sufficient: verify the resulting behavior.

05 · Exchange

Fetch, pull, and push are distinct moves

ActionWhat changesWhen to use / assumptions
git fetch originDownloads objects and updates remote-tracking refs such as origin/main; does not alter your current branch, index, or working tree.Use first to see remote state. Assumes network access and credentials authorized for read.
git pull --ff-onlyFetches then fast-forwards the current local branch only if possible.Use on a clean local main when you want an update without an automatic merge. Fails when local commits diverged.
git pull --rebaseFetches then rebases local, unpushed commits onto the fetched upstream.Use only when rewriting your own local commits is acceptable; conflict resolution may be required.
git push origin branchOffers local commits and asks remote branch to advance.Use after review/test policy is satisfied. A normal push rejects non-fast-forward updates instead of overwriting remote work.
 
# A deliberate update-and-publish loop.
git fetch origin
git log --oneline --left-right --graph main...origin/main
git switch main
git pull --ff-only
git switch -c fix/parser-null-user
# edit, test, git add, git commit
git push -u origin fix/parser-null-user

git pull is shorthand for fetch plus an integration strategy. Its behavior depends on configuration and supplied flags; do not use it as a synonym for “download.” git fetch is the inspection-friendly primitive. A successful push affects a remote system and may trigger CI, review automation, or deployment; inspect the target branch before pressing Enter.

06 · Relationships

Upstream is a default pairing, not a privilege boundary

A local branch can track one remote branch. Git uses that relationship to define the default for status ahead/behind, git pull, and a plain git push. The server still enforces its own permissions and branch protection.

git branch -vv                         # local branch + configured upstream
git rev-parse --abbrev-ref --symbolic-full-name @{upstream}
git status -sb                         # shows ahead/behind after fetch
git push -u origin fix/parser-null-user # create remote branch and set upstream
git branch --set-upstream-to=origin/main main
git push -u origin <branch>

Publish and establish tracking.Use for a newly created feature branch. It assumes the remote name and target branch are correct; subsequent plain push/pull may use this pairing, so verify it with git branch -vv.

git branch --set-upstream-to=origin/main main

Set a local branch’s default remote partner.Use to repair or establish an existing relationship. It changes local configuration, not remote refs or files; it does not prove your branch is up to date.

git log main..origin/main

See commits remote has that local main lacks.Use after fetch. Reverse the order (origin/main..main) to see local-only commits before deciding how to integrate.

07 · History shape

Rebase copies commits onto a new base; merge joins existing histories

Before: After git rebase main: A──B──C main A──B──C──F main ╲ ╲ D──E feature D'──E' feature D' and E' have new parents and IDs; D/E are not moved.
ChoiceMechanismBest fit / consequence
git merge main while on featureCreates a merge commit if histories diverged; original commits keep their IDs.Safe for already-shared history and preserves the actual integration event. Graph may be non-linear.
git rebase main while on featureTemporarily removes feature-only commits then replays equivalent patches onto main, creating new commits.Good for your unshared branch before review. Rewrites commit IDs; a previously pushed branch needs a guarded force push.
 
# On your own feature branch; first update your view of main.
git fetch origin
git switch fix/parser-null-user
git rebase origin/main

# If a conflict occurs: resolve, test, then continue or abort.
git add <resolved-path>
git rebase --continue
# git rebase --abort       # return to the pre-rebase branch when possible

# Only after confirming remote branch ownership and reviewing the graph:
git push --force-with-lease origin fix/parser-null-user
Rewrite boundaryNever casually rebase or force-push a branch that others may have based work on. --force-with-lease refuses to overwrite the remote ref if it changed from the value your local repository last observed; fetch first, but understand that a lease reduces—not eliminates—coordination risk. Do not use bare --force for collaborative work.

08 · Field decisions

Four collaboration scenarios

RULE TUNING

Two analysts change the same correlation window

Fetch and compare the graph before integration. A conflict is evidence of a policy decision, not a syntax chore: examine both experiment reports, choose a final threshold, replay fixtures, then make the merge commit. The final commit should explain the evidence behind the number.

INCIDENT FIX

Production needs an auditable hotfix

Branch from the deployed baseline, commit the narrow correction plus regression test, and push a named branch for review. Merge keeps the approval and integration point visible; avoid rebasing the shared release branch during an incident unless the established release process directs it.

STALE BRANCH

Your local branch is behind the repository

Run git fetch, inspect origin/main, then rebase only your unshared feature commits onto it. Resolve and test conflicts locally. If you previously published that branch, coordinate with consumers and use --force-with-lease after review—not a blind force push.

COLLECTOR CHANGE

A parser change and schema update must land together

Use one branch and coherent commits that pair the parser with schema fixtures and downstream expectations. A fast-forward does not reduce review quality; a true merge signals independent lines joined. In either case, CI must validate the final integrated snapshot, not just each branch in isolation.

09 · Boundaries

Safety, failure modes, and platform notes

CLEAN TREE

Do not switch through unknown edits

Branch switches, merges, and rebases rewrite tracked files. Commit or intentionally stash relevant work first; Git may refuse a risky switch, but that is not a backup plan.

REMOTE ≠ BACKUP

Fetch before assuming

origin/main may be stale until fetch. A clone may also omit inaccessible refs, and local work is not shared until push succeeds.

SECRETS

History replicates data

Never put raw customer logs, tokens, or credentials in a branch “temporarily.” A pushed commit can be copied, cached, or reviewed even if later rewritten.

POLICY

Server rules win

Protected branches, signed-commit rules, required reviews, and CI can reject a push. That is a collaboration control, not a Git error to work around.

Version and shell differencesgit switch was introduced in Git 2.23 (2019); use git checkout <branch> on older installations, with extra care because legacy checkout also restores paths. git init -b main needs Git 2.28+; older Git requires git init then git branch -M main before the first push. The commands shown use POSIX shell syntax. In PowerShell, use Set-Content rule.yml 'value' rather than printf ... > rule.yml, and use cd C:\Temp\detection-git-branching-1-7 for the drill path.

10 · Practice

Hands-on drills: make the graph observable

Run these in the exact disposable path /tmp/detection-git-branching-1-7 on macOS/Linux, or C:\Temp\detection-git-branching-1-7 in Windows PowerShell. Do not run setup commands inside a repository containing real work. Save each graph or status output as your artifact.

1. Prove fast-forward and true merge mechanics

20 min
mkdir /tmp/detection-git-branching-1-7
cd /tmp/detection-git-branching-1-7
git init -b main
git config user.name "Drill User"
git config user.email "drill@example.invalid"
printf 'version: 1\n' > rule.yml
git add rule.yml && git commit -m "Baseline"
git switch -c feature
printf 'feature: true\n' > feature.yml
git add feature.yml && git commit -m "Add feature"
git switch main && git merge --ff-only feature
git switch -c divergent
printf 'owner: detections\n' > ownership.yml
git add ownership.yml && git commit -m "Add owner"
git switch main
printf 'version: 2\n' > rule.yml
git commit -am "Advance main"
git merge divergent
git log --oneline --graph --decorate --all | tee graph.txt
  • Mark the pointer-only fast-forward in graph.txt and explain why it created no merge commit.
  • Identify the merge base and both parents of the later merge commit with git show --no-patch --pretty=raw HEAD.
  • Explain why the same command, git merge, produced different graph operations.

2. Manufacture, resolve, and abort a conflict

20 min
git switch -c short-window
printf 'window_minutes: 5\n' > rule.yml
git commit -am "Use short window"
git switch main
printf 'window_minutes: 15\n' > rule.yml
git commit -am "Use longer window"
git merge short-window
# Inspect markers and status. First, prove abort works:
git merge --abort
git merge short-window
# Choose a justified final value, remove markers, then:
git add rule.yml && git commit -m "Resolve window policy"
git status | tee conflict-resolution-status.txt
  • Label which marker region came from HEAD and which came from short-window.
  • Explain why git add is a resolution declaration rather than merely a file upload.
  • Show that abort restored the pre-merge tip, then show the completed merge has two parents.

3. Simulate a remote and compare rebase with merge

25 min
git init --bare /tmp/detection-git-branching-1-7-remote.git
git remote add origin /tmp/detection-git-branching-1-7-remote.git
git push -u origin main
git switch -c rebase-demo
printf 'test: added\n' > fixture.yml
git add fixture.yml && git commit -m "Add fixture"
git switch main
printf 'baseline: updated\n' > baseline.yml
git add baseline.yml && git commit -m "Update baseline"

git log --oneline --graph --decorate --all | tee rebase-graph.txt

  • Find the pre-rebase and post-rebase commit IDs in the reflog; explain why the replayed commit has a new ID.
  • Show git branch -vv and explain what -u configured. State why an already-pushed rewrite would need --force-with-lease.
