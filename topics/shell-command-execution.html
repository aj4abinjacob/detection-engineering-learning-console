Practical field guide · Shell

Know what runs before you run it.

A shell turns text into processes. Understanding parsing, expansion, command lookup, and exit status lets you automate investigations without silently running the wrong program or corrupting evidence.

01 · Purpose

Why the shell matters in detection work

Detection work constantly crosses the boundary between files, processes, APIs, and small programs. The shell is the control plane connecting them.

01 · TRIAGE

Interrogate a host quickly

Find a process, inspect a log, hash an artifact, or summarize a capture without first writing an application.

02 · AUTOMATION

Turn a sequence into a repeatable tool

A careful script preserves exact commands, inputs, outputs, and failure behavior for later review.

03 · SAFETY

See how text becomes arguments

Quoting and expansion determine whether a filename stays one argument or becomes many—and whether data becomes executable syntax.

04 · DEBUGGING

Explain environment differences

PATH, aliases, startup files, and exported variables explain why a command works interactively but fails in cron, CI, or production.

The useful definitionA terminal is the window and input/output device. A shell—such as Bash or Zsh—is the program reading command text, expanding it, locating commands, starting processes, and reporting their exit status.

02 · Mental model

From command line to running process

The shell does significant work before the target program receives anything. The target receives an argument array, not your original command-line string.

ParseRecognize words, quotes, operators, redirections, and pipelines.printf '%s\n' "$x"
→
ExpandResolve variables, command substitutions, globs, and word splitting in shell-defined order."$HOME"/*.log
→
ExecuteRun a builtin or locate an executable, pass arguments and environment, then collect status.execve(...)

This is why echo "$pattern" and echo $pattern can behave differently: quote removal and word splitting occur before echo starts.

Shell syntax versus program arguments

TextHandled byEffect
| > && ;ShellConnect, redirect, conditionally run, or separate commands.
*.jsonShellUsually expands to matching pathnames before the program starts.
--format jsonTarget programTwo arguments interpreted according to that program's CLI.
KEY=value cmdShellAdds an environment variable for that command invocation.
 
# Reveal the exact argument boundaries a program receives
python3 -c 'import sys; print(sys.argv)' one "two words" '*.log'
Shell is not PythonEach tool has its own parser. Shell quoting ends before Python, awk, sed, jq, SQL, or a regular-expression engine interprets its arguments. Debug one parser boundary at a time.

03 · Command resolution

How the shell finds a command

A bare command name may resolve to an alias, function, builtin, hashed location, or executable in PATH. Do not assume python means the interpreter you intended.

type -a python3

Show every resolution candidate.Unlike which, shell type can report aliases, functions, and builtins as well as files.

command -v python3

Get the command the shell would use.Suitable for portable existence checks in scripts.

which python3

Common executable lookup.Useful interactively, but behavior varies and it may not explain aliases or functions.

printf '%s\n' "$PATH"

Inspect lookup order.PATH is a colon-separated list searched left to right.

env

List exported environment.Environment variables are inherited by child processes; ordinary shell variables are not unless exported.

hash -r

Forget cached executable locations.Useful after installing or moving a program when the shell remembers an old path.

# Trace the selected Python from command name to file
type -a python3
command -v python3
ls -l "$(command -v python3)"
python3 -c 'import sys; print(sys.executable)'
PATH is a trust boundaryPutting a writable or current directory early in PATH can cause an attacker-controlled executable to run instead of the expected system tool. Privileged scripts should use a controlled PATH and explicit command paths where appropriate.

04 · Data stays data

Quoting, expansion, and globbing

FormMeaningExample
Single quotesEverything inside is literal; a single quote cannot appear directly.'*.log $HOME'
Double quotesPreserve one argument while allowing variable and command substitution."$report_dir/run 1.json"
Unquoted variableExpansion is shell- and option-dependent. Bash normally splits and then globs; Zsh normally does not split scalar values by default. Usually wrong for path/data variables.$files
Command substitutionReplaces syntax with captured stdout; trailing newlines are removed."$(date +%F)"
GlobShell pathname matching, not a regular expression.logs/*.json
Brace expansionGenerate literal alternatives or ranges before parameter expansion.rule.{yml,json}
 
report_dir='case files'
pattern='*.json'

printf '<%s>\n' "$report_dir"     # one argument in Bash and Zsh
printf '<%s>\n' $report_dir       # Bash normally splits; Zsh normally does not
printf '<%s>\n' "$pattern"        # literal *.json in both
printf '<%s>\n' $pattern          # Bash may glob; Zsh scalar behavior differs
Your shell dialect is part of the runtimeDo not depend on an unquoted scalar behaving the same in Bash, Zsh, Dash, or another shell. Quote data expansions, use arrays in shells that support them, and declare the interpreter a script requires.

Safe argument construction

In Bash or Zsh, use arrays when building a command dynamically. An array preserves each element as one argument without evaluating data as shell syntax.

args=(--format json --limit 50)
[[ -n "${since:-}" ]] && args+=(--since "$since")
python3 analyzer.py "${args[@]}"

# Avoid eval "$user_supplied_text"
# It turns data back into executable shell syntax.

05 · Environment

Startup files: what runs when

Shell startup behavior depends on the shell, whether it is login or non-login, and whether it is interactive. That is why blindly editing every dotfile creates duplicate PATH entries and confusing side effects.

Shell / modeCommon user filesTypical use
Zsh login~/.zprofileLogin-session environment such as PATH setup.
Zsh interactive~/.zshrcAliases, prompt, completion, interactive options.
Bash login~/.bash_profile or ~/.profileLogin-session environment.
Bash interactive non-login~/.bashrcAliases, prompt, interactive helpers.
Non-interactive scriptNormally none of the interactive filesThe script must declare what it needs.
 
printf 'shell process: %s\n' "$$"
printf 'declared shell: %s\n' "$SHELL"
ps -p $$ -o command=
case $- in *i*) echo interactive ;; *) echo non-interactive ;; esac
Keep startup files boringA startup file should be fast, repeatable, and quiet. Do not print output or launch long-running programs unconditionally; non-obvious side effects break terminals, remote sessions, and tooling.

06 · Reliable automation

Write scripts that fail visibly

#!/usr/bin/env bash
set -euo pipefail

readonly input=${1:?usage: analyze.sh ACCESS_LOG}
readonly out_dir=${OUT_DIR:-reports}

mkdir -p "$out_dir"
python3 analyzer.py "$input" > "$out_dir/summary.json"
printf 'wrote %s\n' "$out_dir/summary.json"
#!/usr/bin/env bash

Select the interpreter through PATH.Portable across common user environments; use a fixed absolute interpreter path when the runtime must be tightly controlled.

set -e

Exit on some unhandled failures.Useful with care, but its exceptions depend on shell syntax and context; handle expected failures explicitly instead of treating it as complete error handling.

set -u

Reject unset variables.Catches misspellings and missing configuration instead of substituting an empty string.

set -o pipefail

Expose pipeline failures.Without it, a failed early stage can be hidden by a successful final command.

trap cleanup EXIT

Run cleanup on script exit.Use for temporary resources, while ensuring cleanup targets are explicit and validated.

shellcheck script.sh

Statically inspect shell code.Finds common quoting, expansion, portability, and error-handling bugs.

Idempotent means safe to repeatA setup script should converge on the same result when run twice: create missing directories, verify before appending, update files atomically, and avoid duplicating config.

07 · On the job

Detection-engineering scenarios

MYSTERY BINARY

The analyzer differs between your terminal and CI

Compare command resolution and exported environment instead of reinstalling randomly.

type -a python3
python3 -c 'import sys; print(sys.executable); print(sys.version)'
env | sort
# In CI, record the same three outputs and compare.

What this reveals: a virtual environment, user-installed binary, alias, or PATH order difference.

UNSAFE INPUT

A case filename contains spaces and wildcard characters

Treat the path as one argument and terminate option parsing when the command supports --.

case_file='captures/login attempt [1].json'
shasum -a 256 -- "$case_file"     # macOS; sha256sum on GNU/Linux
python3 analyzer.py --input "$case_file"

Why it matters: unquoted evidence paths can be split, expanded, or mistaken for options, producing the wrong result without an obvious error.

CRON FAILURE

A script works manually but not from a scheduler

Assume a smaller environment and different working directory. Make inputs, output paths, PATH, and interpreter explicit.

#!/usr/bin/env bash
set -euo pipefail
PATH=/usr/local/bin:/usr/bin:/bin
cd /opt/detection-rules
exec ./run-validation.sh >> /var/log/rule-validation.log 2>&1
TRACE

A setup script behaves differently on the second run

Trace expansions and commands in a sanitized lab run. Never enable tracing around secrets because expanded values can enter logs.

PS4='+ ${BASH_SOURCE}:${LINENO}: '
bash -x ./setup-lab.sh
bash -n ./setup-lab.sh
shellcheck ./setup-lab.sh

08 · Practice

Hands-on drills

Run these from a blank terminal. Save commands, outputs, and your explanation—not just the final result.

1. Trace Python through PATH

15 min
printf '%s\n' "$PATH"
type -a python python3
command -v python3
ls -l "$(command -v python3)"
python3 -c 'import os,sys; print(sys.executable); print(os.environ["PATH"])'
  • Explain the left-to-right PATH search.
  • Identify aliases, shims, or symlinks in the chain.
  • Predict what changes after activating a virtual environment.

2. Compare Bash and Zsh quoting

20 min
mkdir -p shell-lab && cd shell-lab
touch 'one report.json' 'two.json' 'literal*.json'
cat > quote-demo.sh <<'EOF'
value='*.json'
set -- $value
printf 'unquoted argc=%s\n' "$#"
printf '<%s>\n' "$@"
set -- "$value"
printf 'quoted argc=%s value=<%s>\n' "$#" "$1"
EOF

bash quote-demo.sh
zsh quote-demo.sh
  • Explain why Bash and Zsh can produce different unquoted argument counts.
  • Explain why the quoted form remains one literal argument in both.
  • State the script interpreter and options you would require instead of relying on interactive defaults.

3. Build an idempotent setup-and-test script

30–45 min

Create a script that makes a lab directory, creates a virtual environment only when absent, installs from a pinned requirements file, runs tests, and succeeds unchanged on a second run.

  • Use strict mode and quote every data/path expansion.
  • Run shellcheck and explain every suppression, if any.
  • Capture first-run and second-run transcripts; explain why nothing duplicates.
