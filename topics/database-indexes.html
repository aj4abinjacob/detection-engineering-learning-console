Index the predicate you actually run.

An index is an ordered access path with write and storage cost, not a magic speed switch. Query shape, selectivity, statistics, and engine policy decide whether it helps.

01 · Purpose

Indexes are evidence-backed tradeoffs

Detection databases repeatedly filter time ranges, tenants, IPs, and status codes. An index can avoid scanning many rows, but costs every insert/update/delete and can be ignored when a scan is cheaper.

TRIAGE

Fast narrow lookup

Find one tenant/IP/time slice without reading all events.

INGEST

Write cost

Each index must be maintained as telemetry arrives.

STORAGE

Space cost

More indexes compete with data and cache.

REVIEW

Prove the plan

Use plan evidence; do not infer use from DDL.

02 · Mental model

B-tree navigation narrows ordered keys

Root/branchesCompare key ranges to choose a child page.
→
Leaf entriesOrdered key values point to table rows/tuple locations.
→
RowsFetch/filter the actual result as needed.

B-tree lookup/range traversal is commonly described O(log n) to reach a key plus result work. That model does not promise a particular database plan, physical I/O count, or wall-clock time.

03 · Selectivity

Low result fraction is often where an index earns its cost

A predicate returning most of a table can make sequential scan cheaper than random row visits. Statistics, table size, correlation with physical order, visibility, cache, joins, and estimated row counts affect the optimizer. An index on a low-cardinality boolean/status may help only with a selective companion predicate or partial index—measure, never assume.

Index presence is not usePlanners can legitimately choose a sequential scan, bitmap path, or another index. “I created it” is not evidence; compare realistic plans and result correctness.

04 · Composite order

-- PostgreSQL/SQLite-compatible DDL form; run only in a disposable lab
CREATE INDEX idx_events_tenant_seen_ip
ON events (tenant_id, seen_at, client_ip);

-- Supports a leftmost prefix such as tenant_id = ? and seen_at range.
SELECT * FROM events
WHERE tenant_id = ? AND seen_at >= ? AND seen_at < ?;

Use: order columns for common equality predicates then range/order needs, based on actual query patterns. Assumption: the engine can exploit that order for the supplied predicates. Risk: after a range predicate, later B-tree columns often cannot narrow the same scan in the simple leftmost-prefix model; do not put every column into one giant index. PostgreSQL offers additional index types/features; SQLite planning differs—inspect each engine.

06 · Indexes are maintained data

Writes update table plus every applicable index; more/wider indexes consume disk, cache, backup/replication work, and vacuum/maintenance effort. Unique indexes enforce a constraint as well as access path. Remove an index only after reviewing query workload and constraints—an unused-looking index can support rare incident response or uniqueness guarantees.

07 · Safe lab workflow

-- SQLite-compatible, synthetic local schema
CREATE TABLE events(tenant_id TEXT, seen_at TEXT, client_ip TEXT, status INTEGER);
CREATE INDEX idx_events_tenant_seen ON events(tenant_id, seen_at);
EXPLAIN QUERY PLAN
SELECT client_ip FROM events
WHERE tenant_id = 'lab' AND seen_at >= '2026-01-01T00:00:00Z';

Use: a local disposable database and synthetic values. Risk: DDL changes schema and can lock/consume resources; do not run index experiments on production. PostgreSQL uses EXPLAIN/EXPLAIN ANALYZE, not SQLite’s output format.

08 · Safety

Production change requires authorityCreate/drop/reindex operations may lock, use substantial I/O, affect replication, and change write latency. Capture workload evidence, test on representative non-production data, coordinate a migration/rollback plan, and use least-privileged access. Never paste customer identifiers into a benchmark artifact.

09 · Detection scenarios

HUNT

Tenant time-range hunt is slow

Start from tenant_id = ? AND seen_at ≥ ? AND seen_at < ?; test a composite index in that order and compare plans/rows, not only elapsed time.

INGEST

Adding indexes slows bulk telemetry

Each write updates indexes. Keep only justified paths and measure ingest latency plus storage, not just query speed.

STATUS

Index on status does nothing

If most rows share a status or the query returns most data, scan is sensible. Combine selective dimensions or reconsider the query.

DATE

Day extraction disables a time index

Rewrite to a half-open timestamp range or evaluate an engine-specific expression index, with timezone semantics tested.
