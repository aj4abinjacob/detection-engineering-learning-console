Mobile API defense · attestation

Bind a mobile claim to the action, then keep its limits visible.

Mobile API abuse does not need a browser, so browser fingerprints cannot cover it. Play Integrity and Apple DeviceCheck/App Attest can provide signed, server-validated platform signals, but a valid result is bounded evidence about an app/device context and request binding—not proof of a human, honest account, harmless intent, or a permanent device identity.

Why this matters

A mobile app can call your API directly; a web challenge or browser fingerprint may never run. Attestation helps a server decide how much trust to place in a sensitive mobile action when combined with authentication, authorization, rate limits, fraud controls, and telemetry. It must be integrated at the backend: accepting an opaque token in the client is not validation.

Mental model: platform result + bound action + server policy

Server challenge/contextOne-time state or deterministic request digest for a sensitive action.
→
App/platform serviceCreates platform-protected attestation/assertion or integrity token.

Backend validationVerifies issuer, binding, freshness, app identity, lifecycle, then applies tiered policy.

A cryptographic result is meaningful only with server-side verification and a match to the exact action context.

Android Play Integrity: request-bound integrity verdicts

Google’s current Play Integrity API offers standard and classic request flows. For a standard request, the app prepares a token provider, computes a digest of relevant request parameters, passes it as requestHash, receives an encrypted token, and sends it to the app backend. The backend sends the token to Google Play for decryption/verification and evaluates the returned verdict. Verify request package, request hash, timestamp/freshness, and the relevant app/device/account verdicts before policy.

Google documents automatic replay protection for standard requests, but still recommends binding the request with a hash and checking the returned request details. Do not put plaintext sensitive data into a hash/nonce field; use a stable digest of the relevant server-known representation. Do not cache a verdict as a reusable credential: it weakens request-specific protection and increases proxy/relay risk.

Apple App Attest: attest a key, then verify assertions

App Attest uses DCAppAttestService to create a cryptographic key on a device and obtain an attestation object. Your server validates the attestation and retains the associated public key/key identifier. For later sensitive actions, the app creates assertions with that key; the server verifies the assertion, its server-provided challenge binding, and the monotonically increasing counter. Apple’s validation guidance includes verifying the Apple certificate chain, App ID hash/RP ID, challenge-derived nonce, key identifier/public key relationship, environment, and initial counter for attestation.

Do not equate App Attest with DeviceCheck: App Attest supplies an attested key and per-action assertions. DeviceCheck has a separate service for device tokens and two server-managed bits per device. Select the service based on the actual abuse question and platform constraints.

DeviceCheck: limited server-managed device state

Apple DeviceCheck gives an app a token that its server uses with Apple’s service to query or set two binary values associated with a device while preserving the service’s privacy model. It can support narrowly defined business state, such as a promotion already redeemed. It is not a general device identifier, an App Attest assertion, or proof that a user/account is trustworthy. Treat availability and service errors as operational states with safe fallbacks.

Canonicalization must be designed and tested: agree on field order, encoding, excluded fields, and version. Bind action, account/session context, amount or target where relevant, and an expiration. Never log raw tokens, server challenges, authorization headers, or attestation material in analytics.

Server validation is the security boundary

  1. Authenticate and authorize first. Attestation supplements but does not replace user/session authorization.
  2. Receive a token or assertion over an authenticated channel. Associate it with an expected app/version/action context; apply size and rate limits.
  3. Validate with the platform’s documented server process. For Play Integrity, use Google’s backend decode/verify flow. For App Attest, validate the object/certificates/binding/signature/counter against Apple’s guidance.
  4. Check binding and lifecycle state. Match request digest/challenge, freshness, key ID, stored counter, and one-time-use state.
  5. Apply a tiered response. Allow, reduce privilege, step up, delay/review, or deny according to verified result plus independent abuse evidence.
Never trust the client’s interpretationA mobile client can display, omit, serialize, retry, or route data in ways your server must not rely on. The server makes the decision after validating the platform response and its own transaction state.

Key, token, and policy lifecycle

Store App Attest public keys/key IDs, last accepted counters, server challenge status, validation timestamp, app/environment metadata, and an auditable policy version—not private keys or raw token payloads beyond approved retention. Plan enrollment, first-attestation failure, key invalidation/rotation, app reinstall/device migration, platform outage, version rollout, incident revocation, and user support. Google APIs and Apple services can change availability, fields, quotas, and platform requirements, so pin implementation to current official documentation and update tests with SDK/API changes.

What valid results do—and do not—prove

A verified, bound result can supportIt does not prove
That a platform service produced a result satisfying the checked app/device/environment claims at the relevant time, under the documented validation flow.That a human initiated the action, the account is legitimate, or the request has benign intent.
That the expected request/challenge data matched when the server checks it.That the transaction cannot be relayed, farmed, socially engineered, or abused through a valid app/device.
Tiering confidence for a specific route/action.Permanent device identity, universal anti-fraud coverage, or immunity to platform/service failures.

High-level threats include modified or spoofed client environments, relay/proxying of otherwise valid requests, and farmed use of legitimate devices/accounts. Defend with request binding, short freshness, one-time state, server authorization, rate/velocity controls, account reputation, transaction risk controls, and ongoing measurement. Do not seek or publish operational methods to defeat platform attestation.

Detection-engineering scenarios

1. High-value Android transfer

Trigger: a mobile transfer exceeds a risk threshold. Artifact: decoded and verified Play Integrity verdict, request-hash comparison, timestamp, authenticated account, and transaction policy version. Observation point: application backend. Reasoning: validate binding before evaluating verdict tier, then combine with account/transaction controls for a step-up or review. False-positive boundary: a valid verdict does not make an anomalous transfer safe; an unavailable verdict does not automatically prove fraud.

2. Reused iOS assertion challenge

Trigger: an assertion arrives for a challenge already consumed. Artifact: challenge ID/state/expiry, key ID, counter history, and signature-validation result. Observation point: App Attest backend verifier. Reasoning: reject the duplicate action, preserve an audit record, and investigate route/session behavior. False-positive boundary: a retry or network timeout needs an idempotent user-safe flow; do not accuse a user from one duplicate.

3. Promotion abuse needs DeviceCheck state

Trigger: a user requests a one-time offer. Artifact: validated DeviceCheck token outcome, server-side two-bit state, account eligibility, and redemption record. Observation point: owned promotion API. Reasoning: use the limited flag alongside account and transaction controls, with privacy review and support remediation. False-positive boundary: DeviceCheck state is not a complete fraud identity and may need a fair appeal/fallback path.

4. Valid attestation accompanies coordinated abuse

Trigger: many verified mobile requests exhibit abnormal velocity and shared account behavior. Artifact: validation results, rate windows, authorization outcomes, and campaign timeline. Observation point: API gateway and backend. Reasoning: valid attestation confirms only its bounded claim; apply account-level and transaction-level abuse controls. False-positive boundary: do not treat attestation as an all-clear or infer the mechanism behind the campaign from tokens.

Artifact-producing drills

1. Validity one-pager

Save artifacts/mobile-attestation/validity-boundaries.md comparing a valid Play Integrity result, App Attest assertion, and DeviceCheck token/state: what each supports, what it does not, and which backend checks are required.

  • Use only official documentation and supplied examples; never generate third-party tokens.
  • Cover spoof/relay/farming only as high-level threat classes and defensive controls.

2. Request-binding design

Save artifacts/mobile-attestation/request-binding.md for a hypothetical owned sensitive API. Define canonical fields, digest/challenge, expiry, single-use storage, idempotency behavior, server comparison, and data handling.

  • Do not include a real token, key, credential, or nonce value.
  • Explain replay and tampering resistance without claiming perfect prevention.

3. Validation and lifecycle table

Save artifacts/mobile-attestation/validation-lifecycle.csv with normal, stale, mismatched-binding, duplicate, unavailable, key-rotation, and platform-outage cases; document response, owner, metric, and user-safe fallback.

  • Separate verification failure from a fraud verdict.
  • Present the resulting policy without AI.
