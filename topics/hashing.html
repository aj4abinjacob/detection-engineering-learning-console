Make keys stable before you count on them.

A dict uses a hash to find candidates and equality to confirm a key. Good keys preserve grouping; broken or mutable ones corrupt it.

01 · Purpose

Hashing is the grouping primitive

Per-IP counters, dedup sets, join maps, and caches all assume their keys mean the same thing over time. Hashing makes lookup fast only while that semantic contract holds.

LOOKUP

Find candidates

Hash narrows a table location; equality resolves actual identity.

GROUPING

Equal keys merge

Request keys must include precisely the dimensions a detector groups by.

RESILIENCE

Collisions exist

Expected O(1) is not a guarantee under pathological hashes.

SAFETY

Hash is not a digest

Never persist it as an identifier or use it as cryptographic evidence.

03 · Equality/hash contract

from dataclasses import dataclass
@dataclass(frozen=True)
class RequestKey:
    tenant: str; ip: str; route: str

a = RequestKey("lab", "203.0.113.4", "/login")
b = RequestKey("lab", "203.0.113.4", "/login")
assert a == b and hash(a) == hash(b)
assert {a: 1}[b] == 1

Use: frozen value objects/tuples with stable, hashable identity fields. Assumption: those fields capture the detector’s real grouping definition. Risk: adding mutable tags, counters, timestamps, or headers to a key changes semantics and often makes the key unhashable or unsafe.

If implementing manually, __eq__ should return NotImplemented for unsupported types and __hash__ should hash the same stable tuple used by equality. Normal Python protects value-equality classes by making them unhashable unless an appropriate hash is supplied.

04 · Collisions and cost

class BadKey:
    def __init__(self, value): self.value = value
    def __eq__(self, other): return isinstance(other, BadKey) and self.value == other.value
    def __hash__(self): return 0  # lab only: every key collides

Use: only this disposable lab to demonstrate collision work. Risk: never ship a constant/low-entropy hash; many colliding keys can turn lookup/insertion toward O(n) and create a denial-of-service exposure in an unbounded ingestion path. Python’s table implementation mitigates some cases but cannot make a deliberately bad key distribution fast.

05 · Mutable-key hazard

class MutableKey:
    def __init__(self, ip): self.ip = ip
    def __hash__(self): return hash(self.ip)
    def __eq__(self, other): return isinstance(other, MutableKey) and self.ip == other.ip

key = MutableKey("203.0.113.4"); counts = {key: 1}
key.ip = "198.51.100.7"  # lab-only corruption: do not do this in production
# counts[key] may now fail: its table placement used the old hash

Create a new immutable normalized key instead of mutating a member used in equality/hash. Do not attempt to recover a corrupted production dict by guessing its internal layout; rebuild it from trustworthy source data.

06 · Randomization and portability

CPython and other implementations may randomize hashes of some built-in types such as strings/bytes between processes to reduce predictable collision attacks. Therefore hash("ip") is not a stable cross-run value, database key, or evidence fingerprint. Use a documented canonical identifier or a cryptographic digest when that is actually required; a digest has different threat-model and secret-handling requirements.

Version/implementation noteHash-table internals, collision handling, object layout, and randomization details are implementation/version details. Depend on the language-level equality/hash contract, not a particular integer hash or bucket arrangement.

07 · Safety

hash(key)

Inspect a local key contract.Use in tests to verify equal keys hash equally. It is nonportable across processes for randomized types.

key in mapping

Perform normal membership.Use rather than direct dunder calls; it invokes correct hash/equality dispatch.

@dataclass(frozen=True)

Express immutable value-key intent.Nested mutable members still require review; frozen blocks attribute rebinding, not deep mutation.

Untrusted cardinalityEven good hashes cannot stop a stream of distinct valid client keys from consuming memory. Rate-limit, expire, cap, and monitor per-entity state; treat an attacker-controlled key space as an explicit resource boundary.

08 · Detection scenarios

VELOCITY

Equivalent requests split into counters

Identity-based custom objects become distinct dict keys. Use frozen value equality for the exact fields that define one grouping.

NORMALIZE

Route canonicalization mutates a key

Normalize before constructing the key. Keep raw event data separate; never alter an inserted key’s equality/hash fields.

ABUSE

High-cardinality query parameters stress state

Do not key a long-lived map directly by uncontrolled full URLs. Choose bounded canonical dimensions and observe evictions.

FORENSICS

An analyst stores Python hash values

The next process cannot reproduce randomized hashes. Store canonical text/bytes and compute a documented digest only if a stable fingerprint is required.

Hands-on drills

1. RequestKey map

25 min

Build the frozen key above, count two equal fresh keys, and save output to artifacts/4.2-request-key.txt.

  • List the identity fields and exclude mutable metadata.
  • Prove equality and equal hashes.
  • Explain why a hash collision alone is not incorrectness.

2. Collision lab

20 min

Time bounded insertion/lookups of BadKey versus ordinary immutable keys; save environment and results.

  • Use only a few thousand in-memory values.
  • Save artifacts/4.2-collisions.txt.
  • Explain expected O(1) versus collision-driven behavior without claiming universal timings.

3. Mutated-key demonstration

20 min

Run the disposable MutableKey example and then replace it with RequestKey.

  • Save observed lookup behavior.
  • Explain why the key is placed using its old hash.
  • Never use the broken class in analyzer code.
