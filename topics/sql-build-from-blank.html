01 · Purpose

Why SQL is a detection-engineering language

Detection data is usually a collection of related facts: an account, its requests, a device, a transaction, a rule decision. SQL makes you state how those facts connect and exactly which population each aggregate describes.

INVESTIGATE

Build a cohort

Join an event to its owner, then ask which accounts, routes, or source keys behave unusually.

VALIDATE

Measure a rule

Group by time or decision to compare volume, error, conversion, or false-positive evidence.

OPERATE

Respect scale

A query that scans a small lab table can become expensive or disruptive against high-volume telemetry.

AUDIT

Make assumptions inspectable

Schema constraints, query text, and parameter values are a trail another engineer can review.

Diagnostic ruleKeep the exact original attempt and your “guessed this” notes. This guide is for post-diagnostic review, not a way to improve the Week 0 measurement retroactively.

02 · Mental model

Rows have identity; relationships have cardinality

A table models one kind of thing. A primary key identifies a row; a foreign key states that a value must refer to a row in another table. A join creates combinations that satisfy the relation—so its row count is part of the answer.

usersOne row per account.id PRIMARY KEY
1 → many
ordersMany purchases may belong to one account.user_id FOREIGN KEY
→
query resultOne row per selected relationship or aggregate group.JOIN + GROUP BY

A join is not “put the tables side by side.” It pairs rows. If a user has three orders, that user appears three times before grouping.

-- Logical question: which users have orders?
-- Result grain before grouping: one row per matching order.
SELECT u.id, u.email, o.id AS order_id, o.amount_cents
FROM users AS u
JOIN orders AS o ON o.user_id = u.id;

03 · Foundation

Create a small users/orders schema from blank

Use integer money units in this learning schema to avoid floating-point rounding. Real commerce needs additional business rules—currency, refunds, status transitions, retention, and access control—which this tiny model deliberately leaves out.

-- SQLite: first enable this for every connection.
PRAGMA foreign_keys = ON;

CREATE TABLE users (
  id INTEGER PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  created_at TEXT NOT NULL
);

CREATE TABLE orders (
  id INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL,
  amount_cents INTEGER NOT NULL CHECK (amount_cents >= 0),
  status TEXT NOT NULL,
  created_at TEXT NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id)
);

CREATE INDEX orders_user_id_idx ON orders(user_id);
ChoiceWhat it guaranteesWhat it does not guarantee
PRIMARY KEYA non-null unique row identifier.That an ID means the correct real-world person.
FOREIGN KEYAn order references an existing user when enforcement is active.That an order is authorized or not fraudulent.
UNIQUE(email)No duplicate exact stored email value.Case-insensitive or normalized identity semantics.
CHECK(amount_cents >= 0)A simple local invariant.Currency correctness or refund policy.

04 · Relationships

Write the two-table join deliberately

The join condition belongs in ON. Put row filters in WHERE unless you deliberately need to preserve unmatched rows from an outer join.

-- All orders with their owner's email: inner join omits users with no orders.
SELECT o.id, u.email, o.amount_cents, o.status, o.created_at
FROM orders AS o
JOIN users AS u ON u.id = o.user_id
ORDER BY o.created_at, o.id;

-- Keep every user, even where no order exists.
SELECT u.id, u.email, o.id AS order_id
FROM users AS u
LEFT JOIN orders AS o ON o.user_id = u.id
ORDER BY u.id, o.id;
JOIN ... ON u.id = o.user_id

Return matching pairs.Use for the required two-table relationship. Check the result grain: each order produces one row with this one-to-many schema.

LEFT JOIN

Preserve rows on the left.Use to find users with no orders, then test WHERE o.id IS NULL.

COUNT(*) vs COUNT(o.id)

Count rows versus non-null joined values.With a left join, COUNT(*) counts the preserved user row; COUNT(o.id) counts actual orders.

Classic counting bugA LEFT JOIN followed by WHERE o.status = 'paid' removes null order rows and behaves like an inner join. Put the status predicate in ON when “users with zero paid orders” must remain.

05 · Questions

Group first, then use HAVING on groups

WHERE chooses input rows before aggregation. GROUP BY creates groups. HAVING filters the computed groups. The ordering of clauses describes the logical question.

-- Orders per user, sorted from most to least.
SELECT u.id, u.email, COUNT(o.id) AS orders_per_user
FROM users AS u
LEFT JOIN orders AS o ON o.user_id = u.id
GROUP BY u.id, u.email
ORDER BY orders_per_user DESC, u.id ASC;

-- Accounts with at least two successful orders.
SELECT o.user_id, COUNT(*) AS paid_orders, SUM(o.amount_cents) AS paid_cents
FROM orders AS o
WHERE o.status = 'paid'
GROUP BY o.user_id
HAVING COUNT(*) >= 2
ORDER BY paid_orders DESC, o.user_id ASC;
ClauseQuestion it answersExample
WHEREWhich individual order rows count?WHERE status = 'paid'
GROUP BYWhat is one output group?GROUP BY user_id
HAVINGWhich computed groups survive?HAVING COUNT(*) >= 2
ORDER BYHow should stable output be presented?ORDER BY orders_per_user DESC, user_id

Portable discipline: select only grouped columns or aggregate expressions. Some engines allow looser expressions in some modes; relying on them makes a query's meaning engine-dependent.

06 · Scale

Predict one slow query—and say why

The diagnostic asks for a query you expect to be slow plus one sentence of reasoning. A prediction is valuable when it names data volume, access path, and the operation that must process many rows.

-- Expected to become slow as orders grows if no suitable index exists.
SELECT user_id, COUNT(*)
FROM orders
WHERE created_at >= '2026-08-01T00:00:00Z'
GROUP BY user_id
ORDER BY COUNT(*) DESC;

-- Reason: without an index that helps the time predicate, the engine may scan
-- every order in the time range (or whole table), then build aggregate/sort state.

An index is not a magic “make it fast” switch. It costs storage and makes writes more expensive. Query planners choose among available paths using statistics; verify your prediction with the engine's plan, not elapsed time from one warmed-up laptop run.

-- SQLite CLI
EXPLAIN QUERY PLAN
SELECT user_id, COUNT(*) FROM orders
WHERE created_at >= '2026-08-01T00:00:00Z'
GROUP BY user_id;

-- PostgreSQL: do this only on approved, bounded data.
EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, COUNT(*) FROM orders
WHERE created_at >= TIMESTAMPTZ '2026-08-01 00:00:00+00'
GROUP BY user_id;
Plan inspection can execute workEXPLAIN ANALYZE actually runs the statement in PostgreSQL. It is not a harmless preview for write statements or an unbounded production query. Use plain EXPLAIN first and follow local access and change controls.

07 · Platform

SQLite and PostgreSQL are not interchangeable laboratories

ConcernSQLitePostgreSQL
Starting local statesqlite3 diagnostic.db creates a file database.Requires a running server, role, database, and network/local socket connection.
Foreign keysEnforcement must be enabled per connection with PRAGMA foreign_keys = ON.Foreign keys are enforced by the server when declared.
Time typesStores values using dynamic typing conventions; choose and document a text/epoch convention.Has typed temporal values; use timestamptz for an instant with timezone-aware semantics.
Parameters in application codeUse the driver’s parameter markers, never string interpolation.Also use driver parameters; marker syntax depends on the driver, not SQL itself.
# Disposable SQLite lab only; creates a file in the current directory.
mkdir -p sql-diagnostic-lab
cd sql-diagnostic-lab
sqlite3 diagnostic.db < schema.sql
sqlite3 -header -column diagnostic.db < queries.sql

# PostgreSQL: use a separate PostgreSQL-specific file, never the SQLite schema.
# postgres-schema.sql uses BIGINT GENERATED BY DEFAULT AS IDENTITY,
# TIMESTAMPTZ, REFERENCES, and CHECK; it contains no SQLite PRAGMA.
psql --dbname=diagnostic_lab --file=postgres-schema.sql

SQLite's schema.sql is not valid PostgreSQL input: PRAGMA, identity generation, and temporal typing differ. On Windows, use the appropriate SQLite or PostgreSQL client; shell redirection syntax differs in PowerShell. Never put passwords in a shell command, SQL file, screenshot, or committed configuration.

08 · On the job

Detection-engineering scenarios

FRAUD

Many failed payments converge on one account

Filter a bounded time window, group by account and failure state, then join the account only for the attributes you are authorized to view. The count identifies a review cohort; it does not establish intent or allow an account action without corroboration.

DATA LOSS

Users “disappear” from a dashboard

An inner join removes users with no matching event/order. Compare it with a left join and count null event IDs. This distinguishes an absent activity record from an unintended population filter.

RULE QA

A conversion metric changed after a rule rollout

Write the denominator before the query: all eligible users, all attempts, or only completed orders. Then use WHERE for eligibility and HAVING for thresholded cohorts. Different denominators can reverse the apparent result.

COST

An incident query overloads telemetry storage

Start with a narrow time partition and a projection of only necessary columns, inspect the plan, and coordinate with the data owner. A full scan plus large sort may be technically correct yet operationally irresponsible.

09 · Practice

Hands-on drills

All drills produce a reviewable artifact. Preserve the diagnostic attempt, then use a separate disposable sql-diagnostic-lab directory.

1. Build and query a tiny SQLite database

35 min

Save schema.sql, seed.sql, and results.txt. Include the required two-table join, orders-per-user sorted, and a user with no orders.

  • Draw the primary-key/foreign-key relationship and name the result grain of each query.
  • Explain why COUNT(o.id) differs from COUNT(*) under your left join.
  • Show PRAGMA foreign_keys is enabled before testing a bad insert.

2. Add GROUP BY + HAVING evidence

25 min

Save aggregate.sql and aggregate-explanation.md. Write one query for paid orders per user and one cohort query using HAVING.

  • State exactly which rows WHERE removes before grouping.
  • Calculate one group by hand and compare it to output.
  • Add a deterministic secondary sort so output does not depend on accident.

3. Make a performance prediction

20 min

Save slow-query.sql, query-plan.txt, and guesses.md. Include the one-sentence reason you would have given during the diagnostic.

  • Name the filter, expected scan/sort/aggregate work, and index that might change the plan.
  • Label the plan engine and version; do not claim that SQLite and PostgreSQL plans mean the same thing.
  • Keep “what I guessed” separate from “what the plan showed.”
