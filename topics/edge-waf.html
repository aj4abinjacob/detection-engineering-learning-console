Purpose

Why this matters in detection engineering

An edge or WAF observes traffic at a specific termination point and can apply managed or custom rules before the origin. Capability and action availability are plan-specific and change over time; current official documentation is the source of truth for the configured account.

A detection engineer must be able to trace how an observation becomes a feature, how that feature supports an inference, and how policy turns the inference into an action. The useful unit for this topic is an edge-origin diagram plus an app-side shadow rule mirroring one intended expression, replay results, plan capability snapshot, and rollback proof. Preserve enough lineage to reproduce it without collecting content that the decision does not require.

Boundaries

What can go wrong

Closest legitimate lookalike: shared IPs, privacy relays, health checks, crawlers, mobile clients, and accessibility flows can match a narrow edge expression.

Pipeline or interpretation failure: trusting spoofable forwarded headers, assuming enterprise signals exist on Free, blocking before shadow evaluation, and omitting origin controls create blind spots.

Safety boundary: work only with supplied sanitized fixtures or systems and accounts you own and are authorized to test. Minimize identifiers, exclude secrets and content, bound retention and access, and provide an accessible path when an automated action could affect a person.

Do not overclaimThis guide establishes a method for controlled defensive evidence. It does not prove identity, intent, causality, universal tool behavior, or how a third-party system will classify traffic.

Method

A repeatable defensive workflow

  1. Declare the question and scope. Name the owned route, entity, time range, authorization, expected population, and prohibited data before collection.
  2. Version the evidence. Save an edge-origin diagram plus an app-side shadow rule mirroring one intended expression, replay results, plan capability snapshot, and rollback proof, its schema or tool version, observation point, event and availability times, and missing-value behavior.
  3. Build a negative control. Include shared IPs, privacy relays, health checks, crawlers, mobile clients, and accessibility flows can match a narrow edge expression and state the response it should receive.
  4. Replay and decide. Recompute from immutable input, compare expected output, inspect false positives and false negatives, then apply validate in non-enforcing app shadow mode, compare expected matches and lookalikes, and test a narrowly scoped rollback before any optional edge action.

Practice

Detection-engineering scenarios

BASELINE

1. The observed distribution changes

Trigger: a monitor for Cloudflare Free; WAF rules; rate limiting shifts outside its recorded baseline. Artifact: an edge-origin diagram plus an app-side shadow rule mirroring one intended expression, replay results, plan capability snapshot, and rollback proof. Reasoning: compare time, producer, release, population, and data quality before attributing the shift to abuse. Boundary: a changed distribution is an observed fact, not a malicious label.

LOOKALIKE

2. A legitimate journey matches the candidate

Trigger: the candidate logic fires on shared IPs, privacy relays, health checks, crawlers, mobile clients, and accessibility flows can match a narrow edge expression. Artifact: a labeled negative-control replay. Reasoning: preserve the case, inspect which feature dominated, and choose a proportionate fallback. Boundary: do not tune the case away without measuring what new false negatives the change creates.

QUALITY

3. The pipeline changes while the rule stays green

Trigger: trusting spoofable forwarded headers, assuming enterprise signals exist on Free, blocking before shadow evaluation, and omitting origin controls create blind spots. Artifact: contract-test result, schema versions, and quality counters. Reasoning: quarantine or mark degraded evidence and restore the producer contract before judging detection quality. Boundary: absence, default values, and parser failures are not benign observations.

POLICY

4. Evidence is strong enough to review, not to punish

Trigger: several versioned signals agree on an unusual owned-lab journey. Artifact: feature lineage, reason codes, policy version, and expected guardrails. Reasoning: validate in non-enforcing app shadow mode, compare expected matches and lookalikes, and test a narrowly scoped rollback before any optional edge action. Boundary: preserve rollback and never infer that an offline score proves the causal benefit of an intervention.
