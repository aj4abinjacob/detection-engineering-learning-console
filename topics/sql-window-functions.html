A single login record is weak context. Its previous login, rank within a user’s day, and count of nearby attempts often make the useful detection feature.

02 · Mental model

OVER adds a calculation to each row

PartitionWhich rows are peers? e.g. one IP.
→
Order/frameWhich peers are relevant now?
→
Window resultRank/count/previous value on current row.

PARTITION BY resets a calculation; ORDER BY defines sequence; a frame defines a subset of that ordered partition for frame-sensitive aggregates.

03 · Window versus GROUP BY

-- GROUP BY returns one row per client_ip
SELECT client_ip, count(*) FROM events GROUP BY client_ip;
-- Window retains event rows and attaches each IP total
SELECT event_id, client_ip, count(*) OVER (PARTITION BY client_ip) AS ip_total
FROM events;

Use: GROUP BY for summary rows; a window for row-level evidence plus aggregate context. Risk: joining a grouped summary back can be correct but is more verbose and can multiply rows if join keys are wrong.

04 · Ranking functions

SELECT client_ip, failures,
 row_number() OVER (ORDER BY failures DESC, client_ip) AS row_no,
 rank() OVER (ORDER BY failures DESC) AS rank_no,
 dense_rank() OVER (ORDER BY failures DESC) AS dense_rank_no
FROM daily_failures;

ROW_NUMBER gives unique sequence (add stable tie ordering); RANK leaves gaps after ties; DENSE_RANK does not. Choose based on reporting meaning, not aesthetics.

05 · Inter-arrival with LAG/LEAD

-- PostgreSQL syntax; timestamp subtraction yields an interval
SELECT client_ip, seen_at,
 seen_at - lag(seen_at) OVER (PARTITION BY client_ip ORDER BY seen_at, event_id) AS since_prev
FROM events;

Use: sequence analysis with a total deterministic order. Assumption: event_id breaks equal timestamps and event time is trusted. Risk: first row has NULL previous value; late/duplicate timestamps can produce surprising/nonpositive intervals and need data-quality policy.

06 · Frames: make them explicit

With ORDER BY, PostgreSQL’s default frame is typically from partition start through the current row’s peer group (RANGE ... CURRENT ROW semantics), not automatically “one minute.” Peers with equal order values can be included together. Use ROWS BETWEEN 2 PRECEDING AND CURRENT ROW for physical prior rows, or PostgreSQL RANGE BETWEEN INTERVAL '1 minute' PRECEDING AND CURRENT ROW for a time-value range. The latter requires an appropriate single ordering expression and differs from a rolling count definition that uses strict/open boundaries.

07 · PostgreSQL one-minute velocity

-- PostgreSQL-only: event-time rolling frame, counts [seen_at - 1 minute, seen_at]
SELECT event_id, client_ip, seen_at,
 count(*) OVER (
   PARTITION BY client_ip
   ORDER BY seen_at
   RANGE BETWEEN INTERVAL '1 minute' PRECEDING AND CURRENT ROW
 ) AS requests_last_minute
FROM events;

-- Add event_id to the data model for deterministic ties; RANGE frame has peer semantics.

Use: PostgreSQL event-time velocity where inclusive boundary and timestamp peers are acceptable/documented. Risk: this is PostgreSQL syntax and was not validated in SQLite. For strict boundary or tie-specific policy, use an explicit self/correlated range query or an engine-supported design and test exact edges.

08 · SQLite compatibility

-- SQLite 3.25+ supports basic windows; locally valid ranking example
SELECT client_ip, seen_at,
 row_number() OVER (PARTITION BY client_ip ORDER BY seen_at) AS seq
FROM events;

SQLite window support/version and datetime arithmetic differ from PostgreSQL; it does not validate PostgreSQL INTERVAL/RANGE query above. Label engine/version in artifacts and use numeric epoch ordering with tested SQLite syntax if building a SQLite lab.

09 · Safety

Window queries can sort and retain large partitionsBound time/tenant predicates, inspect plans, and avoid testing unbounded production tables. A high velocity score is a triage feature, not attribution; NAT, retries, bots, and batch jobs can all rank highly.

10 · Detection scenarios

AUTH

Failed login burst

Compute one-minute per-IP count with documented boundaries, then preserve individual rows for analyst verification.

AUTOMATION

Regular bot inter-arrivals

LAG exposes highly regular gaps; validate source clock and legitimate scheduler candidates.

TRIAGE

Rank account failure totals

Use dense rank for tiers or row number for a strict top list; define ties.

DATA

Tied timestamps inflate frame

Default/RANGE peers can make a count jump. Add stable ordering/explicit frame and test ties.
