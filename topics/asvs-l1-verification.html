Turn verification requirements into auditable evidence.

ASVS L1 is a verification baseline. A matrix makes requirement, applicability, pass/fail, evidence, owner, N/A rationale, and accepted risk review explicit.

Why it matters

A checklist without evidence creates confidence theater. Verification asks whether a specific requirement applies, how it is tested/inspected, and what remains unresolved.

Pin ASVS edition

The latest stable release checked in August 2026 is OWASP ASVS 5.0.0; the repository's master/bleeding-edge artifacts are not a stable verification target. Record the stable version, target release, review date, and reviewer. ASVS recommends version-qualified references such as v5.0.0-1.2.5 because identifiers can change. Never claim “ASVS compliant” without level, version, scope, and evidence.

The row is an illustrative AbuseGuard record for ASVS 5.0.0's Level 1 database-injection requirement; adapt its result to evidence you actually produced. Store links to local test/config/review artifacts, not copied secrets or production data. Status should be pass, fail, planned, N/A, or accepted risk—not ambiguous green.

Applicability

Assess architecture and feature set first. A requirement can be applicable even if not implemented; that is a fail/gap, not N/A. State component/route/data flow used in decision.

Pass/fail rigor

Pass requires reproducible evidence meeting the requirement. Fail identifies gap and owner. Planned is not pass. Re-test when code/config/dependency/deployment boundary changes.

Evidence quality

Combine tests, configuration inspection, manual review, and deployment proof as needed. Evidence records command/version/input/expected result, sanitized output, and limit. A unit test cannot prove reverse-proxy production configuration.

N/A must be defensible

N/A requires feature absence, architecture proof, and reassessment trigger. “We do not need it” is not rationale. Example: a requirement limited to a feature genuinely absent from v1, with code/config proof and trigger if feature is added.

Accepted risk is a decision

Accepted risk records threat/impact, current compensating controls, owner with authority, expiry/review date, and remediation trigger. It is not a permanent exemption or a disguised pass.

Review lifecycle

Review matrix at release, major architecture/dependency/auth changes, and incident learning. Keep evidence accessible but restrict artifacts containing topology or sensitive configuration.

Defensive scenarios

CSRF requirement

Applicable to cookie-auth state changes; evidence includes rejection tests and route inventory.

Feature absent

Defend N/A with source/config proof and reassessment trigger.

Proxy hardening gap

Mark fail/planned until local deploy evidence exists, not pass from app unit test.

Risk acceptance

Set owner/expiry/compensating control rather than silently omitting row.
