01 · Purpose

HTTP/2 semantics have binary implementation detail

HTTP/2 transmits binary frames over a connection. Frame settings/order may support grouping at a controlled endpoint, while proxying and library versions make broad identity claims unsafe.

02 · Frame baseline

RFC 9113 HTTP/2 uses frame header plus payload on a TCP connection, multiplexed by stream ID. SETTINGS is connection-level; WINDOW_UPDATE increases flow-control window; HEADERS carries compressed header blocks. Parsed frame data requires a compliant HTTP/2 decoder and HPACK state—never apply this guide’s representations to raw arbitrary bytes.

03 · SETTINGS

SETTINGS parameters are 16-bit identifiers with 32-bit values, including HEADER_TABLE_SIZE, ENABLE_PUSH (deprecated behavior/version context), MAX_CONCURRENT_STREAMS, INITIAL_WINDOW_SIZE, MAX_FRAME_SIZE, and MAX_HEADER_LIST_SIZE. Record order as observed if your chosen representation specifies it, along with ACK/endpoint/direction. SETTINGS values are negotiated configuration, not a cryptographic fingerprint.

04 · WINDOW_UPDATE

WINDOW_UPDATE increments connection or stream flow-control window. A client’s initial connection window behavior can be an implementation feature. Record whether the value is connection-level (stream 0), the increment, direction, and capture/parser point. Do not confuse it with SETTINGS_INITIAL_WINDOW_SIZE, which affects stream-level initial windows.

05 · Pseudo-header order

HTTP/2 pseudo-header fields begin with :, must precede regular header fields, and request pseudo-headers include :method, :scheme, :authority, :path as applicable. Their transmitted order can be recorded by a decoder, but proxy/libraries may rewrite them. Field names are lowercase in HTTP/2; header ordering/casing is not a durable identity signal.

06 · Akamai HTTP/2 representation

SETTINGS_ID:VALUE;...|WINDOW_UPDATE_INCREMENT|PSEUDO_HEADER_ORDER
# Example representation only: record exactly what your trusted parser emitted.
# Do not invent settings values or call it an RFC standardized fingerprint.

The commonly cited Akamai HTTP/2 fingerprint representation concatenates ordered SETTINGS id:value pairs, a connection WINDOW_UPDATE increment, and pseudo-header order using delimiters. It is a representation used in tooling/industry context, not an HTTP/2 RFC identity standard. Verify exact formatting, sentinel behavior, parser implementation/version, and observation direction from the implementation you use before comparing values.

07 · Observation point

A TLS/HTTP/2 terminator can decode client→edge frames; an origin behind a proxy may see proxy→origin HTTP/2, HTTP/1.1, or another protocol. A passive encrypted capture cannot directly supply HTTP/2 headers/settings without lawful decryption. Record endpoint roles and whether the terminating proxy reuses/configures outbound connections.

08 · Measure stability, don’t name clients

In a learner-owned loopback app, collect several sanitized client-to-local-terminator observations per client/version/config, then compare. HTTP library updates, browser settings, ALPN/proxy negotiation, connection reuse, and intermediaries can alter output. Report sample size and variance; do not state that an Akamai-format string “is Chrome” or proves bot behavior.

09 · Safety

Owned endpoint onlyUse existing owned captures, synthetic decoded fixtures, or a local terminator. No shared-interface/live third-party capture, endpoint probing, vendor-evasion work, or attempt to alter HTTP/2 fingerprint outside learner-controlled loopback.

10 · Defensive scenarios

UPDATE

Settings drift after browser upgrade

Trigger: representation changes. Artifact: owned sample set. Observation: settings/order difference. Reasoning: version/config likely. Boundary: no client identity claim.

PROXY

Origin sees one HTTP/2 profile

Trigger: uniform output. Artifact: topology. Observation: edge terminates/reissues connection. Reasoning: proxy profile. Boundary: origin cannot infer end client.

FLOW

Window behavior changes under load

Trigger: update increment variance. Artifact: local decoder logs. Observation: connection policy/load effect. Reasoning: implementation/resource condition. Boundary: avoid behavior label.

PARSER

Fixture violates pseudo ordering

Trigger: regular field before pseudo. Artifact: parser test. Observation: invalid fixture. Reasoning: decoder rejection expected. Boundary: no live malformed traffic.
