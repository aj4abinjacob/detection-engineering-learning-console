Purpose

Why this matters in detection engineering

An auditable playbook is a versioned state machine that validates input, enriches from approved sources, proposes an action, records approval and outcome, and supports replay or compensation. Automation does not transfer accountability away from the owner.

A detection engineer must be able to trace how an observation becomes a feature, how that feature supports an inference, and how policy turns the inference into an action. The useful unit for this topic is a mock playbook execution log with immutable input, step versions, actor, evidence, proposed action, approval, effect, and compensation reference. Preserve enough lineage to reproduce it without collecting content that the decision does not require.

Boundaries

What can go wrong

Closest legitimate lookalike: an analyst can reasonably reject the same proposal when business context or evidence availability differs.

Pipeline or interpretation failure: hidden mutable enrichment, excessive permissions, unrecorded manual steps, and irreversible actions prevent review and rollback.

Safety boundary: work only with supplied sanitized fixtures or systems and accounts you own and are authorized to test. Minimize identifiers, exclude secrets and content, bound retention and access, and provide an accessible path when an automated action could affect a person.

Do not overclaimThis guide establishes a method for controlled defensive evidence. It does not prove identity, intent, causality, universal tool behavior, or how a third-party system will classify traffic.

Method

A repeatable defensive workflow

  1. Declare the question and scope. Name the owned route, entity, time range, authorization, expected population, and prohibited data before collection.
  2. Version the evidence. Save a mock playbook execution log with immutable input, step versions, actor, evidence, proposed action, approval, effect, and compensation reference, its schema or tool version, observation point, event and availability times, and missing-value behavior.
  3. Build a negative control. Include an analyst can reasonably reject the same proposal when business context or evidence availability differs and state the response it should receive.
  4. Replay and decide. Recompute from immutable input, compare expected output, inspect false positives and false negatives, then apply use mock data, default to proposal, separate approval from execution, grant least privilege, and test compensation for every effect.

Practice

Detection-engineering scenarios

BASELINE

1. The observed distribution changes

Trigger: a monitor for validate → enrich → propose → record → replay/rollback shifts outside its recorded baseline. Artifact: a mock playbook execution log with immutable input, step versions, actor, evidence, proposed action, approval, effect, and compensation reference. Reasoning: compare time, producer, release, population, and data quality before attributing the shift to abuse. Boundary: a changed distribution is an observed fact, not a malicious label.

LOOKALIKE

2. A legitimate journey matches the candidate

Trigger: the candidate logic fires on an analyst can reasonably reject the same proposal when business context or evidence availability differs. Artifact: a labeled negative-control replay. Reasoning: preserve the case, inspect which feature dominated, and choose a proportionate fallback. Boundary: do not tune the case away without measuring what new false negatives the change creates.

QUALITY

3. The pipeline changes while the rule stays green

Trigger: hidden mutable enrichment, excessive permissions, unrecorded manual steps, and irreversible actions prevent review and rollback. Artifact: contract-test result, schema versions, and quality counters. Reasoning: quarantine or mark degraded evidence and restore the producer contract before judging detection quality. Boundary: absence, default values, and parser failures are not benign observations.

POLICY

4. Evidence is strong enough to review, not to punish

Trigger: several versioned signals agree on an unusual owned-lab journey. Artifact: feature lineage, reason codes, policy version, and expected guardrails. Reasoning: use mock data, default to proposal, separate approval from execution, grant least privilege, and test compensation for every effect. Boundary: preserve rollback and never infer that an offline score proves the causal benefit of an intervention.
