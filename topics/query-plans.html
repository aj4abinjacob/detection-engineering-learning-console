01 · Purpose

Performance changes need causal evidence

A slow detector may be scanning too much, joining with a poor cardinality estimate, sorting a large intermediate result, or waiting on something outside the plan. The plan shows the chosen relational work.

ESTIMATE

Rows drive choices

Bad cardinality can lead to bad join/access choice.

OPERATORS

Nodes compose

Read child work before parent output.

SAFETY

Analyze executes

It is not a read-only inspection for DML.

ITERATE

Change one premise

Verify result and plan after each hypothesis.

02 · Mental model

A plan tree creates rows bottom-up

Scan Read base relation rows.
→
Join/filter/sort Transform/intermediate rows.
→
Aggregate/output Return requested result.

PostgreSQL estimates cost/rows/width before execution. Actual rows, loops, and time are only available with ANALYZE; interpret them together, not as isolated numbers.

03 · PostgreSQL commands

-- Copyable psql lab: prepare a parameterized SELECT, then explain it.
PREPARE tenant_counts(text) AS
SELECT client_ip, count(*)
FROM events WHERE tenant_id = $1 GROUP BY client_ip;

-- Plans without executing the prepared SELECT.
EXPLAIN (COSTS, VERBOSE) EXECUTE tenant_counts('lab');

-- EXECUTES the prepared SELECT and reports actuals.
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) EXECUTE tenant_counts('lab');
DEALLOCATE tenant_counts;

Use: this PREPARE/EXECUTE form is directly usable in psql against a disposable schema; in application code, pass the equivalent value through the driver rather than interpolating it. Plain EXPLAIN is for estimate inspection; EXPLAIN ANALYZE only for authorized, controlled statements/data. Assumption: tenant_id is text; change the declared parameter type to the real schema type. Risk: ANALYZE executes any statement, including INSERT/UPDATE/DELETE. A transaction rollback can reduce persistent DML impact in a lab, but triggers, volatile functions, locks, external side effects, and resource consumption can still occur—do not use it as a production safety trick.

04 · Core nodes

Node Meaning Question
Seq Scan Read relation sequentially Is result fraction large enough that this is sensible?
Index Scan / Index Only Scan Use index path (latter needs visibility/map conditions) Are fetches/filter rows still high?
Bitmap scan Combine/build matching tuple locations Does many-row selectivity justify it?
Nested Loop Repeat inner work per outer row Are outer estimate/inner lookup reasonable?
Hash Join Build hash table, probe other input Does build side fit memory/work settings?
Sort/Aggregate Order/group intermediate rows Can input/order/cardinality be reduced?

05 · Compare estimates to actuals

For each costly node read estimated rows versus actual rows and loops; a large mismatch compounds through joins. Actual time includes this execution’s cache/concurrency conditions. With BUFFERS, inspect shared/local/temp reads/hits to reason about I/O, but do not invent metrics not shown in your plan. Statistics, correlated predicates, skew, stale data, parameter values, and expressions can cause estimation error.

06 · Safe diagnosis workflow

  1. Confirm semantics.Save query, parameters shape, result count, and expected time range.
  2. Read plain EXPLAIN bottom-up.Find scan, join, sort, and estimated row expansion.
  3. Hypothesize one cause.Example: tenant/time predicate is unselective or stats miss correlation.
  4. Use controlled ANALYZE.Only authorized SELECT/lab workload; capture actual rows/loops/buffers.
  5. Change one thing.Query shape, stats, or justified index; verify result equality and new plan.

07 · Safety

Plans can expose sensitive schema and literalsStore sanitized plan artifacts with query parameters redacted. Do not run expensive explain-analyze queries against a production incident system without authority, timeout/resource limits, and a rollback/impact plan. A plan is evidence, not permission to create an index.

08 · SQLite differs

-- SQLite-compatible local plan inspection; output is not PostgreSQL node syntax
EXPLAIN QUERY PLAN
SELECT client_ip FROM events WHERE tenant_id = 'lab';

SQLite EXPLAIN QUERY PLAN gives engine-specific high-level detail; it does not validate PostgreSQL EXPLAIN (ANALYZE, BUFFERS) syntax or node behavior. Label artifacts with engine/version and do not copy a SQLite plan conclusion to PostgreSQL untested.

09 · Detection scenarios

HUNT

Tenant query scans every event

Check selectivity and actual rows. A sequential scan may be correct; only a measured selective predicate supports an index hypothesis.

JOIN

Account-IP join explodes

Locate estimate mismatch and loops; inspect duplicate/cardinality assumptions before adding an index.

SORT

Top-N plan sorts a huge result

Reduce rows earlier or use an appropriate indexed/order-aware design; confirm tie/result semantics.

INCIDENT

Someone runs ANALYZE on a DELETE

It executes. Stop treating EXPLAIN ANALYZE as harmless; use plain EXPLAIN or a disposable copy.
