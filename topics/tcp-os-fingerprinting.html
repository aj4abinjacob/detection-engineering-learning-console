Detection stack · network layer

Fingerprint the TCP peer you actually observed.

TTL, MSS, window behavior, SACK, timestamps, and TCP option ordering may support a passive stack inference. They describe packets at a collector—not necessarily the end user behind a CDN, load balancer, NAT, VPN, proxy, tunnel, or terminating edge.

Why this matters

Passive TCP evidence can help cluster traffic, investigate a server-side anomaly, and explain why two observations disagree. Its value is greatest when raw packets, direction, collector placement, parser version, and likely intermediary are recorded. It cannot identify a person, reliably prove an operating system, or tell you who originated an application request without corroboration.

What a SYN can expose

The initial SYN is often the most useful passive packet because it advertises connection parameters before application data. A parser may compare values and option order with signatures. The values can be changed by stack versions, system configuration, middleboxes, capture loss, offload artifacts, and deliberate or normal implementation choices; an absence may mean “not observed,” not “not supported.”

TTL and hop effects

Each routed hop decrements IPv4 TTL (IPv6 has analogous Hop Limit). A received value is therefore a remaining budget, not the sender’s initial setting. Analysts sometimes estimate a distance by hypothesizing a common initial value higher than the observed value; this is an uncertain heuristic, not a measured path length. Routing changes, tunnels, containers, NAT, and an intermediary change the picture. Record the captured value and any assumption separately.

Read TCP options together

# Offline inspection of a supplied or learner-owned sanitized PCAP only.
tshark -r artifacts/tcp/owned-sanitized.pcapng \
  -Y 'tcp.flags.syn == 1 && tcp.flags.ack == 0' \
  -T fields -e frame.time_epoch -e ip.src -e ip.dst \
  -e ip.ttl -e tcp.options.mss_val -e tcp.window_size_value \
  -e tcp.options.wscale.shift -e tcp.options.sack_perm -e tcp.options.timestamp.tsval

This command reads an existing local file; it does not capture or probe a network. Field availability and names vary by Wireshark/TShark version and IPv6 uses ipv6.hlim rather than ip.ttl. Check your installed field reference, preserve the command/version, and never put a live interface or a third-party capture in the exercise.

p0f: passive classification with a narrow scope

p0f is a passive OS-fingerprinting project that matches observed traffic against signatures and reports an inference with qualifiers. It is not a scanner and should not be pointed at traffic you are not authorized to inspect. For this curriculum, use p0f only with an instructor-supplied sanitized capture or a capture from your own local/learner-owned AbuseGuard environment.

# Read a previously approved local capture; do not capture a live shared interface.
p0f -r artifacts/tcp/owned-sanitized.pcap

Save the p0f version, signature database/version, exact capture provenance, direction, and raw SYN properties. “Unknown” or a low-confidence/ambiguous result is useful evidence about limits; do not force a label. A tool result is an interpretation of its signature data, not an operating-system inventory.

Observation point, peer attribution, and proxies

At an origin behind a CDN or reverse proxy, the TCP peer may be the CDN/proxy, so the fingerprint commonly describes that edge’s TCP stack. At a load balancer or service-mesh hop, it may describe the local proxy. A source IP header can be application metadata forwarded by a trusted intermediary; it does not change which host sent the TCP packets to your collector. Keep network peer attribution and claimed/original-client metadata in different fields.

Required evidence statementEvery finding should say: “Collector X observed TCP peer Y; its SYN had properties Z; possible intermediaries are ….” Never collapse that into “the end user runs OS X” without direct, authorized endpoint corroboration.

User-Agent mismatch is evidence, not proof

A User-Agent is application-layer text supplied through the HTTP path; a TCP fingerprint is network-layer evidence from a particular peer at a particular collector. A mismatch may come from a CDN/proxy, browser update, app-embedded client, remote desktop, header manipulation, shared capture, or ordinary parser uncertainty. It can justify checking architecture and telemetry placement. It cannot prove a proxy, a particular OS, a forged header, or malicious intent.

Defensive evidence workflow

  1. Confirm lawful scope. Use supplied sanitized PCAP or local/learner-owned AbuseGuard traffic with a written capture provenance.
  2. Find the initial packet. Record five-tuple, direction, SYN/SYN-ACK status, time, capture loss caveat, and raw fields.
  3. Locate the collector. Diagram client, CDN, proxy/LB, and origin; name the direct TCP peer at the collector.
  4. Compare cautiously. Preserve parser/p0f versions and raw properties, then corroborate only with authorized server/application evidence.

Detection-engineering scenarios

1. Origin sees a stable stack across many “users”

Trigger: a p0f cluster is stable while application accounts vary. Artifact: origin-side SYN records and infrastructure diagram. Observation point: origin behind a CDN. Reasoning: the direct peer is likely the edge; use it to validate the architecture, not to cluster end users. False-positive boundary: do not call the accounts coordinated or claim they share an OS.

2. Received TTL changes during an incident

Trigger: a flow group has a different observed TTL range. Artifact: time-bounded SYN samples, routing/change timeline, and collector location. Observation point: authorized internal collector. Reasoning: investigate route, VPN, proxy, or topology changes before treating it as a new client platform. False-positive boundary: received TTL is not a measured hop count or identity signal.

3. User-Agent and p0f inference disagree

Trigger: HTTP claims one platform while p0f suggests another class. Artifact: redacted request metadata, p0f version/signature, SYN fields, and direct-peer record. Observation point: application edge. Reasoning: check whether the TCP connection terminates at an intermediary and whether the UA was forwarded/rewritten. False-positive boundary: mismatch alone proves neither spoofing nor proxy use.

4. New TCP-option pattern on a protected route

Trigger: an owned AbuseGuard lab shows a new ordered option pattern with elevated failed logins. Artifact: supplied/owned PCAP, normalized option sequence, server velocity, and policy version. Observation point: documented collector. Reasoning: use it as one cluster feature while investigating application behavior; assess how a legitimate OS/browser update changes the same feature. False-positive boundary: never block from option order alone or reuse a lab signature as a production identity rule.

Artifact-producing drills

1. SYN evidence table

From a supplied sanitized PCAP or learner-owned local capture, save artifacts/tcp/syn-evidence.csv with capture ID, observer, direct TCP peer, direction, TTL/Hop Limit, MSS, window, scale, SACK, timestamps, option order, and missing-field notes.

  • Separate observed value from every assumption.
  • Redact addresses/ports before sharing if required.

2. p0f reproducibility note

Run p0f only on that supplied/owned file and save artifacts/tcp/p0f-note.md with command, tool/signature version, result, raw supporting fields, confidence/unknowns, and provenance.

  • Include one ambiguous or unknown result if present.
  • Do not run p0f on a third-party or shared-network capture.

3. Peer-attribution diagram

Save artifacts/tcp/observer-peer-property.md for a direct client path and a CDN/proxy path. For each, write observer → TCP peer → inferred property → possible intermediary, then add a UA mismatch interpretation.

  • Explain why source headers do not alter TCP-peer attribution.
  • State why the mismatch is evidence rather than proof.
