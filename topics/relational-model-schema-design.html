SQL depth I · data contracts

Model the evidence so bad states cannot quietly enter.

A relational schema states entities, relationships, and invariants. For detection data, the hard part is separating an account, a request, and a rejected parse while retaining the links needed for trustworthy analysis.

01 · Purpose

Tables are claims about reality

A row is not automatically a fact. A good schema records which event was received, which account it references, and whether parsing succeeded. Constraints turn some assumptions into database-enforced checks instead of late dashboard surprises.

INTEGRITY

Keys prevent ambiguity

A primary key identifies a row; a foreign key says its referenced parent exists.

ANALYSIS

Grain controls counts

State whether a table row is one request, one account, or one rejected record before aggregating.

RECOVERY

Rejects are evidence

Keep parse failures separately rather than forcing malformed data into trusted columns.

SECURITY

Constraints reduce blast radius

They do not replace authorization or parameterized SQL, but prevent defined invalid states.

02 · Mental model

Choose a grain, then model relationships

accountsOne row per account identity.account_id
→
access_requestsOne row per accepted request.request_id
→
rejected_requestsOne row per rejected input.reject_id

An access request may reference an account, but anonymous requests have no account. That is a meaningful nullable relationship, not a reason to invent an “unknown” parent row.

03 · Identity

Primary keys, foreign keys, and referential integrity

A primary key (PK) is unique and non-null for each row. A foreign key (FK) references a PK/unique candidate key in another table; it stops an accepted request from pointing at an account that does not exist. Natural keys such as email can change and contain sensitive data; a surrogate integer/UUID PK can be safer operationally, with a separate unique constraint for a stable business identifier.

PRIMARY KEY

Declare the row identifier.Use a value that is stable for the table’s grain. It is not a human identity proof and must not be exposed as authorization by itself.

FOREIGN KEY (...) REFERENCES ...

Enforce parent existence.Use for owned relationships. It assumes enforcement is enabled/configured: SQLite requires PRAGMA foreign_keys = ON per connection; PostgreSQL enforces declared FKs by default.

UNIQUE

Prevent duplicate business values.Use for a declared identity such as canonical account handle. NULL behavior varies by DB: multiple NULLs are generally allowed because NULL is unknown.

04 · Invariants

Put simple truth at the data boundary

-- Synthetic lab schema; run only in a disposable SQLite database.
PRAGMA foreign_keys = ON;
CREATE TABLE accounts (
  account_id INTEGER PRIMARY KEY,
  handle TEXT NOT NULL UNIQUE,
  created_at TEXT NOT NULL
);
CREATE TABLE access_requests (
  request_id INTEGER PRIMARY KEY,
  observed_at TEXT NOT NULL,
  source_ip TEXT NOT NULL,
  status INTEGER NOT NULL CHECK (status BETWEEN 100 AND 599),
  path TEXT NOT NULL,
  account_id INTEGER REFERENCES accounts(account_id)
);
CREATE TABLE rejected_requests (
  reject_id INTEGER PRIMARY KEY,
  observed_at TEXT NOT NULL,
  reason TEXT NOT NULL,
  raw_excerpt TEXT NOT NULL CHECK (length(raw_excerpt) <= 256)
);

NOT NULL says absence is invalid, CHECK constrains a value, and UNIQUE constrains duplicates. Constraints do not validate every semantic rule: a syntactically valid IP may be spoofed, and a timestamp string needs application/DB-specific validation. Minimize sensitive raw excerpts and apply retention/access policy.

05 · Normal forms

Normalize to prevent update anomalies

First normal form (1NF) keeps atomic values—do not store a comma-separated account list in one column. Second normal form (2NF) removes dependence on only part of a composite key. Third normal form (3NF) removes transitive dependency: account handle belongs with the account, not copied into every request. Normalization reduces conflicting updates and makes source-of-truth ownership clear; it is a design tool, not a contest.

NULL is not false or emptySQL’s NULL means unknown/not applicable. Comparisons such as account_id = NULL yield unknown, not true; use IS NULL. Decide whether absence means anonymous, unavailable telemetry, or a parser failure before encoding it.

06 · Deliberate redundancy

Denormalize only with a written synchronization story

A daily aggregate table or materialized view can make a repeated dashboard query economical, but copies introduce staleness and backfill rules. Store the source event first; document the refresh owner, watermark, key, retention, and how corrections propagate. PostgreSQL has materialized views; SQLite does not provide the same built-in feature, so an aggregate table needs explicit refresh code. Do not duplicate PII merely to avoid a join.

07 · Load controlled data

Use a small fixture to validate the model

INSERT INTO accounts(account_id, handle, created_at)
VALUES (1, 'lab-alex', '2026-01-01T00:00:00Z');
INSERT INTO access_requests(observed_at, source_ip, status, path, account_id)
VALUES ('2026-01-01T00:01:00Z', '198.51.100.8', 401, '/login', 1),
       ('2026-01-01T00:02:00Z', '198.51.100.9', 200, '/home', NULL);
INSERT INTO rejected_requests(observed_at, reason, raw_excerpt)
VALUES ('2026-01-01T00:03:00Z', 'bad_status', 'synthetic|not-a-status');

Use only a temporary database or local synthetic data. DDL and INSERT statements mutate state; they are examples to understand, not commands for an unknown production database. PostgreSQL supports richer types such as timestamptz and inet; SQLite uses flexible storage classes, so application contracts matter more.

09 · On the job

Detection-engineering scenarios

QUALITY

Parser change lowers accepted event count

Store rejected records with a reason and bounded synthetic-safe excerpt. A drop in accepted requests can then be reconciled against rejection counts instead of silently disappearing.

ATTRIBUTION

Anonymous burst is falsely assigned to one account

Model the account relationship as nullable and preserve source IP/request grain. An “unknown account” row would make joins and aggregates look like confirmed identity.

BACKFILL

New enrichment field conflicts with old copies

Keep source-of-truth attributes normalized; introduce a derived aggregate only with refresh/version provenance and a backfill plan.

INTEGRITY

Requests reference deleted accounts

An FK forces a deliberate lifecycle choice: restrict deletion, retain/tombstone account rows, or use a documented cascading action. Never let an ORM’s default imply the policy.

10 · Practice

Hands-on drills

1. Design the three-table evidence model

40 min

Save artifacts/schema/schema.sql and grain.md for accounts, accepted access requests, and rejected requests.

  • Label each table’s row grain, PK, FK, nullable fields, and constraints.
  • Explain why rejected input is not placed in the accepted-request table.
  • Use only synthetic handles and documentation IP ranges.

2. Prove constraints

25 min

Save constraint-transcript.txt showing a valid insert plus rejected duplicate, invalid status, and missing-parent attempts in a disposable SQLite database.

  • Enable and verify SQLite foreign keys.
  • State the constraint responsible for each rejection.
  • Show the table remains in the expected state after each failed statement.

3. Write a normalization tradeoff note

25 min

Save normalization.md describing a 1NF/2NF/3NF correction and one proposed daily aggregate.

  • Name the update anomaly avoided.
  • State aggregate owner, refresh/watermark, and staleness risk.
  • Identify any sensitive fields excluded from the copy.
