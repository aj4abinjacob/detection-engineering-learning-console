Practical field guide · HTTP metadata

Headers describe context; they do not prove identity.

Cookie scope, cache policy, validators, and forwarding headers are security boundaries. Treat the values as evidence with a source and trust chain.

01 · Purpose

Metadata changes what users receive

The same route can have different cache, representation, session, and client-origin behavior based on headers. A detection event must preserve the normalized decision—not an unsafe raw header dump.

02 · Header basics

HTTP field names are case-insensitive. HTTP/2 requires lowercase field names on the wire; HTTP/1.x casing/order can vary by client, library, proxy, and normalization. Ordering/casing are implementation metadata that may be useful as low-confidence telemetry in a known observation point, never a stable client identity or authorization signal. Request headers describe preferences/context; response headers control representation/caching; representation headers describe content.

03 · Cookies are scoped browser state

Set-Cookie: __Host-session=opaque; Path=/; Secure; HttpOnly; SameSite=Lax
Cache-Control: private, no-store

Domain broadens host matching; absent Domain is host-only. Path limits path matching but is not an authorization boundary. Secure limits transmission to secure contexts (with local-development caveats), HttpOnly blocks normal JavaScript access but not request attachment, and SameSite controls cross-site sending context—not all CSRF defense. Cookie prefixes such as __Host- and __Secure- have user-agent-enforced attribute requirements; test supported browsers and do not assume every nonbrowser client enforces them.

04 · Cache policy

Cache-Control: max-age=60 allows freshness reuse; no-cache means revalidate before reuse, not “do not store”; no-store asks caches not to store. private restricts shared caches; public permits them subject to other directives. Directives are protocol controls, not a substitute for avoiding sensitive data in URLs/responses.

05 · Validators and conditional requests

ETag: "rules-v17"
If-None-Match: "rules-v17"
-- response: 304 Not Modified, no representation content

Use: validators to avoid transferring unchanged representations. Assumption: ETag generation represents the intended version and intermediary behavior. Risk: validators can reveal/cache user-specific state if response policy/keying is wrong; record validator decisions carefully.

06 · Cache key variation

Vary: Accept-Encoding says responses differ by that request field. Omitting a material selector risks serving the wrong representation; varying on high-cardinality/untrusted headers destroys cache efficiency and can create inconsistent behavior. Shared caches must not reuse authenticated/personalized responses unless policy and keying explicitly make that safe.

07 · X-Forwarded-For is only trusted through a chain

# Policy example, not a universal parser:
# accept client IP from X-Forwarded-For only when socket peer is an allowlisted proxy;
# the proxy must strip incoming X-Forwarded-For and append/set its own value.

Use: derive client identity at a known edge/proxy boundary. Risk: a direct client can send X-Forwarded-For; blindly trusting first/last comma-separated value enables spoofed attribution. Header conventions and standardized Forwarded support vary across proxies; document exact chain/configuration.

08 · Safe observability

Record cache decision (hit/miss/revalidated), normalized cookie presence/attributes—not values—trusted proxy decision, route, status, and bounded selected headers. Hash/pseudonymize where policy requires, but remember a hash is still linkable data. Never log session cookies, authorization fields, or full forwarding chains into broadly accessible logs.

09 · Safety

Do not identify clients from header styleBrowsers, SDKs, proxies, and protocol conversion rewrite header order/case. Use authenticated/account/device signals and explicit trusted network provenance; treat header patterns as investigatory context with false-positive testing.

10 · Detection scenarios

LEAK

Authenticated response cached publicly

Inspect Cache-Control, Vary/keying, auth state, and CDN policy; treat it as a confidentiality incident, not merely a cache miss.

ATTRIBUTION

IP reputation alert uses spoofed XFF

Verify socket peer/proxy allowlist and proxy strip/append behavior before using forwarded client value.

SESSION

Cross-site session behavior changes

Review SameSite, Secure, browser/version behavior, and CSRF controls; a cookie attribute alone does not prove exploitability or safety.

CACHE

Hit rate collapses after Vary change

Check whether a high-cardinality header entered the cache key and whether response representation truly varies.
