Practical field guide · Git safety

Recover deliberately. Destroy nothing by reflex.

Git has separate layers for files, staged content, branch names, and shared history. Identify the layer that is wrong before changing anything; the right recovery is often a read-only inspection followed by one small, reversible move.

01 · Purpose

Why recovery is a production skill

A rushed “undo” can erase uncommitted investigation notes, hide a flawed rule change, or overwrite a teammate’s history. Good recovery preserves evidence first, diagnoses the state second, and chooses the narrowest operation that fixes it.

INCIDENTS

Undo with an audit trail

A bad shared rule is usually reverted, not erased, so responders can see both the mistake and its correction.

FORENSICS

Keep local evidence intact

Working-tree and staging recovery can separate accidental edits from committed, reviewable snapshots.

RELIABILITY

Know what a command rewrites

Reset changes different layers depending on mode; --hard replaces tracked files as well as moving a branch.

COLLABORATION

Do not rewrite another person’s base

Remote histories are shared state. Prefer an additive revert and use force-with-lease only for owned, coordinated branches.

First principleStop, run git status, and preserve a name for anything valuable before experimenting. Git recovery is easiest while objects are still reachable by a branch, tag, stash, or reflog entry.

02 · Mental model

Ask which layer changed—and which history is shared

Working treeFiles on disk. Unstaged edits live here.git diff
→
IndexExact next-commit content. Staged edits live here.git diff --staged
→
Branch / HEADNames the committed snapshot you have checked out.git log -1

A recovery command may affect one, two, or all three layers. Remote history is a separate concern: a local branch move does not change a server until you push it.

Before actingQuestion it answersWhy it is safe
git statusIs there an operation in progress? What is modified, staged, or untracked?Read-only state report.
git diff / git diff --stagedWhat exact content would be discarded or committed?Read-only comparison.
git log --oneline --graph --decorate --allWhere do branch and remote-tracking refs point?Read-only graph view.
git show <rev>Is this the commit/file I want before restoring it?Read-only object inspection.
Untracked is a different riskgit reset --hard removes changes to tracked files, but normally leaves untracked files. git clean targets untracked files; it can delete ignored files with -x. Never treat either as routine cleanup.

03 · Local safety journal

Reflog records recent ref movements—locally and temporarily

The reflog answers “where did this local ref used to point?” It records updates caused by commits, resets, rebases, checkouts, and other ref changes. It is frequently how you find a commit after moving or deleting a local branch.

git reflog --date=local
git reflog show main
git show HEAD@{1}                  # inspect, do not restore blindly
git branch recovered-work <sha>     # give the found commit a durable name
git switch recovered-work
git reflog

List HEAD’s local movement journal.Use after an accidental reset, rebase, or branch deletion. It assumes the relevant local reflog entry has not expired or been pruned; it neither queries nor repairs a remote.

git branch recovered-work <sha>

Protect a found commit without changing files.Use immediately after verifying git show. It creates a local branch ref, making the commit reachable through normal history again.

git fsck --no-reflogs --unreachable

Inspect unreachable objects as a last resort.Use only in a disposable or carefully backed-up repository when reflog is insufficient. Output can include sensitive historical content; it does not guarantee recovery after pruning.

Reflogs are not pushed or cloned as collaboration data. Their entries expire and objects that are no longer reachable may later be pruned by Git maintenance. Default expiry behavior is configurable and can vary: Git commonly expires reachable reflog entries after 90 days and unreachable ones after 30 days, but configuration, manual expiration, garbage collection, and hosting providers change the outcome. Recover and name important work now; do not rely on a time window as a backup policy.

Locality and exposureA reflog can reveal prior commit IDs and messages locally, including work that was later rewritten. Do not paste its full output into tickets if it exposes branch names, paths, or sensitive context. A remote provider’s web history is not your local reflog.

04 · Move layers precisely

Reset matrix: same target, different treatment of files and index

git reset <target> moves the current branch/HEAD reference. The mode determines how far Git also updates the index and working tree. All three modes can make commits disappear from the current branch; check reflog if the move was mistaken.

ModeBranch / HEADIndexWorking treeUse and risk
--softMoves to targetKept as it wasKept as it wasUndo an unpushed commit while keeping its whole snapshot staged. Rewrites local history.
--mixed (default)Moves to targetReset to targetKept as it wasUndo an unpushed commit while keeping its content as unstaged edits. Rewrites local history.
--hardMoves to targetReset to targetTracked files replaced by targetDestructive: discards staged and unstaged tracked edits. It can also delete untracked obstructions in the way of writing tracked files.
# First inspect the target and preserve any important state.
git status
git show --stat HEAD~1
git branch safety-before-reset HEAD

git reset --soft HEAD~1    # keep former commit staged
# git reset --mixed HEAD~1 # keep former commit as unstaged edits (default mode)
# git reset --hard HEAD~1  # only in a disposable repo or after verified backup

git reset --mixed <path> has a different, path-limited form: it resets index entries for those paths without moving HEAD (modern spelling: git restore --staged <path>). Avoid generalizing a path reset into the whole-history reset matrix.

05 · File-level recovery

Use restore/switch for one clear job; understand legacy checkout

IntentModern commandLegacy equivalent / consequence
Discard unstaged edits to one tracked pathgit restore pathgit checkout -- path. Both replace the working file from index by default—destructive to those edits.
Unstage a path but keep its working editsgit restore --staged pathgit reset HEAD -- path. Changes index only.
Restore a file from a specific commitgit restore --source=<rev> -- pathgit checkout <rev> -- path. Writes the chosen historical content into working tree and index; inspect first.
Change branch / inspect commitgit switch branch / git switch --detach revgit checkout branch / git checkout rev. Legacy checkout overloads branch switching and path restoration.
git diff -- rules/login.yml
git restore rules/login.yml                 # destroys only unstaged edits to that tracked file
git restore --staged rules/login.yml        # unstage; retain working-tree edits
git show HEAD~1:rules/login.yml             # inspect prior content first
git restore --source=HEAD~1 -- rules/login.yml
git diff --staged && git diff

git restore and git switch arrived in Git 2.23 (2019). On older Git, use the corresponding git checkout form, and include -- before a path to disambiguate it from a branch name. Neither tool makes a remote backup; restore can overwrite local edits, and switch can be blocked by edits that would be overwritten.

06 · Pointer state

Detached HEAD: inspect freely, name new work before leaving

Normally, HEAD symbolically points to a branch, and commits advance that branch. In detached HEAD, it points directly to a commit. You can inspect, build, and even commit; new commits simply lack a branch name that will keep them conveniently reachable after you move away.

Attached: HEAD → main → C Detached: HEAD → B main → C New detached commit: HEAD → D (no branch names D yet)
git switch --detach HEAD~1        # inspect an older snapshot
git status
# If you make a useful commit while detached:
git switch -c preserve-investigation-note
# If you only inspected, leave safely:
git switch main
Do not panic; do name thingsDetached HEAD is not damage. The risk starts when you create a commit, switch away, and later cannot remember its ID. Create a branch (or tag) before leaving. If you already left, inspect git reflog and create a branch at the commit you find.

07 · Shared-history choice

Revert adds an inverse commit; reset moves a ref backward

SituationPreferWhy
A reviewed/pushed commit caused a bad deploymentgit revert <sha>Adds a new inverse change, preserving shared history and an audit trail. It can conflict if later changes touch the same content.
You want to revise your last unpushed local commitgit reset --soft HEAD~1 or git commit --amendRewrites only your own local history; select mode based on whether content should stay staged.
An owned feature branch was pushed then rebasedCoordinate, then git push --force-with-leaseRemote ref must be updated to rewritten commits. The lease rejects if remote changed since last observation.
# Shared branch: inspect, then create an auditable inverse commit.
git show --stat <bad-sha>
git revert <bad-sha>
git push origin main

# A merge commit has multiple parents; choose which parent is the mainline.
# Do not run blindly: git revert -m 1 <merge-sha>

git revert changes your working tree and creates a new commit after conflict resolution if necessary. It does not erase the original. Reverting a merge needs -m <parent-number> to say which parent is the mainline; inspect the merge first with git show --no-patch --pretty=raw <merge-sha> and follow your team’s release process.

08 · Field decisions

Four recovery scenarios

UNSTAGED NOTE

You accidentally overwrite a working rule edit

Before “fixing” anything, compare git diff and check whether the desired version is in a prior commit. If the edit was never staged or committed and was replaced by restore/reset, Git may not have an object to recover. This is why you inspect and make small commits; use backups/editor history for untracked work.

BAD DEPLOYMENT

A shared detection release increases false positives

Find the specific merged commit, inspect it, and use git revert through the approved release path. The inverse commit documents the operational choice and does not force teammates to repair rewritten history. Validate the reverted rule bundle before publishing.

LOST LOCAL COMMIT

An experiment disappears after reset

Stop rewriting. Use git reflog to locate the old tip, inspect it with git show, and create recovered-work at that ID. Reflog locality means a coworker’s clone cannot be assumed to have this journal or its object.

DIRTY BRANCH SWITCH

A responder needs last week’s parser snapshot

Do not use legacy checkout with a path accidentally. First status/diff and commit or stash your relevant work, then git switch --detach <known-sha> to inspect. Create a branch only if the investigation produces a new commit worth retaining.

09 · Boundaries

Destructive commands, retention limits, and Windows notes

RESET --HARD

Tracked edits can be unrecoverable

It resets branch, index, and tracked files. It does not mean “clean my repo safely.” Name a safety branch or make an external copy before a high-risk operation.

GIT CLEAN

Untracked is not protected

git clean -n previews; git clean -f deletes untracked files; -x includes ignored files such as local configuration. Treat all deletion variants as destructive.

FORCE PUSH

Remote rewrite affects others

Never use bare --force on a collaborative branch. Confirm ownership, fetch, communicate, and prefer --force-with-lease.

SENSITIVE DATA

Deletion is not secrecy

Rewritten or reverted commits can persist in clones, caches, reviews, and reflogs. Rotate an exposed secret and follow the incident process.

git clean -nfd        # preview untracked files/directories only
# git clean -fd       # DESTRUCTIVE: delete precisely what preview showed
# git clean -xfd      # MORE DESTRUCTIVE: also delete ignored files
git version
git init -b main      # requires Git 2.28+; older: git init then git branch -M main
Platform detailsExamples use POSIX printf and /tmp/detection-git-recovery-1-8. In Windows PowerShell use the explicit disposable path C:\Temp\detection-git-recovery-1-8, New-Item -ItemType Directory C:\Temp\detection-git-recovery-1-8, and Set-Content -NoNewline file 'text'. Git’s repository semantics are cross-platform, but case-insensitive default filesystems and line-ending settings can create surprises; use a project .gitattributes policy and do not resolve a conflict by changing every line ending.

10 · Practice

Five safe recovery drills

Perform all five in the exact disposable path /tmp/detection-git-recovery-1-8 (macOS/Linux) or C:\Temp\detection-git-recovery-1-8 (Windows PowerShell). These commands intentionally make recoverable mistakes. Save the stated artifacts and explain why each recovery affects the layer it does.

1. Restore a changed tracked file and unstage without losing it

15 min
mkdir /tmp/detection-git-recovery-1-8
cd /tmp/detection-git-recovery-1-8
git init -b main
git config user.name "Drill User"
git config user.email "drill@example.invalid"
printf 'threshold: 5\n' > rule.yml
git add rule.yml && git commit -m "Baseline"
printf 'threshold: 9\n' > rule.yml
git add rule.yml
git restore --staged rule.yml
git diff | tee drill-1-unstaged.txt
git restore rule.yml
git status | tee drill-1-final-status.txt
  • Show that restore --staged changed index state but left threshold: 9 in the working tree.
  • Explain why the second restore discarded that tracked edit and why it did not move HEAD.
  • State what extra recovery source you would need if the discarded content had never been committed or staged.

2. Compare soft, mixed, and hard reset in isolated branches

25 min
git switch -c reset-lab
printf 'threshold: 10\n' > rule.yml && git commit -am "Commit ten"
git reset --soft HEAD~1
git status --short | tee drill-2-soft.txt
git reset --hard HEAD
printf 'threshold: 10\n' > rule.yml && git commit -am "Commit ten again"
git reset --mixed HEAD~1
git status --short | tee drill-2-mixed.txt
git add rule.yml && git commit -m "Commit ten a third time"
git branch safety-before-hard HEAD
git reset --hard HEAD~1
git status --short | tee drill-2-hard.txt
git show safety-before-hard:rule.yml
  • For each artifact, identify whether the change is staged, unstaged, or absent from the working file.
  • Explain why all modes moved the branch but only hard replaced the tracked file.
  • Explain how safety-before-hard preserved a name for the deliberately discarded commit.

3. Lose a branch tip, recover it through reflog

15 min
git switch main
git switch -c disposable-spike
printf 'experiment: true\n' > spike.yml
git add spike.yml && git commit -m "Try spike"
git switch main
git branch -D disposable-spike
git reflog --date=local | tee drill-3-reflog.txt
git show <lost-sha>
git branch recovered-spike <lost-sha>
git log --oneline --decorate --all | tee drill-3-recovered-graph.txt
  • Show the reflog entry that named the lost tip and the new recovered-spike ref.
  • Explain why a deleted branch did not immediately delete its commit object.
  • State why the result would not be guaranteed after reflog expiry/pruning or in another clone.

4. Enter detached HEAD, create work, and preserve it

15 min
git switch main
git switch --detach HEAD
printf 'note: detached investigation\n' > note.yml
git add note.yml && git commit -m "Detached investigation note"
git status | tee drill-4-detached-status.txt
git switch -c preserved-detached-note
git log --oneline --decorate -3 | tee drill-4-preserved.txt
git switch main
  • Explain what HEAD named before creating preserved-detached-note.
  • Show that the new branch makes the detached commit reachable through a normal ref.
  • Explain the safe difference between inspection-only detached HEAD and committing there.

5. Revert a shared-style mistake rather than reset it away

15 min
git switch main
printf 'enabled: false\n' > rule.yml
git add rule.yml && git commit -m "Accidentally disable rule"
bad_sha=$(git rev-parse HEAD)
git revert "$bad_sha"
git log --oneline -3 | tee drill-5-revert-log.txt
git show --stat HEAD
cat rule.yml
  • Show both the bad commit and the later inverse commit in the log; explain why neither was erased.
  • Explain why reset would be riskier if the bad commit were already pushed and used by teammates.
  • State what you would inspect before reverting a merge commit and why -m is required.
