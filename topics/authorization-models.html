Authorize every object at the server boundary.

RBAC and tenant isolation define permitted actions. Authentication never grants object access by itself; deny by default and test every cross-tenant boundary.

Why it matters

Broken access control happens when a server accepts an identifier without proving the principal may act on that object in that tenant.

Models are policy tools

RBAC maps roles to actions; ABAC uses attributes; relationship/object models express ownership/sharing. Choose the smallest clear policy and enforce it server-side.

RBAC

Roles such as viewer/analyst/admin should grant named actions, not broad UI visibility. Roles change; evaluate current roles and avoid client-supplied role claims as sole evidence.

Tenant isolation

Every tenant-scoped query/filter must include tenant scope derived from authenticated server state. Compound keys, row-level policy, repository methods, and tests can reinforce the boundary.

Object authorization

def may_read_report(principal, report):
    same_tenant = report.tenant_id == principal.tenant_id
    allowed_role = principal.role in {"analyst", "admin"}
    return same_tenant and allowed_role

report = repository.get_report_for_tenant(
    tenant_id=principal.tenant_id,
    report_id=report_id,
)
if report is None or not may_read_report(principal, report):
    raise PermissionError("not found")

Scope retrieval by a trusted tenant identifier as well as checking policy; this reduces the chance that sensitive cross-tenant data is loaded before denial. Check read, update, delete, export, and indirect references. Returning 404 versus 403 is a consistent disclosure-policy choice; do not leak object details in error text.

Deny by default

New routes/actions need an explicit allow policy. Default deny is safer than a fallback role; UI hiding is not enforcement.

IDOR and broken access control

Changing an object ID in a request must not cross ownership/tenant boundaries. Opaque IDs reduce guessing but do not replace authorization checks.

Authorization tests

def test_report_cannot_cross_tenants(client, tenant_a_user, tenant_b_report):
    response = client.get(
        f"/reports/{tenant_b_report.id}",
        cookies=synthetic_session_for(tenant_a_user),
    )
    assert response.status_code in {403, 404}
    assert tenant_b_report.title not in response.text

Use two synthetic tenants and multiple roles. Test allowed owner/role; same-role other tenant; same-tenant wrong role; missing/stale identity; guessed/nonexistent identifier; and mutation, export, and background execution—not just reads. Run at route/service and tenant-scoped repository layers where appropriate.

Safety

Use local synthetic objects only. Avoid demonstration against real apps/accounts. Log safe policy decision IDs, not sensitive resource contents or authorization tokens.

Defensive scenarios

IDOR report route

A synthetic tenant-A principal requests a known tenant-B report ID and gets 200. Trace the route parameter into the repository query, record pseudonymous principal/tenant, object tenant, action, policy decision, and response status, then prove a tenant-scoped lookup denies without rendering content. Sequential-looking IDs may trigger investigation, but identifier shape is not proof of exploitation.

Admin UI hidden

A route-access dashboard shows viewer sessions reaching an admin endpoint that the frontend hides. Inspect current server-side roles, route template, authorization decision ID, deployment version, and direct synthetic requests. A hidden control explains UI intent only; the finding closes when the server denies the action and regression tests cover every method.

Export background job

An export was authorized when queued but runs after the user's role or tenant membership changed. Preserve enqueue/execution times, immutable job owner/tenant/action, policy version, and result location; re-resolve current authority at execution and before download. Queue delay is a legitimate operational condition, not permission to trust stale client claims.

Role change mid-session

A removed analyst continues reading reports through an otherwise valid session. Compare session issuance with server-side role-change time and policy evaluation events, then test revocation/role refresh behavior. The session can still prove identity while its cached authorization is stale; rotate or invalidate according to the documented risk window.
