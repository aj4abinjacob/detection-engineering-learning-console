Python internals II · evidence-led diagnosis

Find the actual failing frame and the actual hot path.

01 · Purpose

Diagnosis is a chain of evidence, not a tool ritual

A detection engineer has to separate a bad event, parser defect, configuration mismatch, and throughput regression. The goal is a minimal reproducible case, a localized cause, a tested correction, and an artifact another person can inspect without copying sensitive production data.

TRACEBACK

Find the failing operation

The last lines name the exception and source location; callers above show how the state arrived there.

DEBUGGER

Inspect one controlled state

A breakpoint answers a specific question inside a reproduced failure, not every question about production.

PROFILE

Measure before optimizing

Call counts and cumulative time reveal where to form a performance hypothesis.

SAFETY

Artifacts can be sensitive

Tracebacks, locals, command lines, and profiles can contain paths, queries, identifiers, and secrets.

02 · Mental model

Reproduce → localize → change one cause → prove the result

ReproduceSmall synthetic input and exact command.fixture + transcript
→
ObserveTraceback, debugger, or profile supports a hypothesis.evidence
→
VerifyRegression test and before/after measurement.proof

Do not start by changing several lines, adding retries, or optimizing a familiar function. That destroys the causal evidence needed to know whether the correction worked.

03 · Exceptions

Read a traceback bottom-up, then walk the call chain

Traceback (most recent call last):
  File "analyzer/cli.py", line 31, in main
    print(render(read_status(path)))
  File "analyzer/parser.py", line 18, in read_status
    return int(fields[2])
ValueError: invalid literal for int() with base 10: 'two-oh-oh'

Start with ValueError: what operation failed, with what input, at which source line? Then move upward: which caller supplied that input, and what boundary should have validated it? The topmost frame is often an entry point, not the bug. A chained exception (raise NewError(...) from exc) adds causal context; inspect both exceptions rather than discarding the original.

python -m analyzer.cli sample.log

Run through the same module entry point used by the application.Use it to preserve imports and argument handling. It assumes the active environment is correct; record Python version and working directory in a reproduction transcript.

python -X faulthandler -m analyzer.cli sample.log

Enable low-level fault traceback help.Use for authorized local investigation of crashes/hangs. It is not a substitute for application error handling and output may disclose paths or current stacks.

traceback.print_exc()

Emit the current exception traceback in an exception handler.Use only at a controlled error boundary. Avoid printing raw locals or request data; logging an exception also needs redaction/retention policy.

04 · Establish a case

Make the smallest honest reproduction

# artifacts/debug/bad.log — synthetic, no production identifiers
2026-01-01T00:00:00Z|198.51.100.8|two-oh-oh

# artifacts/debug/reproduce.txt
python --version
python -m analyzer.cli artifacts/debug/bad.log
# Capture exit code and the relevant traceback, after redaction review.

Record input format, exact command, version, expected behavior, actual behavior, and whether the failure is deterministic. Reduce by removing irrelevant records while retaining the failure. Do not upload a raw customer payload or production core dump merely to make a reproduction convenient.

05 · Interactive inspection

Use breakpoint() to answer a question

def parse_status(raw: str) -> int:
    cleaned = raw.strip()
    breakpoint()  # inspect cleaned only in a controlled local run
    return int(cleaned)

# Or start under the debugger:
python -m pdb -m analyzer.cli artifacts/debug/bad.log
pdb commandMeaningUse carefully
lList nearby source.Confirm where execution is paused.
p expressionEvaluate/print an expression.Expressions can call methods or mutate state; keep inspection side-effect free.
pp expressionPretty-print an expression.Do not pretty-print unbounded/sensitive records.
n / sNext line / step into call.Use s only when the callee is relevant; avoid wandering.
cContinue to next breakpoint/exit.May process more input; use bounded synthetic fixtures.
qQuit debugger.Stops the program; record whether cleanup needs verification.

breakpoint() honors PYTHONBREAKPOINT; it can be disabled or redirected by environment. Python 3.7+ includes it, while behavior/configuration can differ in IDEs. On Windows, terminal launching and path display differ, but python -m pdb works with the active interpreter.

06 · Deterministic profiling

cProfile records calls and timing overhead

# Deterministic profiler: collect a saved artifact
python -m cProfile -o artifacts/profile/before.prof -m analyzer.cli artifacts/profile/events.log

# Read sorted statistics
python -m pstats artifacts/profile/before.prof
# At the pstats prompt: sort cumulative ; stats 20

cProfile instruments function calls, so it is useful for a bounded reproducible workload. tottime is time in a function excluding callees; cumtime includes calls below it and often exposes expensive orchestration. Call count distinguishes “slow once” from “cheap but repeated.” Profiling adds overhead and can distort microbenchmarks, I/O timing, asynchronous scheduling, native code, and contention; it is not a wall-clock capacity test.

07 · Form a performance hypothesis

Read cumulative time before optimizing leaf functions

from collections import Counter

def slow_top_ips(lines: list[str]) -> list[tuple[str, int]]:
    # Deliberate regression: recount the whole input for every distinct address.
    ips = [line.split("|", 2)[1] for line in lines]
    return sorted(((ip, ips.count(ip)) for ip in set(ips)), key=lambda item: item[1], reverse=True)

def top_ips(lines: list[str]) -> list[tuple[str, int]]:
    return Counter(line.split("|", 2)[1] for line in lines).most_common()

First verify both implementations have the same defined behavior on a fixture. Then profile a fixed input size, save before/after reports, and compare total time, relevant call counts, and cumulative time. Do not claim a speedup from one noisy run or optimize away validation that protects the parser.

08 · Failure modes & safety

Debug output is not harmless

FailureWhy it happensResponse
Fixes wrong frameTraceback read top-down or symptoms mistaken for cause.Start at final exception; trace input/callers upward; add a regression test.
Debugger changes behaviorTiming, evaluation side effects, or breakpoint environment differs.Use a minimal reproduction and inspect simple expressions; verify outside pdb.
Profile “optimization” regresses correctnessOnly timing measured, not output equivalence.Run behavior tests before/after and preserve safety limits.
Profiler output leaks dataPaths, function names, command args, or generated labels are shared.Sanitize artifacts and restrict access/retention; profile synthetic data where possible.
Nonrepresentative conclusionTiny fixture or cold-cache single run.State workload, repetitions, machine, Python version, and limits.

09 · On the job

Detection-engineering scenarios

PARSER

A format variant crashes a batch

Save a redacted one-line fixture, read the final traceback frame, then use pdb to inspect only the parsed fields. Fix the input contract or rejection behavior and pin it with a test.

PERF

Top-source report slows as log volume grows

Reproduce with synthetic scale data and cProfile. A growing list-count pattern may show high cumulative time; replace it with a one-pass Counter only after output-equivalence tests pass.

INCIDENT

Intermittent worker crash has a sensitive traceback

Capture the exception type, safe request/run IDs, deploy version, and bounded stack metadata through approved logging. Do not turn on raw local-variable dumps in a shared production sink.

REGRESSION

“Performance fix” changes alert order

Clarify whether order is contractual, then test it alongside count results. A profiler identifies cost, not which output differences are acceptable to downstream analysts.

10 · Practice

Hands-on drills

1. Seed and diagnose one parser bug

35 min

Save artifacts/debug/bad.log, reproduce.txt, traceback-notes.md, and a regression test. Use only synthetic records.

  • Read the traceback from exception upward.
  • State the violated input contract and the correct error behavior.
  • Show the regression test failing before and passing after the correction.

2. Interrogate a controlled breakpoint

25 min

Save pdb_transcript.txt showing l, a side-effect-free p, n or s, and c or q.

  • Write the question each debugger command answered.
  • Remove the breakpoint before final run.
  • Review transcript for secrets, customer data, and local sensitive paths.

3. Seed and measure a perf regression

40 min

Save synthetic input, before.prof, after.prof, profile-notes.md, and equivalence tests for the slow/fixed implementations.

  • Compare call counts plus cumulative time, not one number alone.
  • State Python version, input size, and run conditions.
  • Explain why profiler results do not prove production capacity.
