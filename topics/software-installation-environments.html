Practical field guide · Environments

Make the runtime reproducible.

The code is only half the system. Interpreter choice, native libraries, package versions, PATH, and configuration determine what actually runs—and whether another engineer can reproduce it safely.

01 · Purpose

Why environments matter in detection work

01 · REPRODUCIBILITY

The same commit should mean the same behavior

Pinning and recording dependencies separates a code change from a silent library or interpreter change.

02 · ISOLATION

Projects need independent constraints

A parser requiring one library version should not change the runtime of an unrelated collector.

03 · RESPONSE

Tools must be deployable under pressure

A documented environment can be rebuilt on a clean host instead of relying on one analyst's laptop.

04 · SUPPLY CHAIN

Dependencies execute trusted code

Package names, versions, indexes, build steps, and hashes are security decisions—not setup trivia.

The useful definitionAn environment is the complete runtime context: interpreter, installed packages, native libraries, executable search path, environment variables, working directory, and platform. A Python virtual environment isolates the interpreter-facing Python packages and scripts for one project; it is not a container or OS sandbox.

03 · Isolation

What a virtual environment changes

A venv is a directory containing configuration, a Python executable (often linked to a base interpreter), an isolated site-packages directory, and console-script entry points.

python3 -m venv .venv

# POSIX shells:
source .venv/bin/activate

# Inspect the selected runtime:
command -v python
python -c 'import sys; print(sys.executable); print(sys.prefix); print(sys.base_prefix)'

Activation is a convenience, not magic

The activation script modifies the current shell—primarily by prepending the venv's executable directory to PATH, setting VIRTUAL_ENV, and changing the prompt. It does not start a new shell, container, or security boundary.

Before activationAfter activationWhy
python resolves through normal PATHpython resolves to .venv/bin/pythonThe venv bin directory is prepended to PATH.
pip may be system/user pippip normally resolves inside venvThe venv installs its console scripts in that same bin directory.

Base site-packages rulesVenv site-packages used by defaultpyvenv.cfg controls base-package visibility.
 
# Activation is optional; explicit paths are excellent in automation
.venv/bin/python analyzer.py
.venv/bin/python -m pytest
.venv/bin/python -m pip list

# Leave the activated environment
deactivate
A venv is not portable as a directoryIt records paths and contains generated scripts. Rebuild it from a dependency specification on the target system rather than copying or committing .venv/.

04 · Core working set

A reliable daily workflow

python3 --version
python3 -m venv .venv
source .venv/bin/activate

python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python -m pip check
python -m pytest
python -m pip ...

Bind pip to the selected Python.Safer than assuming a bare pip belongs to the interpreter you intend.

python -m pip list

List installed distributions.Useful for orientation, not by itself a curated dependency specification.

python -m pip show package

Inspect version and install location.Confirms which environment supplies a distribution.

python -m pip check

Check declared dependency compatibility.It does not prove runtime behavior or supply-chain trust.

python -c 'import pkg; print(pkg.__file__)'

Locate an imported module.Names for import packages and install distributions can differ.

deactivate

Undo activation's shell changes.The environment directory and installed packages remain.

Diagnose interpreter confusion

type -a python python3 pip
command -v python
python -m pip --version
python -c 'import sys; print(sys.executable); print(*sys.path, sep="\n")'
python -m pip show requests

These commands connect shell lookup, interpreter identity, pip identity, import path, and distribution location. Run them before reinstalling anything.

05 · Rebuildability

Specify direct dependencies and resolve deliberately

A reproducible environment needs more than pip freeze. Record the Python version, platform/native prerequisites, source index policy, direct dependencies, and a reviewed lock or constraints output.

ArtifactPurposeTrade-off
pyproject.tomlProject metadata and direct dependency intentRanges may resolve differently over time without locking.
requirements.inSmall list of direct requirementsNeeds a resolver step to capture transitives.
Locked requirementsExact resolved versions, often hashesMay be platform-specific and needs controlled refresh.
Constraints fileLimit versions while another input declares requirementsDoes not itself cause packages to be installed.
pip freezeSnapshot everything installed nowIncludes incidental packages and loses direct/transitive intent.
 
# Record runtime evidence with an evaluation artifact
python --version
python -m pip --version
python -m pip freeze --all > reports/environment-freeze.txt
python -m pip check
git rev-parse HEAD
Clean-room testThe real test is to create a fresh venv from the documented Python version and dependency artifacts, install without relying on an old cache, run tests, and reproduce the report. “Works in my existing venv” is not evidence of rebuildability.

06 · Security

Treat installation as code execution

NAME

Verify what you are installing

Typosquatting and dependency-confusion attacks exploit package names and index precedence. Copy names from reviewed project metadata.

SOURCE

Control indexes

Know whether packages come from public PyPI, an internal mirror, a local artifact, Git, or an arbitrary URL.

VERSION

Pin and review updates

Ranges are useful for authoring, but production resolutions should be explicit and updated through review with tests.

INTEGRITY

Use hashes where practical

Hash-checked lock files detect altered artifacts, though they do not establish that the original package was trustworthy.

Never install unknown code casuallyBuild backends and installation steps can execute code. Do not paste pip install commands from untrusted issue text or run mystery requirements with privileged credentials. Inspect the source, provenance, requested version, and destination environment first.

Secrets and configuration

Keep secrets out of requirements, command histories, package-index URLs, committed .env files, and diagnostic output. Supply them through the deployment platform's secret mechanism and document only the required variable names.

07 · On the job

Detection-engineering scenarios

WRONG PYTHON

A module is installed but import fails

command -v python
python -m pip --version
python -m pip show <distribution>
python -c 'import sys; print(sys.executable); print(*sys.path, sep="\n")'

Likely cause: installation and execution used different interpreters or the install distribution and import package names differ.

NATIVE BUILD

A packet-parsing dependency fails to install

Read the first meaningful build error. The Python package may require compiler tools, headers, Rust, or a library such as libpcap at the OS layer.

python --version
python -m pip --version
python -m pip install -v <reviewed-package>
# Install documented native prerequisites via the OS manager,
# then retry inside the venv without sudo pip.
DRIFT

A detection report changes without a code diff

git status --short
git rev-parse HEAD
python --version
python -m pip freeze --all | sort
# Compare with the environment evidence saved for the previous run.

Reasoning: parser, timezone, regex, serialization, or model-library behavior can change with dependencies or the interpreter even when repository code is identical.

PRODUCTION

The service cannot find the activated venv

A service manager does not inherit your interactive activation. Configure the service to execute the venv interpreter explicitly.

/opt/analyzer/.venv/bin/python /opt/analyzer/analyzer.py
# Record a controlled working directory, environment, identity, and logs
# in the service definition rather than relying on ~/.zshrc or ~/.bashrc.

08 · Practice

Hands-on drills

1. Observe PATH activation

15 min
printf 'before PATH=%s\n' "$PATH"
command -v python3
python3 -m venv .venv
source .venv/bin/activate
printf 'after PATH=%s\n' "$PATH"
command -v python
printf 'VIRTUAL_ENV=%s\n' "$VIRTUAL_ENV"
deactivate
  • Identify the exact PATH entry added by activation.
  • Explain sys.prefix versus sys.base_prefix.
  • Show how deactivate restores command resolution.

2. Prove project isolation

20 min

Create two venvs, install different reviewed versions of a small library, and use each environment's explicit Python path to print the version and module file.

  • Do not activate either environment for the final comparison.
  • Show that the base interpreter remains unchanged.
  • Explain what is isolated and what OS resources are still shared.

3. Rebuild from blank

30 min

Delete only a disposable project venv after validating its exact path, create a fresh one from the documented interpreter, install the dependency specification, and run the project's tests.

  • Save Python, pip, platform, and dependency evidence.
  • Explain every dependency source and pinning choice.
  • Run the analyzer with the venv's explicit Python path.
