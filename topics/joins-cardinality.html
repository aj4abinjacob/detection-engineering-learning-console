SQL depth I · relationships

Predict the rows before you join, or your counts are guesses.

A join pairs rows according to a predicate. It does not “add columns” safely by default: one-to-many and many-to-many relationships multiply rows, which can quietly inflate a detection metric.

01 · Purpose

Joins decide who is counted with whom

Detection questions cross entities: which accounts share an IP, which requests have no enrichment, which failures have a matching session. The reliable workflow is to name each input’s grain, predict matches per row, and inspect counts before trusting an aggregate.

GRAIN

Rows have a unit

One request joined to one account is different from one account joined to all its requests.

MULTIPLICITY

Matches multiply

Two matching right rows make two result rows; joins do not deduplicate.

NULL

Outer joins preserve absence

LEFT JOIN shows unmatched left rows with NULL right-side columns.

EVIDENCE

Prediction catches defects

A surprising result count exposes duplicate keys, wrong predicate, or unmodeled relationship.

03 · Prediction

State relationship direction and count expectations

RelationshipExampleExpected result grain
Many-to-onerequests → accountsOne row per request when account key is unique.
One-to-manyaccounts → requestsOne row per request; accounts repeat.
Many-to-manyaccounts ↔ shared IP observationsOne row per relationship; use a linking/event table.

-- Predict: one row per request, including anonymous requests.
SELECT r.request_id, r.status, a.handle
FROM access_requests AS r
LEFT JOIN accounts AS a ON a.account_id = r.account_id;

Check candidate-key uniqueness first. If accounts.account_id is not unique due to a bad import, the apparently many-to-one join becomes one-to-many and duplicates every affected request.

04 · Common joins

INNER filters unmatched rows; LEFT preserves the left

-- INNER: only requests with a matching account.
SELECT r.request_id, a.handle
FROM access_requests r
JOIN accounts a ON a.account_id = r.account_id;

-- LEFT: all requests; NULL handle means no match.
SELECT r.request_id, a.handle
FROM access_requests r
LEFT JOIN accounts a ON a.account_id = r.account_id
WHERE a.account_id IS NULL;

An INNER JOIN excludes requests with NULL/nonmatching foreign keys. A LEFT JOIN followed by a right-table condition in WHERE can accidentally become an inner join: WHERE a.handle = 'x' rejects the NULL-extended rows. Put a match filter in ON when you mean to preserve unmatched left rows.

05 · Other join forms

Know the engine support and the explosion risk

RIGHT JOIN

Preserve every right row.It is symmetric to swapping tables in a LEFT JOIN. PostgreSQL supports it; modern SQLite supports RIGHT JOIN, but rewriting as LEFT JOIN is often clearer and more portable.

FULL OUTER JOIN

Preserve unmatched rows on both sides.PostgreSQL supports it. SQLite support depends on version; portable SQLite work commonly simulates with two LEFT JOIN branches and UNION ALL, carefully avoiding duplicate matches.

CROSS JOIN

Return every left/right combination.Use intentionally for a small declared grid such as dates × rules. It has no join predicate and can create massive outputs; never use it to “see what happens” on production-sized tables.

06 · Correct predicates

Use every key component that defines the relationship

-- A device ID is only unique inside a tenant.
SELECT e.event_id, d.owner_account_id
FROM device_events e
JOIN devices d
  ON d.tenant_id = e.tenant_id
 AND d.device_id = e.device_id;

Joining only device_id here creates cross-tenant matches and inflated rows. Align data types/collations deliberately; avoid joining formatted strings when canonical IDs exist. SQL NULL never equals NULL, so nullable keys need explicit business logic rather than an assumed match.

07 · Self joins and N+1

Alias the same relation to compare entities

-- Accounts that have used the same synthetic source IP.
SELECT DISTINCT a1.account_id AS account_a, a2.account_id AS account_b, o1.source_ip
FROM account_ip_observations o1
JOIN account_ip_observations o2
  ON o1.source_ip = o2.source_ip AND o1.account_id < o2.account_id
JOIN accounts a1 ON a1.account_id = o1.account_id
JOIN accounts a2 ON a2.account_id = o2.account_id;

a1 < a2 removes mirrored/self pairs but does not establish malicious coordination; NAT, proxies, and shared devices are alternatives. N+1 is the opposite workflow problem: query accounts, then issue one request query per account. Prefer one set-based join/aggregate when it preserves the required grain; measure before optimizing.

08 · Safety & platforms

Join analysis can be expensive and revealing

Use parameterized filters, a bounded time window, and only synthetic local data for these exercises. PostgreSQL’s EXPLAIN ANALYZE executes the query and can run DML; plain EXPLAIN does not execute. SQLite’s EXPLAIN QUERY PLAN reports a plan, but run any investigation against an approved read-only/lab connection. Join output can correlate personal identifiers; aggregate or redact before sharing.

09 · On the job

Detection-engineering scenarios

QA

Failed-login count doubles after enrichment

Compare request count before/after joining. If one request has several enrichment versions, choose one deterministically or aggregate enrichment first; DISTINCT can mask a broken relation rather than repair it.

GAP

Which requests lack account attribution?

Use LEFT JOIN and WHERE a.account_id IS NULL. Separate anonymous-by-design from broken FK/enrichment paths before escalating a telemetry gap.

ABUSE

Accounts sharing a source IP

Self-join observations with ordered account IDs, then apply time and tenant boundaries. The result is a correlation candidate; validate against NAT/proxy/device evidence.

PERF

Dashboard does hundreds of small queries

Identify N+1 from query logs, replace it with a tested set query or batched lookup, then confirm row multiplicity and query plan rather than assuming fewer statements means correct results.

10 · Practice

Hands-on drills

1. Predict every join before execution

35 min

Save artifacts/joins/predictions.md and joins.sql. Use a synthetic accounts/requests fixture and predict INNER, LEFT, RIGHT/FULL where your engine supports them, and CROSS row counts.

  • State input grain and expected matches per row.
  • Record actual rows and explain every difference.
  • Mark engine/version-specific syntax used.

2. Find unmatched requests

25 min

Save unmatched.csv and query-notes.md from a LEFT JOIN using only documentation IPs.

  • Explain why the predicate belongs in ON or WHERE.
  • Show why = NULL is wrong.
  • Classify synthetic unmatched reasons.

3. Build a shared-IP self join

30 min

Save shared_ip.sql and false-positive-note.md with a two-account synthetic pair.

  • Use aliases and prevent mirrored pairs.
  • Use a multi-column join if tenant scope exists.
  • Name one benign shared-IP explanation.
