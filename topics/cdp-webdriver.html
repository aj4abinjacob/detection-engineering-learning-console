Browser control · evidence boundary

Know what drives the browser and what the server can see.

WebDriver and Chrome DevTools Protocol (CDP) let tools control or instrument a browser. A page may observe selected local runtime outcomes; an HTTP server sees only requests, connection metadata, and any telemetry the page/client sends. The server never directly observes CDP itself.

Why this matters

Automation frameworks can click, type, navigate, inspect, emulate, and test an owned application. Detection work goes wrong when a local browser-control mechanism is mistaken for a network-visible attribute. Clear boundaries improve investigations, reduce brittle rules, and let teams label their own automation reliably.

Mental model: separate the control channel from the request channel

ControllerTest runner sends WebDriver commands or CDP messages to a browser.
→
Browser/pageExecutes page JavaScript, produces local runtime observations, sends optional telemetry.
→
Application serverReceives HTTP and explicitly transmitted telemetry—not CDP commands.

The exact transport/endpoint between controller and browser is not an application request to the protected server.

WebDriver: standardized browser automation

WebDriver defines a remote-control model: a client sends commands to a WebDriver implementation, which drives a browser session. Frameworks may use WebDriver directly or wrap it. The browser can expose standardized cooperation state such as navigator.webdriver; that is a page-side property, not a server observation unless reported. Use explicit run IDs and dedicated test accounts to identify authorized automation.

CDP: Chromium instrumentation and debugging

CDP is a Chromium-family protocol used for inspecting, debugging, profiling, and controlling browser targets. It has domains such as Page, Network, DOM, Runtime, and Debugger, with versioned protocol definitions. CDP’s existence does not imply a user is malicious: Chrome DevTools, IDEs, QA frameworks, browser diagnostics, and internal tooling can use it. The server cannot read a client’s CDP messages unless a client deliberately transmits information derived from them.

What an owned page can observe

A page can read browser-exposed Web APIs, observe its own DOM/events/performance, and receive data that a first-party fixture intentionally places in its runtime. It cannot reliably enumerate every controller or prove an automation framework from a single artifact. Page-side probes must be minimal, versioned, privacy-reviewed, and used only on owned AbuseGuard local/staging routes or supplied fixtures.

// Local/staging AbuseGuard probe: ordinary page-visible data only.
const pageEvidence = {
  probeVersion: 1,
  webdriverReported: navigator.webdriver === true,
  pageLoadBucketMs: Math.floor(performance.now() / 100) * 100
};
// Test runner label is supplied by owned test configuration, not inferred.
console.log(JSON.stringify(pageEvidence));

Trace a first-party probe into telemetry safely

  1. Define a local test route. Use owned AbuseGuard local/staging and a documented test run.
  2. Compute a minimal page observation. Example: Boolean WebDriver report plus coarse load bucket—not typed content or high-entropy fingerprints.
  3. Transmit only by approved design. Include schema/probe version and explicit test label; authenticate and minimize.
  4. Compare with HTTP logs. Show which fields came from the request and which came from the page report; retain failure/absence as uncertain.
Safety boundaryDo not add scripts that conceal automation, alter browser properties, defeat an anti-bot product, or target a third-party application. A probe fixture demonstrates measurement and data flow, not bypass capability.

Operational safeguards

Tag test traffic with dedicated credentials or a signed server-recognized test identity; never rely on a User-Agent or local browser property to create an allowlist. Segregate test telemetry, redact session identifiers, set retention, and test retries/offline states. Apply an accessible fallback for users who do not send optional browser telemetry. For real abuse, use server-side velocity, account controls, authorization, and reviewed step-up paths.

Detection-engineering scenarios

1. Analyst says “the origin detected CDP”

Trigger: an origin alert is attributed to CDP. Artifact: origin HTTP log and first-party page telemetry schema. Observation point: owned edge/origin. Reasoning: separate request-visible facts from any page-report field, then state that the origin did not observe the CDP channel. False-positive boundary: a timing/header pattern does not prove CDP use.

2. Synthetic monitor is blocked after a rule change

Trigger: owned monitor fails a protected route. Artifact: explicit test run label, route policy version, page probe, and HTTP response. Observation point: staging application and authorized control plane. Reasoning: diagnose the configured rule against an authenticated test identity and restore the dedicated test path if appropriate. False-positive boundary: do not broadly exempt all automated browsers or user agents.

3. Page probe fails to reach telemetry endpoint

Trigger: server has request logs but no probe record. Artifact: response CSP/network error, browser compatibility result, and endpoint status. Observation point: owned client and telemetry service. Reasoning: treat absence as delivery/compatibility uncertainty and retain server-side controls. False-positive boundary: missing telemetry does not establish automation or evasion.

4. A rule combines page and HTTP evidence

Trigger: repeated credential failures occur with an unusual owned-page outcome. Artifact: rate window, account state, route, page schema version, and accessibility fallback result. Observation point: first-party login telemetry. Reasoning: start with observe/step-up and measure legitimate completion; page evidence merely adds context. False-positive boundary: no individual page-side artifact should become a direct block.

Artifact-producing drills

1. Control/data-flow diagram

Automate a local AbuseGuard page with an approved framework and save artifacts/cdp/control-data-flow.md showing controller → browser versus browser → HTTP server. Label the channels and state explicitly that CDP is not server-visible.

  • Use no third-party target.
  • Mark observed facts and inferred claims separately.

2. First-party probe trace

Run the local probe fixture and save artifacts/cdp/probe-trace.json containing the labelled page evidence, the minimal telemetry record, and matching sanitized HTTP log fields.

  • Include schema/version and test-run label.
  • Exclude cookies, secrets, typed input, and raw fingerprints.

3. Boundary review

Save artifacts/cdp/boundary-review.md with three claims an origin can support, three it cannot support, and a fallback for omitted page telemetry.

  • Explain why each conclusion follows from the observation point.
  • Present without AI.
