Define the denominator before you count the signal.

GROUP BY turns rows into groups and aggregates them. Detection quality depends on declared grain, filters, NULL policy, join multiplicity, and whether a “unique” count really describes the entity you think it does.

01 · Purpose

Every aggregate is a compressed claim

“Ten failed logins” is incomplete until you name the window, entity, source rows, filters, and denominator. Grouping makes a result small enough to act on; it also makes mistakes hard to see unless you preserve those definitions.

GRAIN

Groups choose entities

Per IP, per account, per route, and per minute answer different questions.

FILTER

WHERE changes input

It filters rows before groups exist; use it for time/routing/status population.

THRESHOLD

HAVING filters results

It filters completed groups; use it for “more than N” conditions.

QUALITY

COUNT has NULL rules

COUNT(*), COUNT(col), and COUNT(DISTINCT col) differ materially.

02 · Mental model

SQL logical order explains why an aggregate cannot be used in WHERE and why selecting a non-grouped, non-aggregated column is invalid in PostgreSQL (SQLite can permissively return an arbitrary value in some cases—do not rely on it).

03 · Functions

Count exactly what the function says

SELECT
  COUNT(*) AS requests,
  COUNT(account_id) AS attributed_requests,
  COUNT(DISTINCT account_id) AS unique_accounts,
  MIN(observed_at) AS first_seen,
  MAX(observed_at) AS last_seen
FROM access_requests
WHERE observed_at >= '2026-01-01T00:00:00Z';

COUNT(*) counts rows, including rows with NULL columns. COUNT(account_id) counts only non-NULL account IDs. COUNT(DISTINCT account_id) counts distinct non-NULL values. SUM/AVG ignore NULL inputs; empty/NULL-only groups may produce NULL rather than zero. Use COALESCE only after deciding that zero is the honest meaning.

COUNT(*)

Count rows at current query grain.Use for request volume after confirming joins did not multiply rows.

COUNT(DISTINCT account_id)

Count known unique account values.Use to measure account diversity; it excludes NULL and can be costly on large data.

SUM(CASE WHEN status >= 500 THEN 1 ELSE 0 END)

Count a defined subset while retaining all rows.Use for numerator/denominator in one group. PostgreSQL also supports COUNT(*) FILTER (WHERE ...); SQLite support/version differs.

04 · Group grain

Group by the entity you intend to alert on

-- Requests per IP in a declared period.
SELECT source_ip, COUNT(*) AS request_count
FROM access_requests
WHERE observed_at >= '2026-01-01T00:00:00Z'
  AND observed_at <  '2026-01-01T01:00:00Z'
GROUP BY source_ip
ORDER BY request_count DESC, source_ip;

Every selected expression must be grouped or aggregated in portable SQL. Grouping by both IP and path creates finer groups than IP alone; it may hide a high total across routes. Time bucketing is engine-specific: PostgreSQL offers date_trunc; SQLite commonly uses strftime over consistently stored UTC text. Use an explicit half-open time interval to avoid double-counting boundary events.

05 · Filter at the right stage

WHERE filters rows; HAVING filters group metrics

-- Accounts with more than 3 failed logins in the window.
SELECT account_id, COUNT(*) AS failed_logins
FROM access_requests
WHERE status IN (401, 403)
  AND observed_at >= '2026-01-01T00:00:00Z'
GROUP BY account_id
HAVING COUNT(*) > 3;

-- PostgreSQL: COUNT(*) FILTER (WHERE status >= 500) / COUNT(*)::numeric

Putting COUNT(*) > 3 in WHERE is invalid because groups are not formed yet. Putting a row predicate in HAVING may be legal but obscures intent and can prevent straightforward optimization. For error rate, define numerator and denominator explicitly; do not divide integers in PostgreSQL without casting if you need a fractional result.

06 · DISTINCT is not a repair button

Unique counts can conceal a broken join

DISTINCT removes identical selected rows, while COUNT(DISTINCT x) counts unique non-NULL x values. Neither proves your join predicate is correct. If joining request tags creates three rows per request, COUNT(DISTINCT request_id) might restore a request total but loses tag multiplicity; aggregate tags first or choose a different query grain. Multiple columns in distinct counts are PostgreSQL-specific syntax; SQLite differs—use a subquery with SELECT DISTINCT col1, col2 for portable intent.

NULL checkDistinct groups can include a NULL group, but COUNT(DISTINCT column) omits NULL. State whether unknown identity is excluded, counted as its own category, or investigated as a telemetry gap.

07 · Detection calculations

Make numerator, denominator, and false-positive context visible

SELECT path,
       COUNT(*) AS total_requests,
       SUM(CASE WHEN status BETWEEN 500 AND 599 THEN 1 ELSE 0 END) AS server_errors,
       1.0 * SUM(CASE WHEN status BETWEEN 500 AND 599 THEN 1 ELSE 0 END)
           / NULLIF(COUNT(*), 0) AS server_error_rate
FROM access_requests
WHERE observed_at >= '2026-01-01T00:00:00Z'
GROUP BY path;

NULLIF avoids division by zero; a NULL rate says no denominator exists, which may be more honest than 0. Define whether 4xx are failures, abuse signals, or expected user behavior. Counts from untrusted client IPs and shared NATs are leads, not attribution.

08 · Safety & platforms

Aggregate locally before trusting it broadly

Run DDL/DML only on disposable SQLite fixtures or an approved transaction. PostgreSQL EXPLAIN ANALYZE executes the query, including writes; do not use it as a harmless preview. SQLite typing and timestamp functions differ from PostgreSQL; preserve UTC format and test your target engine. Bound time windows and use least-privilege read-only roles for investigation queries. Aggregates can still expose sensitive small populations—apply minimum-count, access, and retention policy.

09 · On the job

Detection-engineering scenarios

VOLUME

Top source IPs in an incident window

GROUP BY source IP under an exact time filter, then compare unique accounts and routes. A busy corporate NAT is a false-positive alternative, not an attacker identity.

OUTAGE

5xx rate rises only on checkout

Group by path with explicit numerator/denominator. Check total volume: a high rate on one request is not the same operational signal as a broad high-volume outage.

AUTH

Accounts exceed failed-login threshold

Filter failed statuses in WHERE, group by account, and use HAVING. Preserve NULL account groups separately so anonymous activity does not vanish.

QA

Unique-account metric drops after tag join

Inspect pre/post join row counts and distinct keys. Do not treat COUNT DISTINCT as proof; locate the multiplicity change before publishing a trend.

10 · Practice

Hands-on drills

1. Aggregate a synthetic access log

30 min

Save artifacts/grouping/queries.sql and results.md with requests per documentation IP and 5xx rate per path.

  • State row grain, time window, numerator, and denominator.
  • Show COUNT(*) and COUNT(account_id) differ.
  • Use a half-open interval.

2. Build a HAVING threshold

25 min

Save failed_logins.sql and threshold-proof.md for accounts over N failures.

  • Predict group counts before running.
  • Explain why the status filter is WHERE and the count filter is HAVING.
  • Document NULL-account policy.

3. Investigate a DISTINCT trap

30 min

Save a small request/tag fixture, multiplicity.sql, and join-grain-note.md.

  • Show row count before and after join.
  • Compare raw count, distinct request count, and distinct account count.
  • State the correct grain rather than hiding duplicates.
