Auth, authz & deployment

Store password verifiers, not recoverable passwords.

Authentication establishes a claimed principal; authorization decides what it may do. New FastAPI work should use pwdlib with Argon2, and legacy hashes need an explicit verified migration path.

Why it matters

Password handling is a high-impact boundary. Passwords are inputs to an adaptive password-hashing KDF; they must never be encrypted for retrieval, logged, committed, or compared by homemade crypto.

Authentication is not authorization

Authentication answers “which principal proved control of a credential?” Authorization answers “may this principal access this object/action now?” A valid session does not grant tenant or role access automatically.

Sessions and tokens

Server-side sessions store an opaque browser identifier whose state is checked server-side. Tokens can carry or reference claims but require issuer/audience/expiry/revocation design. Neither model removes server-side authorization checks.

Use pwdlib Argon2

from pwdlib import PasswordHash
password_hash = PasswordHash.recommended()
stored = password_hash.hash("local-demo-password")
assert password_hash.verify("local-demo-password", stored)

recommended() selects pwdlib’s current recommended password hash (Argon2 for supported configuration). Use a project-pinned dependency and review parameter changes. This creates a synthetic local verifier; never put real password literals in source, fixtures, terminal history, or logs.

Verify and migrate legacy hashes

from pwdlib import PasswordHash
from pwdlib.hashers.argon2 import Argon2Hasher
from pwdlib.hashers.bcrypt import BcryptHasher

# First hasher is the new-write policy; later hashers are temporary readers.
legacy_compatible = PasswordHash((Argon2Hasher(), BcryptHasher()))
verified, updated_hash = legacy_compatible.verify_and_update(
    password, stored_hash
)
if verified and updated_hash:
    save_replacement_verifier(updated_hash)

Configure only legacy schemes actually present in your store and install/pin their pwdlib extras deliberately. The first hasher is used for replacements; a successfully verified bcrypt value therefore becomes an Argon2 value. PasswordHash.recommended() alone recognizes only its recommended Argon2 hasher in pwdlib 0.3.0 and cannot verify a bcrypt legacy hash. Catch an unknown scheme as an operational migration/reset case, never as authentication success. Do not bulk “convert” hashes without passwords; keep compatibility metrics and a retirement date.

Unknown-user timing

For a nonexistent account, run a dummy verification against a fixed valid dummy hash before returning a generic failure. This reduces obvious timing difference, but network noise and response behavior still matter. Do not reveal whether account, password, lockout, or MFA caused failure.

Operational storage

Store only encoded verifiers and algorithm parameters, with restricted database access and backup controls. Rate-limit/monitor attempts, support secure reset flows, and rotate session state on login. A KDF resists offline guessing; it does not solve phishing, credential reuse, or compromised endpoints.

Safety and version limits

Use local synthetic passwords only. pwdlib/passlib APIs and Argon2 recommendations can evolve; pin and document versions. Passlib is primarily compatibility support for legacy hashes in this curriculum, not the choice for new FastAPI code. Never roll your own password hash, salt, or comparison.

Defensive scenarios

Legacy verifier login

Verify through compatibility context and replace only on success; record migration count, never password/hash content.

User enumeration concern

Use generic failures and dummy verify; test response shape/timing policy without claiming perfect timing secrecy.

Valid login accesses another tenant

This is authorization failure, not password-hash failure; test object checks separately.

Hash appears in log

Treat it as sensitive credential material, restrict/rotate process under incident policy, and add redaction regression.
