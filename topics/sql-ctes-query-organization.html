01 · Purpose

Readable query stages reduce analytical mistakes

A detection query often filters trusted events, normalizes fields, derives features, then applies a threshold. Naming those stages makes grain, assumptions, and test points visible.

REVIEW

Name a relation

Each CTE can state one input/output contract.

CORRECTNESS

Protect grain

Know whether a stage is one row/event or one row/entity.

PERFORMANCE

Plan still decides

Read EXPLAIN; style does not guarantee materialization.

SAFETY

Keep reads read-only

WITH can contain DML in PostgreSQL; do not assume it is a SELECT.

02 · Mental model

Each CTE is a named intermediate relation

filteredTrusted scope, one row/event.
→
featuresAdd window values, still one row/event.
→
alertsThreshold/filter output.

Write the grain in a comment. A join can multiply rows; an aggregate changes grain; a CTE name alone changes neither.

03 · Basic CTE

WITH scoped_events AS (
  SELECT event_id, client_ip, seen_at, status
  FROM events
  WHERE tenant_id = $1 AND seen_at >= $2 AND seen_at < $3
), failed AS (
  SELECT * FROM scoped_events WHERE status BETWEEN 400 AND 499
)
SELECT client_ip, count(*) AS failures
FROM failed GROUP BY client_ip;

Use: name reusable logical stages and bind parameters through the driver. Assumption: the half-open time interval and status definition match policy. Risk: SELECT * can silently change output/grain after schema changes; select explicit fields in production queries.

04 · CTE, subquery, or join?

ToolBest forRisk
CTENamed multi-stage logic/reuse/readabilityAssuming materialization/performance.
SubqueryLocal derived value/filterDeep nesting hides grain.
JoinCombine related relationsUnexpected many-to-many multiplication.

Choose the clearest correct relational expression, then inspect its plan. A correlated subquery may run conceptually per outer row; a join/aggregation may be better, but only equivalent semantics and evidence justify rewrite.

05 · Organize a window detector

-- PostgreSQL-only rolling frame; structured for review
WITH scoped AS (
 SELECT event_id, client_ip, seen_at FROM events
 WHERE tenant_id = $1 AND seen_at >= $2 AND seen_at < $3
), velocity AS (
 SELECT *, count(*) OVER (
  PARTITION BY client_ip ORDER BY seen_at
  RANGE BETWEEN INTERVAL '1 minute' PRECEDING AND CURRENT ROW
 ) AS requests_last_minute FROM scoped
)
SELECT * FROM velocity WHERE requests_last_minute >= 5;

Use: stages make scope/window/threshold reviewable. Risk: PostgreSQL frame syntax/peer behavior applies; exact boundary and ties require Topic 6.3 tests. This is not validated by SQLite.

06 · PostgreSQL materialization/inlining caveat

Modern PostgreSQL can inline a non-recursive, side-effect-free CTE used once, allowing optimization across the boundary; it can also materialize where semantics/multiple references require it. PostgreSQL provides MATERIALIZED and NOT MATERIALIZED controls in supported modern versions, but their availability/behavior is version-specific and must be checked against the deployed documentation and plan. Do not use a CTE as an assumed optimization fence. Older PostgreSQL versions had different default behavior.

07 · Safety

WITH is not inherently read-onlyPostgreSQL supports data-modifying CTEs such as WITH moved AS (DELETE ... RETURNING ...). Do not place DML examples into an investigation console or run EXPLAIN ANALYZE on them. Keep this guide’s drills SELECT-only and synthetic. Recursive CTEs can consume substantial work or loop until limits/termination; mention them only with a proven termination condition.

08 · SQLite differences

-- SQLite-compatible read-only CTE structure
WITH failed AS (SELECT client_ip FROM events WHERE status BETWEEN 400 AND 499)
SELECT client_ip, count(*) FROM failed GROUP BY client_ip;

SQLite supports CTEs/window functions in current releases but has different planner details, date functions, and no PostgreSQL INTERVAL/MATERIALIZED portability guarantee. Validate SQLite artifacts locally; label PostgreSQL-only syntax rather than mixing dialects.

09 · Detection scenarios

HUNT

Query hides tenant scope

Put scope in the first CTE, declare one row/event, and review downstream stages for accidental scope loss.

JOIN

Enrichment doubles alerts

Make a CTE that deduplicates/aggregates enrichment to the intended grain before joining; prove cardinality.

WINDOW

Velocity logic is unreadable

Name scoped, velocity, and alerts stages; tests can inspect each intermediate result.

PERF

CTE rewrite gets slower

Compare EXPLAIN and result set; do not blame a CTE name or force materialization without a versioned plan hypothesis.
