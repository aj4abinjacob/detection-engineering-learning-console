01 · Purpose

Why build this without assistance?

A detection engineer often receives semi-structured evidence before a dashboard, parser, or data model exists. The useful skill is not remembering every library call; it is choosing an explicit input contract, isolating transformation steps, and proving the result.

INPUT CONTRACT

Logs are data, not prose

Every metric depends on the timestamp, client identity, and status fields being parsed exactly as you claim.

REPRODUCIBILITY

One command, one result

A CLI makes the input, limit, and output format reviewable in an incident timeline or CI job.

DETECTION SIGNAL

Aggregation creates leads

Top talkers, error-rate shifts, and rate bursts are triage signals—not conclusions about maliciousness.

TRUST

Tests preserve meaning

Five small tests can pin down boundary choices before a rule or report is trusted.

Diagnostic ruleYour Week 0 artifact measures what you can do cold. Preserve the original implementation and gaps.md; make a separate review revision if you improve it after reading this page.

02 · Mental model

Keep parsing, aggregation, and presentation separate

A reliable tiny analyzer is a pipeline. Each stage accepts a narrow value, produces a narrow value, and can be tested without a terminal or real log file.

Text → eventParse one line into a typed record or reject it with a counted reason.parse_line(line)
→
Events → metricsCount client IPs, statuses, and minute buckets with declared rules.summarize(events)
→
Metrics → outputRender stable JSON or text through a small CLI adapter.main(argv)

Do not let file I/O, regular expressions, printing, and counting become one untestable loop. The boundary is what lets you diagnose a wrong result.

from dataclasses import dataclass
from datetime import UTC, datetime

@dataclass(frozen=True)
class AccessEvent:
    client_ip: str
    when: datetime
    status: int
    method: str
    path: str

An immutable event is a useful convention, not a requirement. It makes accidental mutation less likely while the same event feeds more than one aggregate.

03 · Input

Parse access logs with an explicit contract

This example accepts the common Nginx/Apache-style combined log shape. It is a lab contract: real deployments may add a trusted-proxy address, use JSON, omit fields, or escape values differently.

203.0.113.8 - - [10/Oct/2025:13:55:36 +0000] "GET /login HTTP/1.1" 401 182 "-" "curl/8.0"

# Required here: client address, bracketed timestamp, quoted request, numeric status.
# Do not use a regex designed for this line against an unknown vendor format.
re.fullmatch(pattern, line)

Require the full expected shape.Use when the exercise's fixture controls the format; partial matches can silently accept truncated or concatenated evidence.

datetime.strptime(..., "%d/%b/%Y:%H:%M:%S %z")

Parse a zoned timestamp.The %z offset matters: bucket normalized instants, not a timestamp string that only looks comparable.

ipaddress.ip_address(value)

Validate an address literal.It checks syntax, not whether the address is the original client behind a proxy.

import re
from datetime import datetime
from ipaddress import ip_address

LINE = re.compile(
    r'(?P<ip>\S+) \S+ \S+ \[(?P<time>[^\]]+)\] '
    r'"(?P<method>[A-Z]+) (?P<path>\S+) [^"]+" '
    r'(?P<status>\d{3}) \S+ "[^"]*" "[^"]*"'
)

def parse_line(line: str) -> AccessEvent:
    match = LINE.fullmatch(line.rstrip("\n"))
    if not match:
        raise ValueError("unsupported access-log line")
    fields = match.groupdict()
    return AccessEvent(
        client_ip=str(ip_address(fields["ip"])),
        when=datetime.strptime(fields["time"], "%d/%b/%Y:%H:%M:%S %z"),
        status=int(fields["status"]), method=fields["method"], path=fields["path"],
    )
Client IP is not automatically identityAt a reverse proxy, the socket peer may be the proxy and a forwarded header may be spoofable unless the proxy chain strips and sets it. Record what field you used and its trust boundary before attributing activity to an IP.

04 · Aggregation

Make the metric definitions visible

The exercise asks for top-N IPs, error rate, and requests per minute. State the denominator and rounding policy beside the result so another engineer can reproduce it.

from collections import Counter

def summarize(events: list[AccessEvent], limit: int) -> dict:
    top_ips = Counter(event.client_ip for event in events).most_common(limit)
    errors = sum(500 <= event.status < 600 for event in events)
    by_minute = Counter(
        event.when.astimezone(UTC).replace(second=0, microsecond=0).isoformat()
        for event in events
    )
    total = len(events)
    return {
        "bucket_timezone": "UTC",
        "requests": total,
        "server_error_rate": errors / total if total else 0.0,
        "top_ips": top_ips,
        "requests_per_minute": dict(sorted(by_minute.items())),
    }
MetricDefinition used hereQuestion to ask before trusting it
Top-N IPsMost parsed requests by address; ties follow counter encounter order unless you add a secondary sort.Is NAT, a proxy, or a load balancer collapsing many people?
Error rate5xx requests / all parsed requests.Did the investigation mean 4xx + 5xx, a route-specific rate, or upstream failures?
Requests/minuteRequests in each timestamp minute after a chosen timezone conversion.Are timestamps complete, ordered, and all from the same clock/source?
Recommendation, not a universal definitionFor a quick availability signal, treat only 5xx as server errors. Authentication failures (401/403) often deserve a separate abuse metric because including them in “error rate” blends client behavior with service failure.

05 · Interface

Package the tool and expose a small CLI

Package layout lets imports behave consistently in tests and makes the command an explicit interface. argparse is in the Python standard library, so it fits a blank-folder diagnostic without a dependency decision.

log-analyzer/
├── pyproject.toml
├── src/log_analyzer/__init__.py
├── src/log_analyzer/core.py
├── src/log_analyzer/cli.py
└── tests/test_core.py

# pyproject.toml
[project]
name = "log-analyzer"
version = "0.1.0"
requires-python = ">=3.11"
[project.scripts]
log-analyzer = "log_analyzer.cli:main"
import argparse
import json
from pathlib import Path

from .core import parse_line, summarize

def main(argv: list[str] | None = None) -> int:
    parser = argparse.ArgumentParser(description="Summarize access logs")
    parser.add_argument("log", type=Path)
    parser.add_argument("--top", type=int, default=10)
    args = parser.parse_args(argv)
    if args.top < 1:
        parser.error("--top must be at least 1")
    events = [parse_line(line) for line in args.log.read_text().splitlines()]
    print(json.dumps(summarize(events, args.top), indent=2))
    return 0

if __name__ == "__main__":
    raise SystemExit(main())

Install only into a disposable virtual environment: python3 -m venv .venv, activate it for your shell, then python -m pip install -e .. Do not run an unknown package installer with elevated privileges or point it at production logs.

06 · Proof

Write five tests that describe the contract

Tests are executable claims. They should pin down both ordinary inputs and a boundary where a plausible implementation would lie.

# pytest examples; use unittest if that is what you can write cold.
def test_parses_valid_line(): ...
def test_rejects_malformed_line(): ...
def test_top_ips_respects_limit(): ...
def test_error_rate_counts_only_5xx(): ...
def test_empty_input_has_zero_error_rate(): ...
def test_equivalent_offsets_share_one_utc_minute_bucket(): ...
def test_output_declares_utc_bucket_timezone(): ...
Do not test your implementation by echoing itFor example, a test that computes the expected error rate with the same loop and same condition may repeat the same bug. Use a tiny fixture whose expected totals you can calculate by hand.
python3 -m pytest -q
# Or, if you used the standard library:
python3 -m unittest discover -v

07 · Boundaries

Failure modes and safe workflow

FailureWhy it happensSafe response
Regex accepts the wrong sourceFormats vary; a “combined” format is configurable.Version fixtures and fail closed with a parse-error count.
Bad timestamp bucketsNaive times, mixed offsets, daylight-saving transitions, or locale assumptions.Require an offset; normalize deliberately and document display timezone.
Memory exhaustionReading an unbounded production file into a list.Stream line by line, or use an approved query system for large data.
Evidence exposureLogs can contain session IDs, email addresses, URLs, and tokens.Use synthetic fixtures; redact before sharing artifacts; restrict output permissions.
False attributionAddress fields and status codes lack business context.Correlate with proxy configuration, route, user/account signals, and time window.

Platform assumptions: commands use Python 3.11+ and a POSIX-like shell for examples. Windows users can run the Python commands in PowerShell; virtual-environment activation is .venv\Scripts\Activate.ps1, not source .venv/bin/activate. The Python code itself is cross-platform.

08 · On the job

Detection-engineering scenarios

BURST

Login failures spike after a deployment

Run the analyzer for the deployment window, then compare 401/403 separately from 5xx. A top source IP may be an office NAT or a proxy; the decisive question is whether rate, route, account diversity, and client fingerprinting changed together.

OUTAGE

Only checkout returns 502

Bucket 5xx by minute and extend the event model with path. The analyzer establishes onset and volume; it cannot prove the upstream cause. Preserve the exact filter and correlate with load-balancer and application logs.

RULE QA

A rate-limit detection has a suspicious false positive

Recompute the per-minute count on the saved sample using the rule’s client-key definition. If the rule uses a trusted forwarded address while the script uses socket peer, the discrepancy is an instrumentation mismatch, not necessarily a bad threshold.

PIPELINE

A parser change lowers event volume

Count rejected lines and make parse failures visible. A cleaner-looking summary after a format change can mean data loss. Ship the fixture that caused the regression with the test before updating production parsing.

09 · Practice

Hands-on drills

Do these after saving the original diagnostic. Work under a new, explicitly named disposable directory; do not delete broad paths as cleanup.

1. Rebuild a log analyzer from a three-line fixture

45 min

Create artifacts/access.log, artifacts/summary.json, and artifacts/metric-definitions.md. Include at least one 2xx, 4xx, and 5xx line across two minutes.

  • Show your hand-calculated top IPs, 5xx denominator, and minute counts beside the JSON.
  • State which IP field is assumed to be the client and why that can fail behind a proxy.
  • Record malformed-line behavior rather than silently dropping it.

2. Add a CLI and package boundary

30 min

Save pyproject.toml, a package under src/, and artifacts/cli-transcript.txt showing --help, a successful run, and an invalid --top 0 run.

  • Explain why main(argv) is easier to test than reading sys.argv everywhere.
  • Show that output is valid JSON and that errors exit non-zero.
  • Name the Python version and operating system used.

3. Write six behavior tests and a gaps review

35 min

Save tests/test_core.py (or equivalent), artifacts/test-output.txt, and review-gaps.md. Keep the original diagnostic gaps.md unchanged.

  • Include valid, malformed, empty, error-rate, ordering/limit, and time-bucket cases.
  • For each failed first attempt, name the model gap—not merely the missing syntax.
  • Explain one test whose expected value was calculated without calling your production helper.
