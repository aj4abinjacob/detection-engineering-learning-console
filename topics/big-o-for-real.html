Practical field guide · Complexity

Name the growing input before you name the Big-O.

Complexity is a model of how work and retained state change with specified inputs. It tells you which detector will become a production problem before a benchmark does.

01 · Purpose

Why a correct loop can still be unsafe

“O(n)” says nothing until you say n is events in a batch, active entities, bytes per payload, or rules per event. That named model exposes expensive nested scans and unbounded retained state.

CAPACITY

Predict growth

Doubling input exposes n² before it is an outage.

DESIGN

Choose a primitive

Maps and deques change repeated operations.

TRIAGE

Read wall time carefully

Latency includes I/O, allocation, cache, and scheduling.

MEMORY

Count retained state

Fast processing can still have O(n) storage.

03 · Growth orders

# O(n): one pass
for event in events: counts[event.ip] += 1

# O(n²) in number of events: each item rescans all items
for event in events:
    duplicates = [other for other in events if other.ip == event.ip]

Use: write the input variable next to every claim. Risk: do not label the first loop “O(1)” because a dict increment is expected O(1); the loop repeats n times.

04 · Honest qualifications

Average, worst, amortized, and output size

Hash lookup is expected O(1), but collisions can approach O(n). Appending to a dynamic list is amortized O(1), with occasional resize work. Sorting comparison-based data is commonly O(n log n), while its memory/call behavior depends on implementation and key functions. If an API must emit k results, it has at least O(k) output work. State these conditions instead of treating Big-O as a benchmark result.

Complexity is not a security proofAn algorithm can be asymptotically good and still be exploitable through huge keys, expensive parsing, unbounded distinct entities, or remote I/O. Bound each attacker-controlled dimension separately.

05 · Space is a first-class cost

# streams input: O(e) counter state, not O(n) event storage
from collections import Counter
counts = Counter()
for event in stream:
    counts[event.ip] += 1

# This changes retained state to O(n):
events = list(stream)

Use: stream when a result can be computed incrementally. Assumption: source order/one-pass semantics meet the algorithm. Risk: Counter is O(e), which is unbounded if every event has a unique key; add expiration/caps.

06 · Audit your analyzer

  1. Define variables.Example: n input lines, e active IPs, r enabled rules, w retained window events.
  2. Mark every repeated operation.Include parse, lookup, list membership, sort, and nested loops.
  3. Compose costs.Sequential operations add; nested repeated operations multiply.
  4. State retained data.Distinguish current batch from long-lived map/window state.
  5. Find the dominant path at target load.Propose a structure or policy change only after the model.

07 · Model plus measurement

from time import perf_counter
def run(events):
    start = perf_counter(); result = analyze(events)
    return result, perf_counter() - start
# Measure bounded synthetic n=1_000, 2_000, 4_000; record Python/platform.

Use: compare scale steps to falsify an implementation claim. Risk: wall time includes CPU frequency, caching, garbage collection, I/O, allocations, and other processes. Never generate huge files blindly; synthetic in-memory fixtures with a fixed maximum are enough to reveal a slope.

08 · Safety

python -m timeit

Measure isolated operations.Use for tiny bounded snippets; it does not represent full pipeline I/O or memory pressure.

cProfile

Find actual hot functions.Use after the model; profiling changes runtime and needs representative sanitized data.

len(active_entities)

Observe state cardinality.Use as a metric with bounds; it alone does not measure object-byte overhead.

Do not hide n² in convenience callsx in list, string concatenation in a large loop, repeated sorting, and nested comprehensions are easy to miss. Keep an operation audit in review for data-dependent code.

09 · Detection scenarios

DEDUP

Each event scans all earlier events

Replace pairwise search O(n²) with a set/map keyed by a stable identifier, then set a cap/expiry for attacker-controlled identities.

RULES

Rule count triples

A naive n·r evaluation may be correct but needs indexing/pre-filtering if r is large. Measure rule selectivity, not only input volume.

REPORT

Top sources report sorts every entity

For a small N and huge e, use a bounded heap; for all results, sorting is purposeful and its cost should be declared.

STATE

One-pass parser still runs out of memory

The retained per-IP map grows with unique keys. Report e and eviction/dropped-key counts alongside throughput.

10 · Practice

Hands-on drills

1. Analyzer operation audit

30 min

Write artifacts/4.3-audit.md with each operation, variables, time, space, average/worst caveat, and the current worst path.

  • Use n/e/r/w rather than an unnamed “input.”
  • Include one nested-loop multiplication.
  • State whether the worst case matters at expected volume.

2. Scale a bounded fixture

25 min

Run a linear scan and an intentional pairwise scan at 1k/2k/4k in memory; save results.

  • Save artifacts/4.3-scale.txt with environment.
  • Compare trend, not exact milliseconds.
  • Do not exceed a predeclared safe size.

3. Fix one costly operation

25 min

Replace a list-membership duplicate check with a set and write before/after complexity.

  • Save code/test result.
  • Explain hash average/worst caveat.
  • State new retained memory cost.
