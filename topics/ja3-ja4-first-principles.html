TLS deeply

Use TLS fingerprints as evidence features, never identity verdicts.

JA3 serializes selected ClientHello lists and hashes them. JA4 is a newer FoxIO fingerprint family with its own documented formats, versions, licensing, and normalizations; use official materials rather than invented formulas.

Why it matters

Fingerprints reduce high-dimensional handshake metadata into comparable features. They help triage/correlation but collide, vary legitimately, can be normalized/middleboxed, and can be mimicked. They are not a user, malware, or intent label.

JA3 from first principles

JA3 string: SSLVersion,Cipher,SSLExtension,EllipticCurve,EllipticCurvePointFormat

Those five fields mean the ClientHello legacy version; offered cipher suites; extension types; the supported_groups values historically called elliptic curves; and EC point formats. Values remain in observed order, with items joined by hyphens and fields by commas. JA3 removes GREASE values but does not otherwise sort the lists. It captures offers, not server selection or encrypted application behavior. Preserve the raw fields and unhashed canonical string alongside the hash.

Hash is a lookup key, not proof

canonical = "771,4865-4866,0-10,29,0"
# MD5(canonical ASCII) = 0cc238f04c0060280fb90190aaa708ae
import hashlib
assert hashlib.md5(canonical.encode("ascii")).hexdigest() == \
    "0cc238f04c0060280fb90190aaa708ae"

Work the example by hand before running it: version 771; suites 4865-4866; extensions 0-10; group 29; point format 0. JA3 uses MD5 as a compact identifier of the canonical ASCII string, not a cryptographic trust decision. Hash collisions and ordinary same-string collisions mean equal outputs do not establish equal client identity.

GREASE normalization

JA3 excludes GREASE values according to its implementation/spec practice. Record parser version and normalization behavior: different normalizers can create different strings. Retaining raw ordered fields lets investigators reproduce the result.

JA4 is a documented family, not a guessed formula

The maintained FoxIO reference expresses fingerprints as structured a_b_c parts. For the TLS-client JA4 method, it sorts cipher and extension lists to reduce order instability and incorporates signature-algorithm information; that is deliberately different from JA3's preserved order. The broader JA4+ suite includes distinct methods such as JA4S for TLS servers and JA4H for HTTP clients—there is no single universal input formula across the family.

Use the exact technical specification and a pinned reference release/commit when computing a value. The repository currently licenses the TLS-client JA4 method under BSD 3-Clause, while other JA4+ methods use FoxIO License 1.1 with different commercial-use terms. Verify the repository's current license and technical details before redistribution or product use, and store that version with the evidence.

Limits and safety

Same browser/client version may vary by OS, policy, extensions, proxy, GREASE, resumption, or updates. Different clients can collide; deliberate spoofing/middleboxes exist. Use supplied sanitized PCAP/learner-owned AbuseGuard corpus only; never capture external traffic, treat hash as malware proof, or expose raw sensitive handshakes.

Evidence workflow

  1. Save authorized raw parser fields and tool/version.
  2. Record normalization and canonical output.
  3. Compare within time/collector context.
  4. Corroborate with account, route, rate, and endpoint evidence.

Detection scenarios

New JA3 in login burst

Check client update/proxy/middlebox and corroborate behavior before escalation.

Same JA3 across accounts

Could be a common browser/library, not coordinated ownership.

JA4 mismatch across tools

Compare FoxIO implementation/version/license and normalization before treating output as conflict.

Fingerprint block proposal

Assess collision/legitimate variation and false-positive blast radius; use it as one feature.
