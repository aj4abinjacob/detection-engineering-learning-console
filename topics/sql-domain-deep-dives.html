Purpose

Why this matters in detection engineering

SQL detection work starts with grain and keys, then joins, filters, windows, aggregates, and plans. A correct-looking query can duplicate entities, leak future rows, scan unnecessary partitions, or change meaning through null handling; explain both result semantics and execution evidence.

A detection engineer must be able to trace how an observation becomes a feature, how that feature supports an inference, and how policy turns the inference into an action. The useful unit for this topic is a timed SQL packet with schema/grain, query, hand-checked fixture, expected rows, query plan, indexes, availability cutoff, and detection interpretation. Preserve enough lineage to reproduce it without collecting content that the decision does not require.

Boundaries

What can go wrong

Closest legitimate lookalike: multiple orders, shared identifiers, missing enrichment, and late outcomes can legitimately create one-to-many or null relationships.

Pipeline or interpretation failure: implicit many-to-many joins, COUNT after multiplication, future labels, SELECT DISTINCT as repair, and plan claims without EXPLAIN hide errors.

Safety boundary: work only with supplied sanitized fixtures or systems and accounts you own and are authorized to test. Minimize identifiers, exclude secrets and content, bound retention and access, and provide an accessible path when an automated action could affect a person.

Do not overclaimThis guide establishes a method for controlled defensive evidence. It does not prove identity, intent, causality, universal tool behavior, or how a third-party system will classify traffic.

Method

A repeatable defensive workflow

  1. Declare the question and scope. Name the owned route, entity, time range, authorization, expected population, and prohibited data before collection.
  2. Version the evidence. Save a timed SQL packet with schema/grain, query, hand-checked fixture, expected rows, query plan, indexes, availability cutoff, and detection interpretation, its schema or tool version, observation point, event and availability times, and missing-value behavior.
  3. Build a negative control. Include multiple orders, shared identifiers, missing enrichment, and late outcomes can legitimately create one-to-many or null relationships and state the response it should receive.
  4. Replay and decide. Recompute from immutable input, compare expected output, inspect false positives and false negatives, then apply state one-row-per grain, pre-aggregate when needed, join with time conditions, test lookalikes, and read estimates versus actuals on safe local data.

Practice

Detection-engineering scenarios

BASELINE

1. The observed distribution changes

Trigger: a monitor for SQL schema/query/plan exercises shifts outside its recorded baseline. Artifact: a timed SQL packet with schema/grain, query, hand-checked fixture, expected rows, query plan, indexes, availability cutoff, and detection interpretation. Reasoning: compare time, producer, release, population, and data quality before attributing the shift to abuse. Boundary: a changed distribution is an observed fact, not a malicious label.

LOOKALIKE

2. A legitimate journey matches the candidate

Trigger: the candidate logic fires on multiple orders, shared identifiers, missing enrichment, and late outcomes can legitimately create one-to-many or null relationships. Artifact: a labeled negative-control replay. Reasoning: preserve the case, inspect which feature dominated, and choose a proportionate fallback. Boundary: do not tune the case away without measuring what new false negatives the change creates.

QUALITY

3. The pipeline changes while the rule stays green

Trigger: implicit many-to-many joins, COUNT after multiplication, future labels, SELECT DISTINCT as repair, and plan claims without EXPLAIN hide errors. Artifact: contract-test result, schema versions, and quality counters. Reasoning: quarantine or mark degraded evidence and restore the producer contract before judging detection quality. Boundary: absence, default values, and parser failures are not benign observations.

POLICY

4. Evidence is strong enough to review, not to punish

Trigger: several versioned signals agree on an unusual owned-lab journey. Artifact: feature lineage, reason codes, policy version, and expected guardrails. Reasoning: state one-row-per grain, pre-aggregate when needed, join with time conditions, test lookalikes, and read estimates versus actuals on safe local data. Boundary: preserve rollback and never infer that an offline score proves the causal benefit of an intervention.
