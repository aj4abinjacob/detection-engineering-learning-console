Why it matters

Threat modeling is a structured design review, not a vulnerability prediction oracle. It turns assumptions into reviewable requirements and testable abuse cases.

Scope AbuseGuard v1

Declare in-scope local browser/client, reverse proxy, FastAPI app, session store/database, operator, and telemetry. State exclusions such as third-party identity provider or cloud control plane rather than silently assuming safety.

Assets

Protect account data, session state, password verifiers, tenant records, detection configuration, availability, audit evidence, and deployment secrets. Rank impact and owner.

Actors and capabilities

Model anonymous user, authenticated tenant user, tenant admin, operator, compromised browser, and external network actor. Describe allowed interfaces, not motives or real targets.

Context diagram

Browser -> TLS/proxy -> AbuseGuard -> database; operator -> admin interface

Mark trust boundaries where identity, protocol, privilege, or ownership changes. This is a local design diagram, not live reconnaissance.

Container view

Separate proxy, app/API/templates, persistence, and logging/telemetry. Note secrets/configuration and client-IP transformation at each boundary.

Data-flow diagram

For register/login/request/export paths, label source, transformations, storage, sink, and trust boundary. Include error/log paths: sensitive data often leaks there.

STRIDE per element

Apply spoofing, tampering, repudiation, information disclosure, denial of service, and elevation of privilege to each process/store/flow. Convert plausible threats into controls, owners, evidence, and tests.

Security requirements

Examples: server-side tenant authorization, session rotation, bounded request size/rate, parameterized DB access, no secrets in logs, trusted proxy chain. Requirements must be observable pass/fail statements.

Defensive scenarios

Cross-tenant export

A design review follows report_id from the route through the export queue and finds no trusted tenant scope at execution. Record the affected flow, asset classification, principal/tenant source, queue message fields, and policy point; require tenant-scoped lookup plus a two-tenant denial test. A guessed ID is an input fact, not proof that data crossed the boundary.

Spoofed client IP

Local telemetry changes when the same request supplies a forged X-Forwarded-For. Inspect socket peer, each owned hop's strip/set behavior, app trust configuration, and final normalized address, then add direct and through-proxy tests. NAT and Docker bridges legitimately alter peer addresses, so the threat-model artifact must distinguish peer fact from inferred end client.

Login flood

Authentication latency and verifier CPU rise during a synthetic loopback burst. Use route/outcome counts, bounded client keys, queue/worker saturation, and latency percentiles to trace the resource path; define a cap, generic response, alert, and recovery test. A shared NAT or password-manager retry can resemble a burst, so avoid permanent account denial from rate alone.

Error disclosure

A malformed local request causes a stack trace containing a synthetic session value in an operator log. Trace request → exception mapper → structured logger → retention sink, identify who can read each artifact, and add response/log redaction tests. Preserve only a sanitized event and treat the exposed value according to incident policy; one safe HTTP error does not prove downstream logs are safe.
