Fingerprint surface · rendering

See rendering variation as noisy, costly evidence.

Canvas, WebGL, and Web Audio can expose reproducible rendering outcomes. Their usefulness comes with collision, change, compatibility, and privacy risk—so a defensive system should prefer purpose-bound coarse features and never equate a render result with a person or device identity.

Why this matters

Rendering APIs let a page ask a browser to draw, expose a graphics capability, or process audio. Differences in implementations can become a correlation feature. Detection engineering must understand both the mechanism and the failure modes: routine browser/GPU updates, privacy protections, remote desktops, accessibility configuration, and virtualized/mobile environments can change or suppress the feature.

Mental model: code path → output → derived feature

Declared testText, shapes, shader, or offline audio graph.
→
ImplementationBrowser, OS, driver, CPU/GPU, settings, and policy render it.
→
Derived featureCoarse bucket or hash, with test version and uncertainty.

A result is an observation of this pipeline at this time—not a permanent device serial number.

Canvas: text and pixels are implementation output

A 2D canvas test typically chooses a fixed size, font stack, text, compositing mode, and shapes, then reads pixels or serializes an image. Font fallback, text rasterization, antialiasing, color management, browser build, display/GPU path, and privacy settings can alter the output. The exact drawing recipe determines what is being measured. A same output can be shared by many devices (collision); a changed output can be the same device after an update (instability).

// Owned test fixture: record capability, test version, and byte length only.
// It intentionally does not exfiltrate pixels or create an identity token.
const c = document.createElement('canvas');
const ok = Boolean(c.getContext('2d'));
const evidence = { testVersion: 1, canvas2dAvailable: ok, width: c.width, height: c.height };

This first-party fixture is suitable for a local AbuseGuard lab. It checks capability rather than collecting a fingerprint. Do not replace it with code to mimic, conceal, or defeat a third party’s rendering checks.

WebGL: capabilities and renderer paths

WebGL exposes a graphics API and selected parameters. A capability result depends on browser support, GPU/driver, hardware acceleration, enterprise policy, virtualization, sandboxing, and privacy defenses. Detailed renderer/vendor values can be high-entropy and may be unavailable by design. Use a capability category when it answers the operational question (for example, whether an owned visual challenge can render); do not persist raw renderer strings without a reviewed necessity.

Audio: signal processing is also variable

An offline audio graph can produce samples whose floating-point and implementation details vary across engines and environments. Audio hardware is not required for every offline rendering path, but API availability, suspended state, browser policy, rounding, engine version, and platform still matter. Audio output can become an identifying feature if collected at scale. Never request microphone input for fingerprinting, and do not treat audio API absence as abusive behavior.

Stability, uniqueness, and collision are separate measurements

QuestionMeasure on consented, first-party dataFailure mode
StabilityHow often one known test environment changes across time/version.Updates look like new devices.
UniquenessHow often a feature separates the defined population.High entropy increases privacy cost.
CollisionHow often distinct known environments share a result.Different users are incorrectly joined.
AvailabilityHow often the API/test is unavailable or permission/policy-limited.Compatibility is mislabeled as risk.

Sample sizes, population definition, test version, and collection point determine all four numbers. A short internal comparison is not a population-wide identity study.

Privacy and accessibility are design constraints

First ask whether a low-entropy server-side or account-flow signal answers the same question. If rendering evidence is justified, document purpose, field granularity, test version, retention, access, consent/notice basis, and deletion path. Store derived coarse outcomes rather than raw images, pixel arrays, audio buffers, or detailed GPU strings. Provide an accessible alternate path for WebGL/canvas failures, keyboard-only users, screen readers, reduced-motion users, low-power devices, and privacy-hardened browsers.

Do not overclaimEntropy describes variation in a population under assumptions; it is also a privacy cost. It does not mean “this identifies a human,” establish consent, or justify a permanent cross-context identifier.

First-party defensive workflow

  1. Specify the business question. Example: can the owned page offer a WebGL-based visual control?
  2. Use the least identifying field. Record an availability bucket and fixture version before considering a derived output.
  3. Measure change and harm. Compare approved test environments over updates and evaluate alternate-path completion.
  4. Corroborate before response. Combine with route, rate, account outcome, and a safe step-up—not a direct block.

Detection-engineering scenarios

1. Rendering bucket changes after a release

Trigger: a returning account’s coarse canvas outcome changes. Artifact: test version, browser-version change, prior success, and capability bucket. Observation point: consented first-party page telemetry. Reasoning: attribute the change to an update candidate and compare a controlled test device before escalating. False-positive boundary: do not call it a device change or takeover without independent account-risk evidence.

2. WebGL unavailable on an accessibility path

Trigger: an owned visual control cannot initialize. Artifact: capability outcome and fallback completion rate. Observation point: owned client and application logs. Reasoning: route the user to an equivalent accessible method and monitor reliability. False-positive boundary: disabled WebGL can be policy, hardware, privacy, or assistive setup—not automation.

3. Shared audio-derived bucket in a signup spike

Trigger: many requests share a bucket during abuse. Artifact: aggregate bucket counts, route velocity, account outcomes, and test version. Observation point: first-party signup telemetry. Reasoning: use it as one cluster feature alongside server evidence and assess how common the bucket is in known-good traffic. False-positive boundary: a collision is expected; never treat a shared value as a coordinated actor proof.

4. Privacy review rejects raw pixel storage

Trigger: a proposed detector asks to retain canvas images. Artifact: data-flow review and a capability-only alternative. Observation point: design review. Reasoning: replace raw output with purpose-limited buckets or eliminate the collection. False-positive boundary: a technically useful feature is not automatically necessary or proportionate.

Artifact-producing drills

1. Explain the source

Read the canvas-related code in the current open-source FingerprintJS educational baseline or a supplied fixture. Save artifacts/rendering/canvas-explanation.md explaining the declared draw, the output read, likely sources of variation, and why it is not a device identifier.

  • Do not run it against a third-party site or use it for tracking.
  • Mark source/version and inference separately.

2. Capability-only owned fixture

Run a local AbuseGuard fixture that records only canvas/WebGL/Web Audio availability and fixture version. Save artifacts/rendering/capabilities.json for three approved environments.

  • No raw pixels, audio samples, renderer string, account ID, or third-party endpoint.
  • Include a privacy/accessibility configuration if available.

3. Stability and privacy note

Save artifacts/rendering/stability-privacy.md with a hypothetical collision, update-change, and unavailable case; propose retention, fallback, and corroboration requirements.

  • Define stability, uniqueness, collision, and availability in your own words.
  • Explain the result without AI.
