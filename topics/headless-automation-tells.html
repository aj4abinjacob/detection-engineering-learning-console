Fingerprint surface · automation

Measure browser modes on your own app, then bound the claim.

Headless, headed, automated, and interactive browsers overlap substantially. navigator.webdriver, timing, capability outcomes, and implementation artifacts can be useful context in a first-party lab, but no page-side tell proves intent, and no server-side decision should rest on a single signal.

Why this matters

Browser automation powers CI, synthetic monitoring, accessibility testing, visual regression, data entry, and internal support. Abuse also uses automation. The defensible question is therefore not “is this browser human?” but “does this observed first-party flow, combined with server evidence, merit an approved response?”

Mental model: page observations are local and conditional

Mode / launch configHeaded or headless; test framework; browser version.
→
Page runtimeNavigator/capability/timing outcomes visible to an owned page.
→
Server eventOnly telemetry the page chooses to send plus ordinary HTTP facts.

The server does not see a browser’s local property unless the page or client reports it. A missing report may simply be a compatibility or network outcome.

Headed, headless, and automation are different axes

Headed means a visible browser UI; headless means a browser mode without the usual visible UI. Automation means a controller drives the browser, often through WebDriver or a browser protocol. A headed browser can be automated, a headless browser can be a legitimate test, and implementation differences evolve with browser versions. Record browser version, OS, launch mode, framework, and test purpose before comparing anything.

navigator.webdriver is an explicit cooperation signal

The standardized read-only navigator.webdriver property reports whether the user agent is controlled by automation in defined cases. It can be true in standard automation contexts and false in ordinary contexts; it is neither a security proof nor an entitlement decision. It can also cause legitimate CI and accessibility test traffic to look unusual. Use it to label owned test traffic, validate monitoring coverage, or select a controlled test path—not to block unknown users.

Do not create a “masking” recipe. A controlled first-party validation can test whether a detector’s reliance on a single property is brittle, but the test artifact must be an explicit owned fixture marker and a measured outcome—not reusable concealment code.

Timing differences are flow evidence, not proof

Automation may submit faster or with more regular cadence, but a password manager, autofill, keyboard macro for accessibility, internal testing, low-latency network, or returning user may do the same. Browser scheduling, CPU load, page hydration, background tabs, and remote desktops change timings. Bucket time coarsely; use server timestamps and route sequence as the primary evidence; never collect raw keystrokes or require pointer behavior.

Explicit first-party test-only probe fixture

// Serve only from local/staging AbuseGuard with an explicit test label.
// This measures a declared property; it does not modify or hide browser state.
const probe = {
  fixtureVersion: 1,
  webdriverReported: navigator.webdriver === true,
  languageCount: navigator.languages?.length ?? 0,
  viewportBucket: "coarse-bucket"
};
console.log(JSON.stringify(probe)); // Save locally as a labelled test artifact.

Run this fixture in approved headed and headless modes on the same owned app. Keep results local or send them under an approved telemetry policy with a test-run label. Do not run detection comparisons on another site, and do not turn measurements into instructions for altering properties, launch flags, or browser behavior.

Response and safety boundaries

Protect actual harms—credential stuffing, mass account creation, inventory abuse—with route-specific rate limits, account controls, verified partner/API design, and accessible step-up options. Evaluate false positives across mobile, privacy-hardened, assistive, remote/virtual, and automated QA clients. Version every detector and retain a rollback. A production rule that blocks on headless or webdriver alone is a reliability and accessibility risk.

Detection-engineering scenarios

1. CI creates a signup alert

Trigger: a velocity rule fires during a release. Artifact: explicit CI run ID, owned probe output, test account list, and server timestamps. Observation point: AbuseGuard staging signup route. Reasoning: correlate the approved test window and label, then exclude only that known run from alert noise. False-positive boundary: webdriver=true does not authorize any arbitrary automated request.

2. Headless update changes a capability

Trigger: an approved synthetic monitor starts reporting a changed property. Artifact: browser/framework version, fixture version, and baseline comparison. Observation point: owned monitoring page. Reasoning: investigate version and test-environment changes before modifying a detector. False-positive boundary: the change does not establish an evasion attempt or user risk.

3. Rapid login attempts lack probe telemetry

Trigger: login failures increase and optional client telemetry is missing. Artifact: server rate, account outcomes, response status, and client-report availability. Observation point: owned login service. Reasoning: use server-side limits and an accessible verification path; inspect page-delivery failures separately. False-positive boundary: missing JavaScript/reporting is not evidence of headless automation.

4. A proposed “headless block” harms users

Trigger: a team proposes blocking an unusual navigator value. Artifact: proposed rule, owned comparison matrix, accessibility test results, and expected business impact. Observation point: pre-production review. Reasoning: replace it with corroborated risk and observe-first measurements. False-positive boundary: common browser variability and legitimate automation make a one-feature block indefensible.

Artifact-producing drills

1. Owned headed/headless matrix

Run the explicit fixture on local/staging AbuseGuard in one approved headed and one approved headless browser mode. Save artifacts/automation/mode-matrix.json with browser/framework/version, test label, and coarse outcomes.

  • Do not target any third-party site.
  • Write one benign explanation for each difference.

2. Single-signal brittleness review

Save artifacts/automation/brittleness-review.md describing a hypothetical detector that depends only on navigator.webdriver, the explicit test-only fixture used to measure it, and the corroborating evidence it would need.

  • No property masking, launch-flag alteration, or stealth code.
  • State how legitimate CI and accessibility users are handled.

3. Safe response plan

Save artifacts/automation/response-plan.md for a signup abuse event: server trigger, optional page evidence, accessible step-up, metric, rollback, and owner.

  • Include API/mobile and privacy-tool outcomes.
  • Explain it aloud without AI.
