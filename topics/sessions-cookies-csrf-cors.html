Bind browser state to intent.

Cookies, sessions, CSRF, and CORS are different controls. CORS is never authorization.

Why it matters

Browsers attach cookies automatically in contexts. State-changing cookie-auth requests need a server-checked intent signal and current server-side authorization.

Opaque sessions

Generate IDs with CSPRNG, store state/verifier server-side, set expiry/idle/logout policy, and evaluate authz on every request.

Cookie attributes

Secure restricts transport to HTTPS; HttpOnly limits JavaScript reading but not CSRF; SameSite constrains some cross-site sending; Path/Domain minimize scope; Max-Age bounds life.

Rotate session state

Rotate/invalidate ID after login, reset, MFA elevation, or privilege change. Never adopt attacker-chosen session ID.

CSRF tokens

Require a server-validated anti-CSRF token for unsafe cookie-authenticated actions. A synchronizer token is generated server-side, bound to the user's session, rendered into the form, and compared on submission; a signed double-submit design has different storage and binding assumptions. Keep state-changing operations off safe methods, validate Origin/Referer as defense in depth where appropriate, and test valid, missing, invalid, expired, and cross-session token cases. The token proves request intent under the chosen model, not authorization.

SameSite is defense in depth

Browser/navigation behavior varies; document legitimate cross-site flows and do not rely on SameSite alone for sensitive state changes.

Narrow CORS

Allow exact origins, methods, headers, and credentials only when necessary. Credentialed CORS cannot use wildcard origin. Preflight is browser policy, so non-browser callers still require authn/authz.

from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.example.test"],
    allow_credentials=True,
    allow_methods=["GET", "POST"],
    allow_headers=["Content-Type", "X-CSRF-Token"],
)

Use the exact deployed origin, including scheme and port; avoid reflecting arbitrary Origin values. This permits selected browser reads—it does not make the origin trusted to act as a user.

Local tests

Assert Set-Cookie attributes, post-login rotation, CSRF rejection, and allowed/disallowed origin/preflight using synthetic local identities.

Safety

Secure-cookie behavior needs HTTPS/proxy policy; local exceptions must not weaken deployment defaults. Never log session IDs, CSRF tokens, or authorization headers.

Defensive scenarios

Fixation

A regression test finds the same opaque session identifier before and after synthetic login. Inspect only hashed session references, issuance/authentication timestamps, principal binding, and revocation state in the server store. The login must create a new identifier and invalidate the pre-auth value; a changed cookie without revoked server state is incomplete evidence.

Cross-site POST

Local test telemetry shows a state-changing request with a valid session cookie, foreign Origin, and missing CSRF token. Confirm the route is unsafe, the server rejected before mutation, and the decision event contains a safe reason—not token/cookie content. Browser extensions, privacy tools, and older clients can affect Origin/Referer, so the session-bound token remains the primary proof.

Wildcard CORS

A preflight response reflects an unexpected synthetic origin while allowing credentials. Save the request/response headers, deployed middleware configuration, route, and release, then test the exact approved and denied origins including scheme/port. Even a corrected CORS policy protects browser reads only; direct non-browser requests must still fail authn/authz independently.

Admin route

An authenticated non-admin receives a 200 from a direct request although the UI hid the link. Correlate the pseudonymous principal, current server role, route template, policy reason, and response status; reproduce with synthetic viewer/admin identities. The failure is missing server authorization, not a cookie, CSRF, or CORS defect.
