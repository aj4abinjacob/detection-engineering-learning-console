Practical field guide · Git

Make change recoverable.

Git is the safety system around your code, rules, queries, runbooks, and infrastructure. This guide gives you the mental model and small command set needed to work confidently—especially when a merge goes wrong or a commit seems lost.

01 · Purpose

Why Git matters in detection work

A detection is a production decision expressed as code. Git lets you prove what changed, review why it changed, test it in isolation, and return to a known-good version.

01 · AUDITABILITY

Every change has a trail

A commit connects an exact snapshot to an author and an explanation. During an incident, you can answer “what changed?” without relying on memory.

02 · SAFE EXPERIMENTS

Branches isolate risky work

Tune a threshold, rewrite a Sigma rule, or test a parser without destabilizing the version others depend on.

03 · REVIEW

Diffs make reasoning visible

A reviewer can inspect a five-line logic change instead of rereading the whole file. That is how false-positive risk gets caught before deployment.

04 · RECOVERY

Mistakes become reversible

Revert a bad shared change, restore a deleted file, or recover a commit through the reflog. Confidence comes from knowing the escape routes.

05 · REPRODUCIBILITY

A commit identifies the evidence

Pin an evaluation report, rule bundle, and test corpus to one commit SHA so another engineer can reproduce the result.

06 · COLLABORATION

Parallel work can converge

Multiple engineers can change different rules at the same time, then merge their work with conflicts called out explicitly.

The useful definitionGit is a local version-control system. It stores snapshots of a project and a graph of how those snapshots relate. GitHub, GitLab, and Bitbucket host Git repositories and add collaboration features; they are not Git itself.

02 · Mental model

Think in snapshots and pointers

Most Git confusion disappears when you stop thinking “save/upload” and track which of three places currently contains each version of a file.

Working treeFiles you can see and edit right now. Changes here are not yet selected for the next snapshot.git diff
→
Staging areaAlso called the index. The exact content selected for the next commit.git diff --staged
→
RepositoryCommitted snapshots and the graph connecting them, stored inside .git.git log

git add moves content into the staging area. git commit records the staged snapshot. Editing after git add creates a new unstaged difference.

Commits form a graph

A──B──C────────M main ╲ ╱ D──E─── tune/login-rule HEAD → main → M

A commit points to a complete project snapshot, its parent commit or commits, and metadata. A branch such as main is only a movable name pointing at one commit. HEAD identifies what you currently have checked out—usually a branch.

Three distinctions to keepA commit is a snapshot, not merely a diff. A branch is a pointer, not a folder or copy. A remote such as origin is another repository, not an automatic backup.

The object model, briefly

ObjectWhat it storesWhy you care
BlobFile contentIdentical content is stored once and addressed by its hash.
TreeDirectory listing: names, modes, and blob/tree referencesA commit can identify a complete filesystem snapshot.
CommitRoot tree, parent(s), author, time, messageThis is the unit you inspect, share, revert, and review.
TagA stable name, often for a release commitUse it to mark a known rule-pack or deployment version.
 
# Follow the current commit to its tree, then inspect an object
git cat-file -p HEAD
git cat-file -p HEAD^{tree}

03 · Before the first commit

Set up identity and safe defaults

Configure your author identity once. Use the identity your team expects; the email may be tied to commit signing or your repository-hosting account.

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

# See where every active value came from
git config --list --show-origin

Start or copy a repository

git init

Start tracking the current directory.Creates a hidden .git directory. It does not commit files or publish anything.

git clone <url>

Copy an existing repository.Downloads its history, creates remote-tracking branches, and checks out the default branch.

Before you add anythingCreate a .gitignore for logs, virtual environments, generated data, credentials, local config, and large captures. Git is not a secrets store. If a real secret is ever committed, assume it is compromised and rotate it—even if you later delete it from history.
# A small Python / detection-project .gitignore
.venv/
__pycache__/
*.py[cod]
.env
*.log
captures/
reports/private/

# Force-add only when a broad ignore rule hid a known-safe file
# git add -f reports/example-sanitized.json

04 · Core working set

The everyday workflow

Use this loop: orient, inspect, stage intentionally, inspect again, commit one coherent idea.

git status --short
git diff
git add rules/suspicious_login.yml tests/test_suspicious_login.yml
git diff --staged
git commit -m "Tune suspicious-login threshold"
git log --oneline --graph --decorate -8
git status --short

Orient before acting.Shows tracked, modified, staged, and untracked files. Run it after any surprising command.

git diff

Review unstaged edits.Answers: “What have I changed in my working tree?” Add -- path to focus on one file.

git diff --staged

Review the next commit.Answers: “What exactly will be recorded if I commit now?”

git add <path>

Stage selected content.Prefer explicit paths. git add -p lets you select individual hunks from a mixed file.

git commit -m "…"

Record the staged snapshot.Write the reason or outcome: “Reject empty user-agent values,” not “update file.”

git log --oneline --graph --decorate --all

See the commit graph.Useful when a merge, rebase, branch, or detached HEAD feels confusing.

git show <sha>

Inspect one commit.Shows its metadata and patch. Use git show <sha>:<path> for a file as it existed then.

git blame <path>

Find context, not a culprit.Maps lines to commits so you can read the decision that introduced a line.

A good commit is a review unitKeep code and its focused test together. Avoid mixing threshold tuning, formatting, dependency updates, and documentation in one commit. Small coherent commits make review, bisecting, and reverting safer.

05 · Parallel work

Branches, merges, and remotes

A branch gives a line of work a name. The usual team flow is: update your view of the remote, create a focused branch, commit, push it, and request review.

git switch main
git pull --ff-only
git switch -c tune/impossible-travel

# edit, test, add, commit
git push -u origin tune/impossible-travel

The branch commands

git branch

List local branches.Use -a for local and remote-tracking branches, or -vv to see upstream relationships.

git switch -c <name>

Create and enter a branch.It begins at the currently checked-out commit unless you supply another starting point.

git switch <name>

Change branches.Your working tree is rewritten to match the target branch. Commit or stash relevant work first.

git merge <branch>

Bring another line of work into the current branch.A fast-forward just moves the pointer; diverged histories require a merge commit.

Remote vocabulary

Command / nameMeaningWorking tree changes?
originConventional nickname for the repository you cloned. It can be renamed and is not inherently special.No
origin/mainYour local record of where the remote's main was at the last fetch.No
git fetch originDownload new objects and update remote-tracking refs without integrating them.No
git pull --ff-onlyFetch, then advance the current branch only when no merge commit is needed.Yes
git pushSend commits and update an allowed branch on the remote.No

Resolve a merge conflict deliberately

  1. Read the state. Run git status; it names unmerged paths and the operation in progress.
  2. Open every conflicted file. Between <<<<<<< and ======= is one side; between ======= and >>>>>>> is the other.
  3. Decide the correct final content. Do not mechanically choose “ours” or “theirs”; both changes may be needed.
  4. Remove the markers and test. For a detection rule, validate syntax and replay positive and negative fixtures.
  5. Stage and complete. Run git add <resolved-path>, verify git status, then git commit.

Need to stop?git merge --abort returns to the pre-merge state when possible. For a rebase conflict, use git rebase --abort. Read git status before choosing either.

06 · Safety & recovery

Undo the right layer

“Undo” is not one operation. First identify whether the mistake is in the working tree, staging area, local history, or shared history.

SituationCommandRisk
Unstage a file; keep its editsgit restore --staged <path>Safe
Discard unstaged edits to a tracked filegit restore <path>Destructive to edits
Fix the most recent local commitgit commit --amendRewrites commit
Undo a commit already sharedgit revert <sha>Safe for shared history
Move branch back; keep changes stagedgit reset --soft <target>Local history only
Move branch back; keep changes unstagedgit reset --mixed <target>Local history only
Make tracked files exactly match targetgit reset --hard <target>Destroys tracked work
Find a recently lost commitgit reflogRead-only
Preserve a found commitgit switch -c recovered <sha>Safe

Revert versus reset

SHARED HISTORY

Prefer git revert

It adds a new commit that applies the inverse change. Teammates keep a consistent history, and the undo itself remains auditable.

UNPUSHED LOCAL HISTORY

Use git reset carefully

It moves the current branch pointer. Choose soft, mixed, or hard according to what should happen to the index and working tree.

Reflog: your local safety journal

Git records recent movements of local references: commits, resets, rebases, checkouts, and deleted branch tips. When you think work disappeared, stop changing history and inspect this journal.

git reflog --date=local
# Find the SHA before the mistaken reset/rebase/branch deletion
git show <sha>
git switch -c recovered-work <sha>

The reflog is local, temporary, and not pushed. It is a safety net, not a backup strategy.

Detached HEAD is a state, not a disaster

When HEAD points directly to a commit instead of a branch, you can inspect and run old code safely. If you create commits there, give them a branch name before switching away.

# Enter detached HEAD to inspect an older snapshot
git switch --detach HEAD~2

# Leave without keeping new commits
git switch main

# Or preserve work created while detached
git switch -c keep-detached-work
Pause before destructive commandsBefore reset --hard, clean, forced pushes, or history rewrites: run git status, inspect the target SHA, and make a temporary branch if the work matters. Never copy a “fix” from the internet without knowing which layer it changes.

07 · On the job

Detection-engineering scenarios

Commands become durable knowledge when each one is tied to a decision you will actually make.

RULE CHANGE

Tune a noisy login detection

Create a branch, update the rule and fixtures together, inspect the staged diff, and commit the measurable reason for the change.

git switch -c tune/login-velocity
# edit rule + add a legitimate high-velocity fixture
./test-rules.sh rules/login_velocity.yml
git add rules/login_velocity.yml tests/login_velocity/
git diff --staged
git commit -m "Reduce login-velocity false positives for NAT traffic"

Why Git helps: the pull request can show the rule logic, test evidence, and reason in one reviewable unit. If production quality degrades, the exact change is revertible.

INCIDENT

A recently deployed parser breaks ingestion

Identify the deployed commit, verify the suspected change, and create a new revert commit. Avoid rewriting a shared production branch during an incident.

git log --oneline --decorate -12
git show <suspect-sha>
git revert <suspect-sha>
# run focused tests, then push the revert through the emergency process

Why Git helps: recovery is fast and auditable. The original change and its inverse both remain available for post-incident analysis.

EVIDENCE

Make an evaluation result reproducible

Record the exact commit alongside corpus version, command, environment, and output. “Tested the latest rule” is not reproducible; a commit SHA is.

git rev-parse HEAD
git status --short
# Expect no uncommitted changes before claiming this SHA identifies the run

./evaluate --corpus corpus-v3.json > reports/run-v3.txt

Why Git helps: another engineer can check out the SHA and distinguish code drift from data drift or environment differences.

SECRET

A credential appears in your change

If it is only staged, unstage it, remove the secret from the file, and add an ignore rule where appropriate. If a real secret was committed or pushed, rotate/revoke it first and follow the team's history-remediation process.

# Secret staged but not committed
git restore --staged .env
# add .env to .gitignore, then verify
git status --short

# Check whether a path exists in committed history
git log --all -- .env

Why Git helps: it makes exposure discoverable, but deleting a file in a later commit does not erase earlier copies. Rotation is the security control.

DEBUGGING

Find when a regression began

When you have a reliable pass/fail test, git bisect performs a binary search across history to locate the first bad commit.

git bisect start
git bisect bad                 # current commit fails
git bisect good <known-good-sha>
# test the checked-out commit; mark it good or bad until Git identifies one
git bisect reset

Why Git helps: a hundred candidate commits require roughly seven checks instead of reading a hundred diffs. The test supplies the truth; Git supplies the search.

08 · Practice

Week 0 hands-on drills

Run these without AI in a disposable directory. Save the terminal transcript and annotate every step you did not understand. These drills intentionally manufacture recoverable problems.

1. Commit, branch, and merge

10–15 min

Build the normal workflow before breaking it.

mkdir git-drills && cd git-drills
git init
printf 'threshold: 5\n' > rule.yml
git add rule.yml && git commit -m "Add baseline rule"

git switch -c tune-threshold
printf 'threshold: 8\n' > rule.yml
git add rule.yml && git commit -m "Tune threshold"

git switch main
git merge tune-threshold
git log --oneline --graph --decorate --all
  • Explain why this merge is probably a fast-forward.
  • Point to HEAD, main, and tune-threshold in the graph.
  • Show the commit and file snapshot with git show.

2. Manufacture and resolve a conflict

15–20 min

Create divergent commits that edit the same line.

git switch -c rule-a
printf 'threshold: 10\n' > rule.yml
git commit -am "Raise threshold on rule-a"

git switch main
printf 'threshold: 12\n' > rule.yml
git commit -am "Raise threshold on main"

git merge rule-a
# Read git status and rule.yml. Choose the correct final value,
# remove every conflict marker, then:
git add rule.yml
git commit
git log --oneline --graph --decorate --all
  • Explain each conflict marker before deleting it.
  • Explain why Git could not choose the correct threshold.
  • Identify both parents of the merge commit.

3. Lose a commit and recover it

10–15 min

Delete the only branch naming a disposable commit, then recover it from the reflog.

git switch -c disposable-spike
printf 'experimental: true\n' >> rule.yml
git commit -am "Try experimental rule"
git log -1 --oneline

git switch main
git branch -D disposable-spike

# The commit no longer has a branch name. Find and recover it:
git reflog
git show <lost-sha>
git switch -c recovered-spike <lost-sha>
  • Show that recovered-spike points to the lost commit.
  • Explain why the object was still recoverable after branch deletion.
  • State why reflog is not a remote backup.

4. Enter and exit detached HEAD

10 min

Inspect an earlier snapshot without moving a branch.

git switch main
git switch --detach HEAD~1
git status
git log -3 --oneline --decorate

# Optional: make a disposable commit here, then preserve it with:
git switch -c saved-detached-work

# If you made no commit, simply leave with:
git switch main
  • Explain what HEAD points to while detached.
  • Explain why switching away can make a new detached commit hard to find.
  • Demonstrate both “inspect only” and “preserve new work” exits.
Artifact to saveRecord the session with script git-drills.txt on macOS/Linux, run all four drills, then type exit. Add a short git-drills-notes.md explaining why each recovery worked. Do not clean up the transcript to hide mistakes; the mistakes are the diagnostic.
