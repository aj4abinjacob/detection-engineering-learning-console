Make a related change wholly true, or leave the prior truth intact.

Transactions group statements into an atomic unit. Constraints reject invalid states; rollback restores the unit’s pre-transaction state. Isolation defines what concurrent transactions can observe—not an excuse to skip a concurrency design.

01 · Purpose

Integrity is a detection prerequisite

If a backfill records a derived alert but not the event it refers to, a dashboard can show an impossible story. Transactions and constraints let you define all-or-nothing state changes and prove that a failed step did not leave an orphan behind.

ATOMICITY

All or nothing

The committed unit appears complete; rollback abandons its changes.

CONSISTENCY

Invariants continue

Constraints and application rules define valid states before and after a commit.

ISOLATION

Concurrency has rules

Transactions do not all see each other’s intermediate work, but levels have tradeoffs.

DURABILITY

Commit survives defined failure

Database durability depends on engine/configuration/storage guarantees, not a Python print.

02 · Mental model

One boundary surrounds a coherent state transition

BEGINEstablish transaction context.pending
→
StatementsEvery change must preserve/check rules.valid or error
→
COMMIT / ROLLBACKPublish all or discard all.durable / undone

Autocommit means each statement can be its own transaction. Explicitly group only changes that must succeed together; long transactions hold locks/resources and make concurrency worse.

03 · ACID

Use the words precisely

Atomicity prevents partial committed units. Consistency means a transaction moves from one state satisfying declared invariants to another; it is not a promise that values are business-correct. Isolation describes concurrent visibility/anomalies. Durability is the committed data’s survival according to the engine’s configured persistence guarantees. Backups, replication lag, and application caches are separate concerns.

04 · Control statements

Make the mutation boundary visible

-- Disposable local SQLite fixture only.
BEGIN;
INSERT INTO accounts(account_id, handle, created_at)
VALUES (1, 'lab-alex', '2026-01-01T00:00:00Z');
INSERT INTO access_requests
  (request_id, observed_at, source_ip, status, path, account_id)
VALUES
  (10, '2026-01-01T00:01:00Z', '198.51.100.8', 401, '/login', 1);
COMMIT;

-- On any intended failure path:
ROLLBACK;
BEGIN

Start an explicit unit of work.Use before related DML. It mutates transaction state and may obtain locks; never paste it into an unknown production session.

COMMIT

Make successful changes visible/durable per engine guarantees.Use only after checking intended validations. It cannot be casually undone; use a new compensating transaction, not hope.

ROLLBACK

Discard uncommitted changes in the current transaction.Use after error or deliberate test. It cannot undo a prior committed transaction.

05 · Failure is valuable evidence

Let a constraint fail, then prove no partial state

BEGIN;
INSERT INTO accounts(account_id, handle, created_at)
VALUES (2, 'lab-bea', '2026-01-01T00:00:00Z');
-- Fails if status CHECK enforces 100..599:
INSERT INTO access_requests
  (request_id, observed_at, source_ip, status, path, account_id)
VALUES
  (11, '2026-01-01T00:02:00Z', '198.51.100.8', 999, '/login', 2);
ROLLBACK;
SELECT * FROM accounts WHERE account_id = 2; -- no row after rollback

Constraint timing matters. PostgreSQL supports deferrable constraints for specific use cases; SQLite supports immediate enforcement patterns but differs. In PostgreSQL, after an error within a transaction, the transaction is generally aborted: subsequent commands return “current transaction is aborted” until ROLLBACK (or an appropriate savepoint rollback). Do not catch an error and keep issuing writes as if nothing happened.

06 · Concurrent reality

Isolation levels choose anomalies and costs

ConceptQuestionDesign response
Dirty readCan I see another transaction’s uncommitted work?Most production engines prevent this; do not rely on it for coordination.
Nonrepeatable readCan a reread change after another commit?Choose isolation/locking or redesign the operation.
PhantomCan a predicate return new matching rows?Understand snapshot/predicate behavior in target DB.
Serialization anomalyCan individually valid transactions conflict?At SERIALIZABLE, be prepared to retry the whole transaction safely.

PostgreSQL’s default is Read Committed; it offers Repeatable Read and Serializable with documented semantics. SQLite serializes writes (single writer) and its locking/journal mode changes concurrency behavior; it does not expose PostgreSQL’s isolation-level menu. Read the engine’s current docs before designing a concurrent enforcement workflow.

07 · PostgreSQL

Errors abort the transaction until recovery

BEGIN;
INSERT INTO accounts(handle, created_at)
VALUES ('lab-alex', '2026-01-01T00:00:00Z');
-- Suppose this violates a unique constraint.
INSERT INTO accounts(handle, created_at)
VALUES ('lab-alex', '2026-01-01T00:00:01Z');
-- PostgreSQL now requires ROLLBACK (or ROLLBACK TO a prior SAVEPOINT).
ROLLBACK;

Use SAVEPOINT ingest_batch only when a partial, documented recovery boundary is required; ROLLBACK TO SAVEPOINT ingest_batch does not replace a clear outer transaction policy. Serialization failures/deadlocks can require a retry from the start, provided the operation is idempotent or has a durable idempotency key.

08 · SQLite

Small local labs still need explicit assumptions

Python’s sqlite3 may start an implicit transaction for DML depending on connection configuration; use an explicit transaction/context manager in tests and inspect your Python version’s documentation. Enable FKs with PRAGMA foreign_keys = ON. SQLite’s BEGIN IMMEDIATE can acquire write intent earlier; it can also produce lock contention. This is for controlled local experiments, not a production lock-management recipe.

09 · Safety

Transactions are not a sandbox

BEGIN followed by COMMIT changes data; EXPLAIN ANALYZE in PostgreSQL runs its statement. Use local synthetic SQLite fixtures, an explicitly named disposable database, and least-privilege credentials. Never “test rollback” on an unknown production table, and do not put real account identifiers in a lab transcript. Audit/replication/trigger side effects may occur even when an application intends to roll back—know the deployment contract.

10 · On the job

Detection-engineering scenarios

INGEST

Event and derived alert must agree

Insert the raw event and alert record in one transaction. If alert validation fails, rollback both and retain a safe rejection record through a separate declared path.

BACKFILL

Batch includes one malformed record

Choose and document atomic whole-batch rejection or savepoint-per-record quarantine. Do not accidentally create a mixture of committed rows and an unreported failure.

RACE

Two workers claim the same investigation

Use an explicit concurrency design—constraint, locking strategy, or atomic update—and test retry semantics. A transaction alone does not say which worker wins.

QA

Constraint failure leaves unclear state

Reproduce in a disposable database, verify the engine’s aborted/rollback behavior, and add a test that queries final state rather than trusting console text.

11 · Practice

Hands-on drills

1. Prove atomic success

25 min

Save artifacts/transactions/success.sql and success-proof.txt for a synthetic account/request pair committed together.

  • State each table invariant.
  • Show rows before and after commit.
  • Explain why two autocommit statements would differ.

2. Trigger failure then rollback

30 min

Save failure.sql and rollback-proof.txt: insert a valid row, trigger a CHECK/UNIQUE/FK failure, roll back, prove no change.

  • Use only a disposable local database.
  • State PostgreSQL aborted-transaction difference if comparing engines.
  • Query final state explicitly.

3. Write an isolation decision note

25 min

Save isolation-note.md for a synthetic two-worker alert-claim scenario.

  • Name the anomaly/race to prevent.
  • Describe PostgreSQL and SQLite differences.
  • State retry/idempotency behavior.
