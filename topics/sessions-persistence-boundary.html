Keep browser state opaque and storage replaceable.

01 · Purpose

Login state crosses two trust boundaries

The browser stores a cookie; the server resolves opaque state; the application reads account data. Keep those concerns separate so session revocation, storage migration, and tests remain possible.

CONFIDENTIALITY

Opaque ID

Cookie contains an unpredictable reference, not profile/secrets.

REVOCATION

Server state

Delete/expire a session centrally.

DESIGN

Repository boundary

Routes call domain methods, not SQL strings.

TESTS

Fake storage

Inject disposable repository/session implementation.

02 · State flow

Browser cookieopaque session ID; Secure/HttpOnly/SameSite policy.
→
Session storeprincipal, expiry, rotation/revocation metadata.
→
Repository/serviceauthorized account/domain data.

Cookie possession is an authentication credential; protect issuance, transport, expiry, rotation, and server-side lookup. Authorization is still evaluated for each protected action.

03 · Opaque server-side sessions

import secrets
session_id = secrets.token_urlsafe(32)  # store server-side with account_id, expiry
# Cookie value is session_id, not JSON user profile/password/authorization claims.

Use: a cryptographically secure random identifier from secrets. Risk: do not use predictable IDs, store secrets in client-readable state, or log the session ID. Session rotation on login/privilege change and expiry/revocation policy belong to the authentication design.

04 · Cookie transport policy

response.set_cookie("session", session_id, httponly=True, secure=True,
                    samesite="lax", path="/")

Use: production HTTPS cookie policy. Assumption: TLS terminates correctly and browser/client behavior matches deployment. Risk: secure=True can prevent local HTTP development cookie return; use a clearly isolated development setting, never silently weaken production. Cookie flags help but do not replace CSRF controls, server-side session validation, or XSS prevention.

05 · Repository boundary

from typing import Protocol
class AccountRepository(Protocol):
    def find_by_email(self, email: str): ...
    def create(self, email: str, password_hash: str): ...
    def get_account(self, account_id: str): ...

Routes/services depend on this domain-shaped contract; SQLite implementation owns parameterized SQL, connections, and mapping rows to values. Do not expose arbitrary query methods that let handlers build SQL or bypass tenant/authz policy.

06 · SQLite is a local Week 10 tool

SQLite is embedded, file-backed, and useful for a single-process/disposable learning app. It has concurrency/locking characteristics unlike a server database: many readers are possible, but writes serialize; long transactions can cause lock contention. WAL and timeout settings are deployment choices, not blanket fixes. Use parameterized queries and per-request/clearly scoped connections; do not share one unsafe connection across threads without understanding the driver setting.

07 · Atomic state changes

with connection:  # sqlite3 transaction context in local repository
    connection.execute("INSERT INTO sessions(id, account_id, expires_at) VALUES (?, ?, ?)",
                       (session_id, account_id, expiry))

Use: parameterized local transaction for a small atomic write. Risk: transaction/context behavior depends on Python sqlite3 isolation/autocommit version settings; inspect current docs and test failure/rollback. Never interpolate user values into SQL.

08 · Test boundaries

Use a temporary/disposable SQLite path or an in-memory database with connection-lifetime caveats, then inject the repository dependency. Test login creates a server-side session, invalid session redirects/denies, logout revokes it, and route code never needs to know SQL. Do not use production DBs or real credentials.

09 · Safety

Session IDs are secretsDo not put them in URLs, logs, analytics, error pages, or client-side storage. Use HTTPS in deployment, secure cookie policy, server-side expiry/revocation, rate controls, and protected diagnostics. SQLite is not a production multi-writer architecture plan.

10 · Detection scenarios

SESSION

Cookie appears in application logs

Redact/quarantine logs, rotate affected sessions, and audit request/error middleware that recorded it.

LOGOUT

Logout does not invalidate access

Verify server-side lookup/revocation; deleting the browser cookie alone is not enough.

LOCK

SQLite writes intermittently fail

Measure transaction duration/concurrency and redesign boundary; do not add blind retries that duplicate session/account actions.

MIGRATE

Route tied to SQLite SQL

Extract repository contract and test fake implementation before changing storage engine.
