Detection stack · browser layer

Turn client signals into bounded, fair evidence.

Browser properties, rendering behavior, and interaction telemetry can help prioritize abusive automation—but they vary across legitimate devices, assistive technology, privacy tools, browsers, and network conditions. Collect the minimum, retain it briefly, and make no single signal a verdict.

Why this matters

Application and edge logs say what reached a route; browser-side telemetry can add careful context about whether a first-party page completed expected capabilities or an account flow has an unusual shape. It is useful for fraud and abuse triage, tuning, and post-incident explanations. It is not a way to identify a person, prove a device, or deny access merely because a browser looks uncommon.

The same property may result from a normal browser update, accessibility software, remote desktop, privacy setting, or automation. Preserve the observation point and uncertainty.

Browser and navigator state

navigator exposes browser-supplied information such as language preferences, platform-related compatibility values, hardware-concurrency hints, and automation state. Values can be reduced, frozen, absent, permission-gated, extension-affected, or different in embedded/mobile browsers. Treat a missing API or unusual combination as a compatibility outcome to investigate, not an identity claim.

Record normalized categories and feature availability rather than raw high-entropy values whenever the detection question permits it. The WebDriver standard intentionally exposes navigator.webdriver so pages may adapt to controlled browsers; it should never be used to punish test infrastructure or users.

Headless and CDP context

Headless execution is a browser mode, not a motive: accessibility testing, CI, synthetic monitoring, rendering, and internal QA may use it legitimately. Chrome DevTools Protocol (CDP) is a documented instrumentation and debugging protocol used by DevTools and many developer tools. Some products label particular API combinations, timing patterns, or instrumentation side effects as “CDP artifacts”; those labels are product-specific observations, not a universal CDP detector.

BoundaryDo not publish tests that teach a client to conceal automation or defeat an external anti-bot system. In this course, compare only browser modes you own against learner-owned AbuseGuard or a supplied sanitized fixture, and use the result to improve allowlists, test labels, or a step-up path.

Canvas, WebGL, and audio are noisy rendering evidence

A canvas draw/readback, WebGL renderer/capability report, or Web Audio render can vary with GPU, driver, operating system, browser version, color pipeline, virtualization, privacy defenses, battery/thermal state, and user settings. They can be high-entropy and privacy-sensitive. Prefer a coarse capability or stable first-party compatibility result; do not retain raw pixel buffers, detailed renderer strings, or audio output unless a documented, reviewed purpose requires it.

If a feature is used, version the exact test, hash or bucket the result where appropriate, measure collision and change rates on consenting first-party traffic, and provide an accessible fallback. A challenge or service path must remain usable for keyboard navigation, screen readers, reduced-motion users, non-pointer input, slow devices, and users who decline optional telemetry.

Behavioral signals measure a flow, not “humanness”

Useful low-risk aggregates include time from rendered form to submit, count of failed submissions, route sequence, focus/blur transitions, and server-observed retry cadence. Pointer velocity, scroll cadence, keystroke timing, and touch gestures are especially sensitive and confounded by motor disabilities, switch or voice control, password managers, mobile keyboards, translation tools, latency, and browser backgrounding. Avoid collecting raw keystrokes; do not require pointer movement or a particular cadence to succeed.

Privacy, minimization, and accessibility review

  1. Name the purpose. For example: reduce automated account creation on a first-party signup route—not “fingerprint all visitors.”
  2. Minimize. Use coarse derived fields, sample where possible, omit content and direct identifiers, and limit access.
  3. Set a retention and deletion rule. Document owner, duration, aggregation, and incident-only access.
  4. Test disparate breakage. Include keyboard-only, screen-reader, mobile, privacy-hardened, remote/virtual, and automated QA paths in evaluation.

Obtain the approvals your organization requires for telemetry, consent, notices, and data transfers. Legal compliance is jurisdiction- and implementation-specific; it cannot be inferred from the technical feature.

Defensive evidence workflow

// First-party AbuseGuard example: derive coarse event facts, not identity.
const event = {
  route: location.pathname,
  webdriverReported: navigator.webdriver === true,
  languageCount: navigator.languages?.length ?? 0,
  elapsedMsBucket: Math.floor((Date.now() - pageShownAt) / 500) * 500
};
// Send only under your approved telemetry policy; do not include typed values.

The code is a controlled instrumentation sketch for a learner-owned application. It deliberately avoids canvas pixels, audio output, pointer paths, raw screen/GPU details, and third-party collection. Log schema version, consent/policy context, and whether the page was an expected browser route. Join an alert to server evidence before action; measure precision, completion rate, support tickets, and accessibility failures after each policy change.

Detection-engineering scenarios

1. Signup burst from an internal QA run

Trigger: a signup-rate rule fires. Artifact: first-party event records show webdriverReported=true with the CI run label and expected test accounts. Observation point: AbuseGuard’s signup page and server audit log. Reasoning: correlate the explicit test identity, time window, and account allowlist before suppressing the alert. False-positive boundary: WebDriver alone does not identify the run; retain rate protection for unlabelled or compromised automation.

2. High-risk checkout has incomplete browser telemetry

Trigger: an account changes payment details after repeated failed attempts. Artifact: missing optional client event plus server-side failures and a new authenticated session. Observation point: first-party checkout and auth logs. Reasoning: missing telemetry may be an extension, network failure, or privacy setting; use it only to select a low-friction, accessible step-up verification. False-positive boundary: never block solely for absent JavaScript, canvas, or WebGL data.

3. Render-capability change after a browser update

Trigger: a coarse rendering bucket changes for a returning account. Artifact: bucket change, browser-version change, and successful normal session history. Observation point: consented first-party telemetry. Reasoning: a software update or GPU/remote-session shift is more likely than takeover without corroborating behavior. False-positive boundary: do not treat a capability change as a device replacement or account-compromise proof.

4. Impossibly fast form submissions

Trigger: many new accounts submit a multi-step form in the same short bucket. Artifact: server timestamps, route sequence, validation outcomes, and aggregate elapsed buckets. Observation point: application logs; client timing only supplements them. Reasoning: cluster by campaign and apply route-specific rate limits or review, then test an accessible challenge path. False-positive boundary: password managers, autofill, returning users, and fast networks can be quick; do not assume timing proves automation.

Artifact-producing drills

1. First-party signal register

Save artifacts/browser/signal-register.md for five proposed fields. Include purpose, collection point, granularity, retention, access, accessibility impact, and the alternative explanation for every field.

  • Reject at least one tempting high-entropy field as unnecessary.
  • State how a user can complete the flow if the field is absent.

2. Owned AbuseGuard comparison

In a local/staging AbuseGuard page you control, collect only the four coarse fields in the example for a normal browser, an approved automated test, and one privacy/accessibility configuration. Save artifacts/browser/mode-comparison.json after removing account IDs and timestamps precise enough to identify a person.

  • Label each run and observation point.
  • Write one legitimate explanation for each difference.

3. Fairness and response test

Save artifacts/browser/response-test.md: a proposed rule, its corroborating server evidence, step-up/fallback path, and outcomes for keyboard-only, JavaScript-disabled/privacy-hardened, mobile, and CI test cases.

  • Record completion and false-positive measurements.
  • Do not install or run a detector on another organization’s site.
