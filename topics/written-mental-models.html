01 · Purpose

Why write a model instead of memorizing a list?

Detection engineering rewards causal explanations. A written model lets you locate which component observed a fact, which assumption turned it into a conclusion, and where the conclusion can fail.

DEBUG

Locate the failing layer

“The page is broken” becomes a testable boundary: DNS, connection, TLS, proxy, route, handler, data, or response.

DETECT

Separate signal from verdict

A rate, TLS characteristic, header, browser behavior, or reputation is evidence with uncertainty—not a direct label of maliciousness.

COMMUNICATE

Explain decisions honestly

A one-page causal chain is more reviewable than a pile of terms and makes missing observability obvious.

LEARN

Measure improvement

Your preserved Week 0 pages are a before/after artifact for Week 14, not homework to silently replace.

Post-diagnostic onlyThis guide must not be used to prepare the Week 0 diagnostic. Save the original url-to-handler.md and bot-decision.md, including uncertainty and gaps; later additions belong in a clearly dated review file.

02 · Method

Write claims, boundaries, and uncertainty

A mental model is an executable explanation in prose: a reader should be able to turn its claims into an observation or a question. Keep it compact by answering the same six prompts for each hop.

PromptGood written answerWeak written answer
Who acts?Browser resolver, client OS, CDN edge, reverse proxy, application worker.“The internet.”
What crosses the boundary?A DNS query, TCP/QUIC packet, TLS handshake fields, HTTP request, or application object.“Data gets sent.”
What is observable?At this component, before/after encryption or termination, with a named log/source.“Cloudflare sees everything.”
What decision follows?Route match, auth check, score/action, cache decision, or handler invocation.“It knows it is a bot.”
What assumption matters?Trusted forwarding chain, DNS cache freshness, device-signal availability, identity binding.Unstated assumptions.
How could it be wrong?Shared IP, proxy, missing telemetry, clock skew, vendor/model change, false positive.“It cannot be wrong.”
Claim: The reverse proxy forwards a request to the application handler.
Evidence to seek: proxy access log + application request ID + route log.
Assumption: the proxy is the configured public entry point.
Limit: a matching request ID proves correlation, not that the upstream response was correct.
Next question: where is the original client address established and trusted?
Useful notationUse fact for directly documented/observed behavior, inference for a conclusion supported by facts, and unknown for a boundary you cannot inspect. That discipline prevents a confident diagram from becoming fabricated certainty.

03 · First one-pager

What happens between a URL and your handler?

The exact path depends on the browser, network, protocol, CDN/proxy configuration, and app framework. This is the smallest useful model for a common HTTPS web application, not a guarantee for every request.

InterpretBrowser parses scheme, host, port, path, query, and fragment.https://app.example.test/a
→
Reach serviceResolve host; establish a secure transport connection to the selected endpoint.DNS + TCP/TLS or QUIC
→
Serve requestEdge/proxy and app parse HTTP, choose a route, execute middleware and handler.GET /a → handler

The URL fragment (#section) is normally handled by the browser and is not sent in the HTTP request. The query string is normally sent and may be sensitive.

  1. Parse the URL. The scheme indicates a protocol family; host identifies the name to resolve; an omitted HTTPS port conventionally means 443. A browser may apply caches, service workers, HSTS, proxy settings, or local policy before a network request.
  2. Resolve the hostname. A resolver obtains an address from caches or authoritative DNS paths. The answer can point to a CDN/load balancer rather than your application host, and DNS alone does not authenticate the intended application.
  3. Establish transport security. HTTPS commonly uses TCP then TLS, or QUIC with HTTP/3. During TLS, the client validates a certificate for the hostname; failure normally stops the browser from treating the connection as trustworthy.
  4. Send the HTTP request. The request has method, target path/query, headers, optional body, and protocol framing. Cookies or authorization material may be attached according to browser policy; the fragment remains client-side.
  5. Cross the edge and reverse proxy. A CDN/WAF may cache, rate-limit, challenge, block, or forward. A reverse proxy can terminate TLS, add a request ID, normalize headers, and forward to an application over an internal network.
  6. Run the application pipeline. Framework middleware may parse the request, load session/auth context, enforce authorization, bind route parameters, validate input, invoke the handler, and serialize a response. The handler may call storage or other services before the response travels back through the chain.
URL: https://app.example.test/products?sort=recent#reviews

Network request target usually includes: /products?sort=recent
Browser-only fragment:                 #reviews
Possible evidence chain:
DNS resolver log → edge request ID → proxy access log → app trace → DB/query trace

Each arrow is a correlation opportunity, not proof that every component retained every field.

04 · Boundaries

Who can observe what?

Visibility changes as encryption is applied and terminated. Do not flatten “the network” into one observer.

Actor / pointCommonly observableNot automatically observable
Browser/clientFull URL, request/response content, cookies available to the browser, local timing.Server-side routing, database state, private vendor scoring logic.
On-path observer before TLS terminationIP/port metadata; often destination name exposure depending on protocol/configuration; traffic timing/size patterns.Encrypted HTTP headers, paths, bodies, and cookies.
TLS-terminating CDN/proxyDecrypted HTTP it terminates; connection and request characteristics; its own policies and logs.Origin application internals unless forwarded/logged; another provider’s telemetry.
Application handlerForwarded request representation, app/session context, route data, application timing.Original network facts not preserved through proxying; private edge model features.
Forwarded address is a trust boundaryX-Forwarded-For and similar headers are data. An application should use them only when a known proxy strips untrusted inbound values and sets a verified chain. Otherwise an external client can supply a misleading header.

05 · Second one-pager

How can Cloudflare decide that traffic is automated?

No outside guide can state a provider’s current proprietary model, thresholds, or all features. A defensible model describes classes of evidence a bot-management service may combine, the policy action it can take, and the uncertainty that remains. It is a defender’s model—not an evasion recipe.

ObserveConnection, protocol, request, browser/client behavior, and historical/context signals where available.evidence
→
EvaluateRules and/or models estimate automation or abuse risk under provider/customer policy.score / category
→
Act & learnAllow, log, rate-limit, challenge, block, or route; monitor outcomes and tune.policy action

A score is an input to a decision. The action also depends on asset sensitivity, local policy, confidence, and operational cost of a false positive.

CONNECTION

Network and transport context

Source/network reputation, connection patterns, protocol characteristics, and consistency may be relevant signals; none uniquely proves automation.

REQUEST

HTTP and behavior context

Request rate, path sequence, failure patterns, header consistency, and session continuity can show behavior that diverges from expected users.

CLIENT

Browser/client evidence

When a provider can collect it lawfully and technically, browser execution or client characteristics may add evidence, with privacy and accessibility implications.

HISTORY

Reputation and feedback

Prior observed outcomes, customer policy, and abuse reports can influence treatment. Reputations are contextual and can change.

Defensive decision record (example)
fact: login attempts from one source key rose 20× in 10 minutes
fact: attempts cover 500 accounts; successful logins remain near baseline
inference: credential-stuffing risk is elevated, but source key may be shared
action: apply approved rate limit / step-up verification policy; preserve telemetry
unknown: whether the client is an individual, corporate NAT, or automated service
review: measure false positives, successful challenge rate, and account impact

Documented Cloudflare facts versus unknowns

Public documentation saysWhat you still cannot claim
Bot Management scores range from 1–99: lower means Cloudflare is more certain a request is automated; higher means it is more certain the request is human.A score does not reveal private feature values, model weights, a customer's action threshold, or the intent of a person behind a request.
Score 0 means Bot Management did not evaluate the request; it does not mean safe or human. Bot Analytics also exposes automated, likely automated, likely human, and verified-bot groupings.Group availability and granular score access are plan- and configuration-dependent, and a verified bot category is not a universal allow decision.
Cloudflare documents Enterprise Bot Management engines including heuristics, supervised machine learning, and optional JavaScript detections.Those public categories are not a complete or stable description of proprietary logic. Recheck official documentation before designing policy.
Do not reverse-engineer an adversary playbookFocus on authorized defenses: signal quality, auditability, privacy, false positives, and recovery paths. Do not test ways to bypass third-party bot controls, impersonate browser signals, or evade a service on systems you do not own.

06 · Reasoning

From observation to a proportionate action

A good detection model contains feedback. It makes the action reversible or reviewable where possible and measures the harm it can cause.

Observation → normalization → correlation → hypothesis → policy decision → outcome review

Example:
request timestamps → per-account/per-source rate → unusual credential fan-out
→ possible automated login abuse → temporary, scoped control
→ challenge/block outcome + support tickets + account recovery review
Correlation ID

Connect one request across layers.Use it to compare edge, proxy, app, and downstream events; do not assume an absent ID means a request did not occur.

Baseline

Describe normal before calling something anomalous.Use comparable time windows, routes, client classes, and deployment state.

False-positive review

Measure control harm.Pair security outcomes with accessibility, customer-support, conversion, and legitimate automation needs.

Retention & minimization

Keep only justified telemetry.Browser/client signals and identifiers can be sensitive; follow policy and legal requirements.

Platform assumptions: the URL model assumes a browser accessing an HTTPS service; native clients, enterprise proxies, service meshes, and HTTP/3 change details. Bot-management behavior is provider- and configuration-specific. Do not write secrets, real request bodies, account identifiers, or session tokens into the two saved pages.

08 · On the job

Detection-engineering scenarios

INCIDENT

A customer says the site is intermittently slow

Use the URL-to-handler model to ask for evidence at each boundary: resolver behavior, edge timing, proxy upstream time, handler trace, and database latency. This avoids treating a browser symptom as proof of a database incident.

FALSE POSITIVE

An approved integration is challenged as automated

Start with the documented policy/action and the integration’s authorized traffic characteristics. Compare it with legitimate cohort behavior, then scope an allow/rate policy through approved controls. Do not try to make the client mimic a browser.

AUTH ABUSE

Login failures grow rapidly

Model the evidence chain: request routing, trusted client key, account fan-out, response class, and successful-login follow-through. A high failure count can be an attack, a broken client release, or a changed authentication dependency.

OBSERVABILITY

The origin sees one IP for every request

The boundary model points to the proxy configuration rather than a detection threshold. Verify which component sets and trusts forwarded client information, document the chain, and test with authorized synthetic traffic before changing attribution logic.

09 · Practice

Hands-on drills

These drills create durable before/after evidence. The first versions must remain untouched after the diagnostic; add a dated review companion rather than rewriting history.

1. Save the original URL-to-handler page

30 min

Save url-to-handler.md with one page of your original explanation and url-to-handler-review.md with corrections after review. Include the fragment/query distinction, DNS, secure connection, edge/proxy, route, handler, and response.

  • For every arrow, name the actor and one thing it can observe.
  • Mark at least three assumptions or unknowns rather than filling gaps with certainty.
  • Use no real domain secrets, cookies, request bodies, or production trace IDs.

2. Save the original bot-decision page

30 min

Save bot-decision.md and a separate bot-decision-review.md. Describe evidence classes, uncertainty, policy actions, false-positive risk, and feedback. Keep it defensive and vendor-agnostic where facts are not public.

  • Label every sentence as fact, inference, or unknown in the review copy.
  • State why a score/action is not proof that a person is malicious.
  • Include one recovery/review mechanism for a legitimate user or integration.

3. Build an evidence-boundary matrix

25 min

Save visibility-matrix.md for client, on-path observer, edge/proxy, and application. Add one row for URL/path, headers, body, client address, request ID, and timing.

  • Distinguish encrypted-in-transit from visible-after-termination.
  • Identify the trusted proxy/configuration assumption for client address.
  • List one telemetry field you wish existed and the privacy/retention trade-off it introduces.
