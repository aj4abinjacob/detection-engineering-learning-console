01 · Purpose

HTTP is evidence with declared meaning

A request is not automatically benign because it is GET, and a 200 is not automatically a successful business outcome. Still, protocol semantics give the baseline that lets a detector identify unexpected patterns.

ROUTING

Target and method

Explain what handler was requested.

OUTCOME

Status family

Separates redirect, client refusal, and server fault.

RETRY

Idempotency

Informs safe retry intent, not business safety proof.

TELEMETRY

Context matters

Correlation fields and trusted client identity qualify a request.

02 · Message model

GET /products?limit=10 HTTP/1.1
Host: lab.example
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 18

{"items":[...]}

A request line has method, target, and version; header fields carry metadata; a blank line ends the header section; framing determines any content. A response starts with version/status/reason phrase (reason text is not a reliable machine category), then headers and optional content. HTTP/2/3 encode these concepts differently; do not parse their bytes as HTTP/1.1 text.

03 · Methods

MethodUsual semanticsDetection question
GET/HEADSafe retrieval; HEAD omits response contentWhy does a safe route cause state change?
POSTSubmit/process, often non-idempotentAre retries creating duplicates?
PUTReplace/create target representationIs full replacement authorized?
PATCHPartial modificationWhich patch format/fields are accepted?
DELETERequest removalIs authorization/audit present?
OPTIONSCommunicate optionsIs CORS/preflight behavior expected?

Safe and idempotent are RFC semantics/intent, not guarantees that a particular implementation has no side effects. GET logging, billing, cache fill, or a buggy handler can change state; an idempotent request may still return different status as state changes.

04 · Status families

1xx informational; 2xx successful protocol handling; 3xx redirection; 4xx client-request/authz/authn category; 5xx server failure category. Record exact code: 401 authentication challenge differs from 403 authorization refusal; 404 can be intentional concealment; 429 says rate limit. Application errors can still be embedded in a 200 response.

05 · Target, headers, content

Origin servers normally receive origin-form targets such as /login?next=/; proxies can see other request-target forms. Decode/canonicalize only under a declared policy: percent encoding, duplicate query keys, Unicode, and path normalization affect route telemetry. Do not log full sensitive bodies or query strings by default—select allowed fields and size-bound them.

06 · Retry and cache implications

Idempotent methods are designed so repeating the same request has the same intended effect, enabling intermediaries/clients to retry after transport uncertainty. POST may be made idempotent by an application key, but that is an application contract. Detection should correlate retries by request/operation ID, not assume method alone proves duplicate abuse.

07 · Useful event shape

{"request_id":"lab-r17","method":"POST","route":"/login","status":401,
 "duration_ms":12.4,"tenant":"lab","client_identity_source":"trusted_proxy"}

Use: store normalized bounded fields and a documented identity source. Risk: raw headers/URLs/bodies can contain credentials, personal data, and hostile control characters. Preserve protected raw evidence only under a retention/access policy.

08 · Safety

Protocol semantics are not authorizationNever infer that DELETE is permitted, a client is malicious, or a user owns a resource merely from a method/status. Validate at the application authorization boundary and use local synthetic traffic for exercises.

09 · Detection scenarios

RETRY

POST checkout retries spike

Correlate idempotency/request IDs and transport errors; method alone cannot distinguish a client retry storm from duplicate intent.

AUTH

401/403 rate changes

Separate authentication failures from authorization refusals and join with trusted tenant/client context.

ROUTES

Unexpected state-changing GET

Flag implementation behavior against method semantics, then validate handler code and legitimate integration use.

OUTAGE

5xx grows while 2xx remains

Inspect exact status, route, latency, and application result; aggregate status family is only first triage.

  • Label start line, headers, blank line, body/framing.
  • Use no secrets or real hosts.
  • Explain every status/method choice.

2. Ten statuses

20 min

Make artifacts/8.1-statuses.md classifying ten exact codes and one caveat each.

  • Include 401,403,404,429,500.
  • Separate protocol from business success.
  • State telemetry fields needed.

3. Local AbuseGuard contract

25 min

Document methods/statuses for one local route and save a sanitized event example.

  • State safety/idempotency intent.
  • Define authorization check.
  • Set body/log size policy.
