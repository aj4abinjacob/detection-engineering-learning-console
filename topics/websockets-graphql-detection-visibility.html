Observe the operation, not just the endpoint.

01 · Purpose

One URL can represent many actions

A REST route often approximates an operation. A WebSocket remains open for messages; GraphQL commonly shares one endpoint for many named operations and selected fields. Visibility must move up a layer.

LIFECYCLE

Connection context

Open/close/reconnect/message rate are separate signals.

SEMANTICS

Operation identity

GraphQL operation/field shape matters more than /graphql.

AUTHZ

Every resolver/message

Handshake authentication does not authorize all actions.

CAPACITY

Bound work

Depth, complexity, size, and concurrency are policy inputs.

02 · WebSocket model

A WebSocket begins with an HTTP Upgrade handshake, then becomes a persistent bidirectional framed message channel (RFC 6455). The initial route/status alone cannot describe subsequent message types. Define authenticated connection context, allowed message schema, per-message authorization, size/rate/concurrency limits, ping/close handling, and audit events. Browser origin behavior is not a complete authorization control; validate credentials and origin policy deliberately.

03 · GraphQL model

GraphQL clients submit a document naming operation type/name, fields, arguments, variables, and fragments; the server resolves a schema-defined graph. A single endpoint means REST per-route rules do not map one-to-one. Persisted/allowlisted operations, schema validation, resolver authorization, depth/complexity limits, pagination, and request-size/time limits give more useful defenses than URL counts alone.

Collect only bounded, privacy-reviewed dimensions. Do not log full GraphQL variables or WebSocket messages: they can contain credentials, personal data, and hostile payloads.

05 · Authorization stays at the action

Authenticate a connection/request, then authorize each subscription, message action, resolver, object, and field as applicable. Avoid assuming a valid session can access every object selected by a GraphQL query or every message after WebSocket upgrade. Return controlled client errors and protected internal diagnostics; do not leak schema/object existence through inconsistent errors.

06 · Abuse controls are resource policy

{"operation":"GetAccount","depth":3,"estimated_cost":12,
 "result":"allowed","request_id":"lab-r18"}

Use: enforce documented maximum message/request bytes, parsed depth, complexity/cost, pagination, resolver timeout, connection count, and messages per interval. Assumption: cost model is tested against actual resolver fan-out. Risk: a simplistic depth rule misses wide queries; a cost model can undercount custom resolvers. Apply backpressure/rate limits and observe rejects without labeling them automatically malicious.

07 · Event contract

For WebSocket: connection ID, authenticated principal/tenant pseudonym, handshake outcome, message type allow/deny, bounded size, rate bucket, close code, duration. For GraphQL: operation name/hash, selected field classes or approved persisted ID, validation/authz/cost outcome, resolver latency summary, row/page limits, request ID. Associate client network data only through explicit trusted-proxy policy.

08 · Safety

“Blind spot” is not “bypass”WebSocket and GraphQL need different observability; they do not inherently defeat controls. Exercise only local AbuseGuard/synthetic endpoints, set hard resource caps, and never use production schemas, credentials, real user messages, or third-party endpoints.

09 · Detection scenarios

SOCKET

One connection emits thousands of messages

Route telemetry shows one upgrade; message-rate/size/type metrics reveal load. Validate legitimate realtime client behavior before action.

GRAPH

One GraphQL URL has expensive queries

Observe operation/cost/field classes and resolver time; add tested complexity/pagination limits rather than blocking endpoint-wide.

AUTHZ

Authorized user requests another account

Resolver/object authorization must reject it; authentication at endpoint/handshake is insufficient evidence of permission.

RECONNECT

Clients reconnect in a storm

Track close codes, edge failures, app health, and backoff behavior; a spike can be outage recovery rather than abuse.
